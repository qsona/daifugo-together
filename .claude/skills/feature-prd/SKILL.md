# 機能 PRD を書いて実装を依頼する

設計側(このリポジトリで開発者と議論しているセッション)が、議論の結論を PRD に固定し、別セッションの実装担当へ引き渡すまでの手順。

## 1. 前提

先に [docs/implementation-guide.md](../../../docs/implementation-guide.md) を読む。特に **§1(変更権限の 3 段階)**、**§8(PRD テンプレート)**、**§9(ファイルの置き場)**。

PRD はガイド §8 のテンプレートに従って書く。**テンプレート本体や権限ラベルの定義をこのスキルに書き写さない** — 正はガイド側にあり、更新はガイドだけに入る。レビュー種別の語彙は [docs/review-guide.md](../../../docs/review-guide.md) §4 に従う。

## 2. 議論の結論を固定する

PRD の `[変更不可]` 層(背景と目的 / ユーザー体験 / 受け入れ条件 / スコープ外)には、**開発者と議論して合意した内容だけ**を書く。

- 議論で決まっていないことを、勝手に「決定」として `[変更不可]` に書かない。設計側の推測が開発者の決定として実装担当に届いてしまう
- 埋まらない欄がある(受け入れ条件が曖昧、スコープ外の線引きが未確認、文言が未定 など)なら、**書き始める前に開発者に確認する**。確認は AskUserQuestion 等で簡潔に、選択肢を示して聞く
- 確認するほどでもない細部なら、`[変更不可]` に上げず下の層へ回す(§3)
- **セルフチェック**: `[変更不可]` に書いた各項目について「議論のどのやり取りで合意したか」を言えるか確かめる。言えないものは書かず、開発者への確認に回す
- 意図的に未決のまま実装に渡す項目(設計側が「妥当な仮定を置いて進んでよい」と明示するもの)は、`[変更不可]` に書かずテンプレート §7「未決事項」に書く

## 3. 層の振り分け(このスキルの核)

書こうとしている一文ごとに、どの層に置くかを決める。

| その内容の出どころ | 置く層 |
|---|---|
| 開発者が明示的に決めたこと / ユーザーから見える挙動(画面・文言・遷移) | `[変更不可]` |
| 設計側が単独で導出した詳細仕様・エッジケースの扱い・エラー時挙動 | `[変更可・記録必須]` |
| コード調査に基づく実装方針・`file:line` アンカー・既存構造のメモ | `[参考]` |

- `[変更可・記録必須]` は**実装担当のレビューを歓迎する層**。ここを厚く正確に書くほど実装の質が上がる。「どうせ変えられる」と薄く書くのではなく、現時点の最善案を根拠付きで書く
- `[参考]` には調査済みの根拠(どのファイルの何がどうなっているか)を書いておく。実装担当の再調査コストが下がる。ただし実装を縛るものではない。アンカーはずれる前提で、関数名など取り直せる手がかりを添える
- **迷ったら、保護の強い側ではなく弱い側に置く。** 実装担当の裁量を不必要に奪わない
- ただし**ユーザー体験に関わるものは、迷っても必ず `[変更不可]`**。黙って変えられて困るのはここだけ

## 4. ファイルを作る

`docs/specs/YYYY-MM-DD-<slug>.md`(slug は ASCII)。1 ファイルが既定で、大型機能では `-design.md` / `-implementation.md` の分冊も可(implementation-guide §9)。

冒頭の「状態」行は **起草中**で作り、実装を依頼する時点で**実装中**へ更新する。

## 5. status.md に登録する

[docs/status.md](../../../docs/status.md) の「進行中」に 1 行足す。含めるもの: 機能名 / PRD へのリンク / 依頼先(どのセッションに投げたか)/ 指定したレビュー種別。

status.md がまだ無ければ、`## 進行中` / `## 外部ゲート・受入待ち` / `## 人間判断待ち` / `## 小粒の残件` の見出しだけの薄いファイルとして作る。

## 6. 実装依頼文を出す

**依頼を出す前に、PRD と status.md を `main` へ取り込む**(AGENTS.md の運用に従う)。実装担当は別 worktree・別 clone のセッションであることがあり、未コミットのファイルは見えない。

実装担当セッションにそのまま貼れる短い依頼文を出力する。含めるもの:

- `AGENTS.md` と `docs/implementation-guide.md` を先に読むこと
- 対象 PRD のパス
- レビュー種別の指定 — 小規模なら「レビューなし」または「完了レビューのみ」、大型なら「2 パス + 中間レビュー(+ 仕上げ後に完了レビュー)」。判断の目安は implementation-guide §3
- 追加の制約があれば明記(期限、触ってはいけない領域、先に取り込むべき変更 など)

**渡すのはこれだけ。会話の要約も、設計側の言い分も渡さない。** 実装担当は独立したセッションで、PRD に書いていないことは伝わらない。書き切れていないと気づいたら、依頼文で補うのではなく **PRD に戻って書く**。これは implementation-guide §3 がレビュアーへの依頼に課しているのと同じ独立性の原則。

## 7. 実装報告を受けたら

1. **仮定の裁定** — PRD 実装記録の「置いた仮定」を確認する。レビューを入れた依頼ではレビュアーが裁定済み。**レビューなしの依頼では、設計側が代わりに裁定せず、開発者に確認して裁定を得る**
2. **decision-log への反映** — レビューを入れた依頼では、レビュアーが [docs/decision-log.md](../../../docs/decision-log.md) へ反映済みか確認する(review-guide §6)。レビューなしの依頼では、開発者の裁定を設計側が反映する。採用は決定として記録し、人間判断が必要なものは未決事項として台帳に載せる
3. **status.md の更新** — 行を更新する。完了なら行を消す(進行中だけを持つファイルなので残さない)
4. **PRD の状態を「完了」へ** — 冒頭の状態行を更新する
5. `[変更不可]` 層への提案が報告に含まれていたら、開発者に上げる。設計側だけで採否を決めない
