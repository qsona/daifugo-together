## 1. 戦い方の全体方針

フォロワーが少ない個人開発アカウントでは、**1本のポストで広く届くことはまず起きません**。狙うべきは「誰かの引用・リポストで界隈の外へ跳ぶ」ことで、そのために必要なのは**一文で説明できる異物感**です。このゲームの異物感は「ユーザーがルールを提案すると、AIが実装して本当にゲームが変わる」の一点に集約されます。ここを主語にしないポストは、ただの「大富豪つくりました」になって埋もれます。

刺さる層は3つ、優先順位は次のとおりです。**(1) AI・個人開発界隈** — 「AIがゲームを自動改造する」は仕組み自体が話題になり、この層は引用リポストで拡散してくれる。ここが唯一の跳躍口なので初速はここに賭けます。**(2) ローカルルールで盛り上がった経験のある大人** — 「うちの地元では8切りが〜」という語りたい欲を刺激でき、リプが伸びやすい(リプが伸びると表示も伸びる傾向があります)。**(3) 実際に遊ぶ子供〜学生層** — Xにはほぼいません。ここへは大人経由(親・兄姉・先生)と口コミで届くので、X上で直接狙わない。

そして重要な前提として、**Xの初日は本番ではなく前哨戦**です。本命は数日後に出す技術記事(§6)で、そこからのはてなブックマーク経由の流入が個人開発では一番読まれます。X告知は「記事を出したときに参照される最初の一次情報」を置く作業だと捉えてください。

## 2. リリース告知ポスト本文 3案

**どれか1本を選んで投稿します。3本とも投稿するのは避けてください**(同じ内容の連投は自分のフォロワーの体感が悪く、どれも伸びません)。迷ったら **案A** を推奨します。異物感が最も素直に出ていて、拡散してくれる層(AI・個人開発界隈)に直撃するためです。

いずれも改行込みでX上の文字数制限(全角140字相当)に収まっていることを計測済みです。**そのままコピペしてください**。URLは最終行に単独で置いています(本文中に挟むと読み飛ばされ、末尾単独だとタップされやすい)。

### 案A: 仕組みの異物感で殴る(個人開発・AI界隈向け / 推奨)

```text
オンライン大富豪をつくりました。

遊んだ人が「このルール入れたい」と提案すると、AIが実装して本当にゲームに入ります。8切りも革命も都落ちも、この仕組みで入りました。

登録なし・ブラウザだけ。空席はAIが埋めるので1人でも遊べます。

毎日どこかで、新ルール。
https://daifugo-together.fly.dev/
```

狙い: 1行目で「何を作ったか」、2段落目で「他と何が違うか」を言い切る。既存ルールを例に出すことで、抽象的な「AIが実装」を具体に落としています。キャッチコピーを最後に置いてブランドの締めにする構成。
添付: 動画があれば動画。なければスクショ4枚(§3)。
**「この仕組みで入りました」という言い方を変えないでください。** 現在入っている10種類は公開前に開発者自身が提案して通したもので、一般ユーザーの提案はまだゼロです。「そうやって入りました」等と書くと「もう誰かが提案した」と誤読されます。リプツリー2本目(§4-2)でこの点を明示する設計にしています。

### 案B: 共感から入る(一般・ノスタルジー向け)

```text
大富豪、「うちの地元ではこうだった」ってルールありますよね。

そのローカルルールを提案するとAIが実装して、みんなの卓で遊べるようになる大富豪をつくりました。提案には都道府県を添えられます。

登録不要、スマホのブラウザで4人対戦。空席はAIが埋めます。
https://daifugo-together.fly.dev/
```

狙い: 開発の話を一切せず、読み手の記憶から入る。「うちは違った」というリプを誘発しやすく、**リプ欄が勝手に盛り上がる**のが最大の効用。技術に興味がない層にも届きます。フォロワーに非エンジニアが多いならこちらが有利。
添付: 提案フォーム(都道府県を選んでいる画面)を1枚目に置くと、文とスクショが噛み合います。

### 案C: 実例で笑わせる(ネタ・バズ狙い)

```text
「10を出したら、その枚数だけ手札を捨てる」

こういうルールが、提案→AIが実装、という流れで本当にゲームに入ります。今は8切り・革命・都落ち・スペ3返しなど10種類が稼働中。放っておくと増えます。

登録なしで遊べるオンライン大富豪です👇
https://daifugo-together.fly.dev/
```

狙い: 冒頭を鉤括弧の異物で始めてスクロールを止める。「放っておくと増えます」で世界観(カオスが育つ)を一言で伝えます。リスクは、ゲーム名も自己紹介もないため**通りすがりには何のポストか分かりにくい**こと。フォロワーがある程度いて、ネタが回りやすいアカウントなら強い。
添付: ルール一覧かルール図鑑(`/rules`)のスクショ必須。「10種類が稼働中」の証拠になります。
**投稿前に必ず** `https://daifugo-together.fly.dev/rules` で稼働中の種類数を数え、10でなければ本文の数字を実数に直してください。

## 3. 添付メディアの指示

### 3-1. 何を添付するか(優先順)

1. **15〜30秒の縦動画1本**(最強)。動きがないと「AIが実装して本当に変わる」が伝わりません
2. 動画が間に合わないなら **スクショ4枚**
3. 5〜8秒の**GIF**は、動画の代わりではなく「ルール発動の瞬間だけ」を見せたいとき(§5の平日ポスト向き)

スクショ4枚の中身は次で固定します。順番に意味があります(1枚目がタイムラインで最も大きく出るため)。

| 順 | 画面 | 撮り方 |
|---|---|---|
| 1 | タイトル画面(キービジュアル) | 開いて最初の画面をそのまま。「ちゃんとしたゲーム」だと一目で伝える役 |
| 2 | 対局画面(自分の手番) | 手札トレイと「あなたの番」が出ている状態。カードが読める瞬間を選ぶ |
| 3 | ルール発動のカットイン、または部屋の有効ルール一覧 | ルール名が並んでいる絵が「増殖」を一番よく表す |
| 4 | ルール提案フォーム(都道府県を選んでいる状態) | 「自分が提案できる」を証明する役 |

### 3-2. 撮影手順(Mac)

**方法A: Chromeのデバイスモードで撮る(推奨・速い)**

1. Chromeで `https://daifugo-together.fly.dev/` を開く
2. `⌥⌘I` で DevTools → `⇧⌘M` でデバイスツールバー → 端末を **iPhone 12 Pro (390×844)** にする → ズーム100%
3. DevToolsを閉じずに、画面右側の端末枠だけが見える状態にする
4. 静止画: `⇧⌘4` → スペースキーではなくドラッグで**端末枠の内側だけ**を範囲選択(枠線や背景を入れない)
5. 動画: `⇧⌘5` → 「選択部分を収録」→ 端末枠の内側だけを選択 → 収録開始

**方法B: iPhone実機で撮る(絵は一番きれい)**

1. 設定 → コントロールセンター → 「画面収録」を追加
2. 事前に「おやすみモード」をオンにして通知バナーが写り込まないようにする
3. コントロールセンターから収録 → 遊ぶ → 停止 → 写真アプリに `.mov` が入る
4. AirDropでMacへ送る

### 3-3. 動画の撮影内容(30秒の台本)

これをそのままなぞって1回撮ってください。撮り直しは2〜3回で十分です。

| 秒 | 操作 |
|---|---|
| 0-3 | タイトル画面をタップ |
| 3-7 | 「あそぶ」→「みんなのルールであそぶ」 |
| 7-20 | 実際にカードを出す。**8切りなどルールが発動してカットインが出る瞬間を必ず入れる** |
| 20-26 | 部屋の有効ルール一覧を開いて、ルール名が並んでいるところをゆっくり見せる |
| 26-30 | ルール提案フォームを開き、都道府県を選ぶところで止める |

ルール発動が撮れるかは運なので、**先に何回か遊んで発動する場面を確認してから収録**すると早いです。

### 3-4. 変換コマンド(ffmpeg)

```bash
# 未インストールなら
brew install ffmpeg

# 1) 頭の無駄を切って30秒に、X向けにエンコード(音声なし)
ffmpeg -i raw.mov -ss 00:00:02 -t 00:00:30 \
  -vf "scale=720:-2:flags=lanczos,fps=30" \
  -c:v libx264 -profile:v high -pix_fmt yuv420p -crf 22 \
  -movflags +faststart -an out.mp4

# 2) もし無音のせいでアップロードに失敗したら、無音の音声トラックを足す
ffmpeg -i out.mp4 -f lavfi -i anullsrc=channel_layout=stereo:sample_rate=44100 \
  -c:v copy -c:a aac -shortest -movflags +faststart out-audio.mp4

# 3) GIFが必要なとき(2パス。1パス変換より圧倒的に綺麗で軽い)
ffmpeg -i out.mp4 -vf "fps=12,scale=480:-1:flags=lanczos,palettegen=stats_mode=diff" -y palette.png
ffmpeg -i out.mp4 -i palette.png \
  -lavfi "fps=12,scale=480:-1:flags=lanczos[x];[x][1:v]paletteuse=dither=bayer:bayer_scale=3" -y out.gif
ls -lh out.gif   # 15MBを超えたら fps=10 / scale=360 / 秒数を削る

# 4) 動画から静止画を1枚抜く(スクショを撮り直さずに済む)
ffmpeg -ss 00:00:12 -i out.mp4 -frames:v 1 -q:v 2 shot.png
```

### 3-5. X上での動画・GIF・静止画の違い

- **動画**: タイムラインで自動再生され、再生数も計測されるので手応えが分かる。短いほど最後まで見られるので15〜30秒が扱いやすい。長さの上限は一般アカウントで2分20秒程度が目安(仕様は変わりうるので、投稿前に下書きで確認してください)
- **GIF**: 自動再生でループし、音は出ない。他のメディアと混ぜて添付できず1点のみ。**サイズ上限が厳しい**(モバイルで15MB程度が目安)ため、5〜8秒の一瞬を切り取る用途に限定するのが安全
- **静止画**: 最大4枚。タイムラインでは切り抜かれて表示されるため、**縦長スクショは上下が切れる前提**で、見せたい要素を画面中央に寄せた瞬間を選ぶ。4枚添付すると2×2で並びます
- **重要な副作用**: メディアを添付すると、URLのリンクカード(OGP画像)は表示されません。OGPを見せたいならメディアなしで投稿することになりますが、**自前のプレイ映像のほうが圧倒的に強い**ので、添付を推奨します
- 各メディアには**ALTテキスト**(代替テキスト)を付けてください。「スマホ画面の対局中のスクリーンショット」程度で十分です

## 4. 投稿タイミングと初動運用

### 4-1. 土曜昼は妥当

土曜12:00〜13:00 JSTは妥当です。理由は3つ。(1) 週末昼はスマホを触っている人が多い、(2) このゲームは**その場で友達を4人集めて遊べる**ので、人が暇な時間に出すほど実プレイに変換されやすい、(3) 家族で遊ぶ層(きほんモードの対象)が動ける時間帯。

一方、土日はビジネス・技術系の閲覧が平日より落ちるという定説があります。ただし個人開発者は週末にXを見ている人も多く、断定はできません。取るべき対策は**日を分けて二の矢を撃つこと**で、開発者界隈向けの深掘り(技術記事)は月曜の朝または夜に回します(§5)。

### 4-2. 投稿直後の60分でやること

1. **投稿する**(12:00〜13:00)
2. 自分のポストの「…」メニュー →「プロフィールに固定する」で**固定ポスト化**。以後プロフィールに来た人が必ず見る場所になります
3. **セルフリプライで補足ツリーを3本**ぶら下げる(下記テンプレ)。本文に入りきらない情報はここに置きます。ツリーは投稿から5〜10分以内に付け終える
4. **自分で1卓遊んで、本当に動いていることを確認**する。同時に `fly logs` を眺めてエラーが出ていないか見る
5. 初動1時間はスマホを手元に置き、**来たリプに全部返す**。最初の30分の反応が伸びに効きます
6. **デプロイしない**。ルールPRのマージ後にデプロイが走ると再起動でプレイ中の卓に影響します。初日はマージを止めてください

```text
遊び方はかんたんです。画面をタップして「あそぶ」→「みんなのルールであそぶ」で部屋ができるので、招待リンクかQRコードを友達に送るだけ。集まらなくても大丈夫で、空いた席はAIが埋めます。4人固定、3戦で1セットです。
```

```text
ルールが増える仕組みはこうです。①ルールを提案する ②AIが実装できるか判断して実装する ③リリースされると全員の卓に反映される。実装はAIですが、公開前にわたしが中身を確認しています。今入っている10種類も、公開前にわたし自身が提案して仕組みを通したものです。
```

```text
https://daifugo-together.fly.dev/
```

### 4-3. リプ・引用への反応方針

- **全部に返す**。「ありがとうございます!」だけでも良いので返す。リプが増えるとポストが動き続けます
- **ルール案がリプで飛んできたら最大のチャンス**。「それ面白いです、アプリの『ルールをていあんする』から出してもらえたらAIが実装します」と**必ず製品側へ誘導**する。ここを口頭で終わらせると、拡散が提案に変換されません
- 「うちの地元では〜」系のリプには、そのルールについて一言感想を返す。会話が続くほど良い
- **バグ報告には即お礼を言い、直したら報告する**。直した報告ポストはそれ自体が良いネタになります
- **「提案が何件も出せない」と言われたら**: 未登録だと同時に進行できる提案は1件までで、Googleでログインすると複数を同時に出せます、と案内する
- **「普通の提案なのにイエローカードが出た」という抗議が最優先案件**です。次の定型で返してください(§9も参照)
- 批判・辛口の引用リポストには、**反論せず事実だけを短く**返す(§9)。言い返した記録はずっと残るので、勝ち負けを競わない
- 伸びている引用リポストがあれば、それを自分が引用し直して補足するのは有効。ただし1〜2件まで

**イエローカード誤検知への定型リプ(コピペ用)**

```text
すみません、確認します。イエローカードの画面から「異議を送る」で申し立てができるので、そちらから送ってください。届いた内容を確認して、誤検出であれば取り消します(72時間以内を目安に見ています)。教えていただけて助かりました。
```

Xで反論を続けるより、**アプリ内の異議申し立てへ誘導して実際に取り消すほうが早く収まります**。手順は次のとおりです(§8と同じ `fly ssh console` → `cd /app` の中で実行)。

```bash
# 届いている異議を一覧する
DATABASE_PATH='/data/daifugo.sqlite' node packages/server/dist/ops.js list-appeals

# 誤検知だったカードを取り消す(--card は上の一覧のID、--note は理由メモ)
DATABASE_PATH='/data/daifugo.sqlite' node packages/server/dist/ops.js \
  revoke-card --card 12 --note '誤検出のため取り消し'
```

## 5. リリース後1週間の投稿カレンダー

このゲームは**放っておいてもネタが増える**という稀な性質があります(ルールが増える・変なルールが入る・却下される)。それを毎日の投稿に変換するのが基本設計です。数字の入る箇所は `【 】` で示したので、投稿前に実数に置き換えてください(卓数・ルール数・県数は `ops metrics`、提案件数は `ops funnel` で確認できます。§8)。

**投稿は1日1本を上限**にします。無風の日に2本出すよりは、翌日に回すほうが効きます。

### 8/2(土)夜 21時 — 初日の様子

```text
リリース初日の様子です。今日は【N】卓が遊ばれて、ルールの提案が【M】件届きました。届いた提案はこれから順に見ていきます。実装されたらまた報告します。

まだ遊べます(登録なし・空席はAIが埋めます)
```

## 7. ハッシュタグと検索対策

### 使うタグ(1ポストあたり最大2個)

| 場面 | タグ |
|---|---|
| リリース告知(案A/C) | `#個人開発` |
| リリース告知(案B・一般向け) | タグなし、または `#大富豪` |
| 技術記事の紹介 | `#個人開発` |
| 週次まとめ・進捗 | `#個人開発` |

置き場所は**本文の最後、URLの前後**。文中に混ぜると読みにくくなります。

### タグを付けすぎない理由

タグが3個以上並んだポストは「宣伝」と認識されて読み飛ばされやすく、本文の信頼を下げます。また日本語のXでは**本文中の単語そのものが検索対象**になるため、「大富豪」「ローカルルール」「8切り」「都落ち」といった語を自然に本文へ入れておけば、タグがなくても検索からは拾われます。表示アルゴリズムがタグをどう扱うかは公開情報が限られるため、**タグの有無で伸びが決まると考えないほうが安全**です。

### 検索対策として実際に効くこと

- プロフィールに「みんなでつくろう 大富豪」とURLを入れる(引用された人が飛んでこられる)
- ポスト本文にゲーム名を最低週1回は書く(名前で検索されたときに引っかかる)
- `大富豪 ローカルルール` `大富豪 8切り` などで検索して、盛り上がっている会話を見る。**押し売りはせず**、話題が合うときだけ自然に混ざる

## 8. 計測と成功の目安

### どこで見るか

**X側(見え方)**: ポスト下の「表示回数」タップ、または analytics.x.com。見るのは「表示回数(インプレッション)」「エンゲージメント」「リンククリック数」の3つだけで十分です。

**サーバー側(実プレイ)**: X上の数字は「見られたか」しか分かりません。実際に遊ばれたかはこちらで見ます。

```bash
# 本番(Fly.io)。DATABASE_PATH は必ずサーバーと同じパスを指定する。
# 別パスを指定すると空のSQLiteが作られて全部0に見えます。
fly ssh console
cd /app
DATABASE_PATH='/data/daifugo.sqlite' node packages/server/dist/ops.js metrics --since 2026-08-02
DATABASE_PATH='/data/daifugo.sqlite' node packages/server/dist/ops.js funnel  --since 2026-08-02
DATABASE_PATH='/data/daifugo.sqlite' node packages/server/dist/ops.js status --limit 100
```

役割分担は次のとおりです。**遊ばれた量とルール数は `metrics` にしかありません**(`funnel` は提案のステータスだけ)。

- `metrics`: 卓数・稼働ルール数・都道府県カバー数・セット評価
- `funnel`: 提案の投稿数と、却下・実装失敗・リリースの内訳
- `status`: 今どこで詰まっているか(審査待ち・実装待ちのキュー)

**カレンダーの穴に入れる数字とキーの対応**

| 使う場所 | 書く数字 | 取り方 |
|---|---|---|
| 8/2「今日は【N】卓」 | 遊ばれた卓(セット)数 | `metrics` の `completedSets` + `partialSets`。3戦やり切った卓だけ出したいなら `completedSets` のみ |
| 8/2「提案が【M】件」 | 届いた提案数 | `funnel` の `total` |
| 8/5 の発動判定 | 報告のある県数 | `metrics` の `prefectureCoverage`(3未満なら代替ポストへ) |
| 8/7「今【N】種類」 | 稼働中のルール数 | `metrics` の `rules.active` |
| 8/9「遊ばれた卓」 | 同上 | `metrics` の `completedSets` + `partialSets` |
| 8/9「届いた提案」 | 同上 | `funnel` の `total` |
| 8/9「実装されて入ったルール」 | 期間中にリリースされた数 | `metrics` の `rules.releasedDaily` を合計(累計が欲しいなら `rules.released`) |

`--since` は日付だけなら JST 00:00 として扱われます。時刻まで指定するときは `2026-08-02T12:00:00+09:00` のようにオフセットを必ず付けてください(実行PCのタイムゾーンに依存させないため)。

**毎日21時に1回だけ見る**と決めてください。何度も見ても数字は増えません。

### 現実的な数値感(過度な期待を防ぐため)

フォロワー数が数百規模の個人アカウントを想定した目安です。あくまで幅であり、保証ではありません。

| | 表示回数 | リンククリック | 実際に1卓遊ぶ人 | 提案 |
|---|---|---|---|---|
| よくある着地 | 500〜3,000 | 10〜60 | 5〜25人 | 0〜3件 |
| うまくいった | 5,000〜20,000 | 100〜400 | 40〜150人 | 5〜20件 |
| 跳ねた(運) | 50,000以上 | 1,000以上 | 数百人 | 数十件 |

換算の考え方: リンククリック率は表示回数の**1〜3%程度**、クリックした人のうち実際に遊ぶのは**2〜4割**、遊んだ人のうち提案するのは**1割前後**。つまり**表示回数1万で提案が数件**というのが自然な連鎖です。「提案が来ない」のはたいてい製品の失敗ではなく、単に**上流の人数が足りていない**だけです。

### 成功の目安

- **最低ライン(これで十分成功)**: 自分以外のメンバーだけで1卓成立する / 提案が1件でも来て、それが実装されて動く
- **良い**: 初週で提案10件、うち半分がリリースまで到達する / 8/9のまとめで書ける数字が揃う
- **すごい**: 1週間でルール数が倍になる / 誰かが自発的にプレイ動画やルール紹介を投稿する

**伸びなかった場合の解釈を先に決めておきます**。初日のインプレッションが1,000未満でも、それは製品の評価ではなく初速の問題です。本命は§6の技術記事で、そこが読まれれば1週間後に流入が来ます。**初日の数字で製品の良し悪しを判断しない**でください。

## 9. 注意事項

### 「AIが実装」への反発に備える

「AIの書いたコードを本番に入れるなんて」「品質は?」「セキュリティは?」という反応は**必ず来ます。そしてそれは正当な疑問です**。事前に答えを用意しておき、来たら短く事実で返します。

> 実装はAIですが、生成されたコードは自動テストと静的な制約チェックを通り、PR経由でデプロイされます。公開前にわたし自身が中身を確認していて、問題があれば戻せるようにしてあります。

**やってはいけないのは、「完全自動」「人は一切介在しない」と煽ること**です。実際には公開前に開発者が確認する運用なので、そう書けば嘘になりますし、後から「実は人が見ている」と分かるほうがダメージが大きい。逆に**「人が確認している」と最初から書くほうが、この界隈では評価されます**。

「AIが仕事を奪う」系の一般論に話が広がったら、そこには乗らず製品の説明に留めてください。議論の勝ち負けはこの告知の目的ではありません。

**設計上のトレードオフを自覚しておいてください**: 「公開前に人が確認している」「今の10種類は自分が提案したもの」という但し書きは、本文ではなくリプツリー(§4-2)に置いてあります。本文を140字に収めて訴求を鈍らせないための判断ですが、**引用リポストで広がるときに読まれるのは本文だけ**で、ツリーは追われません。したがって「全自動でユーザー提案が次々入っている」という誤解が一人歩きする可能性は残ります。誤解した引用を見かけたら、**その引用に直接リプライして訂正**してください(ツリーを増やしても届きません)。

### イエローカードの誤検知が、いちばん現実的な炎上経路

「普通のルールを提案しただけなのにイエローカードが出た」という抗議は、AI論争より確率が高く、しかも**相手に完全に正当性がある**ケースです。備えは3つ。

- **アプリに異議申し立てがある**ことを知っておく(イエローカードの画面から「異議を送る」。72時間以内を目安に確認すると画面に書いてあります)
- Xでは弁明せず、**§4-3の定型リプで異議申し立てへ誘導する**。「検出精度は完璧ではありません、すみません」と先に認めてよい
- 届いた異議は `list-appeals` で確認し、誤検知なら `revoke-card` で取り消す。**取り消したことを本人に伝える**。ここまでやると、抗議した人がむしろ味方になります

イエローカードをネタにする8/6のポスト(§5)は、この問い合わせを増やす方向に働きます。**対応する余裕がない日には出さない**でください。

### 子供も遊ぶゲームであることのトーン配慮

- 本アカウントで下ネタ・攻撃的な煽り・過度な内輪ノリを出さない。**このアカウントは家庭用ゲームの公式窓口だと思って運用**してください(桃太郎電鉄の公式が言わないことは言わない、が分かりやすい基準)
- **他人の提案文をスクショで公開するときは、必ず全文を読んでから**。不適切な内容や個人情報が混ざる可能性があります。提案者の表示名は写さない
- 都道府県は「その人がそこで遊んでいたという報告」であって「その県のルール」ではありません。断定した書き方をしない
- 「ルールを提案するとAIが実装する」という説明は、子供にも分かる言葉で書く(「パイプライン」「LLM」などは大人向けポストだけで使う)

### 誇大表現の禁止

「日本初」「世界初」「完全自動」「業界を変える」は使わない。検証できませんし、**事実をそのまま書くだけで十分珍しい製品**です。数字は必ず `ops metrics` / `ops funnel` の実数で出し、盛らない。盛った数字は1週間後のまとめポストで辻褄が合わなくなります。

### 運用上の地雷

- **告知直後にデプロイしない**。ルールPRのマージ後にデプロイが走ると再起動が起き、プレイ中の卓に影響します。初日〜週末はマージを止め、平日の人の少ない時間帯に回す
- **落ちたら隠さない**。「今エラーが出ていて直しています」と1本出すほうが、黙って直すより印象が良く、直った報告もネタになります
- 初動でアクセスが集中したら `fly logs` を見る。Fly.ioの単一プロセス構成なので、**負荷の兆候は早めに把握しておく**
- リプ返しで疲れないこと。1週間続ける体力配分のほうが、初日に全力を出すより効きます
