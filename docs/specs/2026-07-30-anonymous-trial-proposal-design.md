# 設計: 匿名おためし提案枠(AU-D4 の緩和)

- 作成日: 2026-07-30
- 状態: 設計承認済み(2026-07-30 開発者との検討セッション)。実装計画は未着手
- 一次情報源: `docs/epics/E15-auth-account.md`(§1.2 AU-D4・§2.6・§2.7)/ `docs/epics/E05-rule-proposal.md`(§2.1・§3.1)/ `docs/epics/E06-injection-yellowcard.md`(§3.3(b) の旧決定)
- 関連決定: decision-log G-14(提案ログイン必須)を本設計で緩和する

## 1. 背景と目的

E15(AU-D4)でルール提案を Google ログイン必須にした。狙いはイエローカード停止の「匿名作り直しで回避」を入口で防ぐことである。しかし、主要な想定利用者である子供の大半は Google アカウントを持たない。子供だけの卓(近くに登録済みの大人がいない状況)では、コア体験である「自分の提案でゲームが変わる」(企画書 §2.2)に一切触れられなくなり、継続率を下げる要因になる。

そこで、**匿名ユーザーにも「同時進行 1 件」の提案枠**を与える。提案は本物のパイプライン(E6 検査 → E7 可否判断・実装 → 全卓反映)に乗り、手応えは登録済みユーザーと同じ本物である。登録の意味は「提案のゲート」から「特典(無制限提案・別端末引き継ぎ・E19 実績・E16/E17 通知)」へ移す。

E06 §3.3(b) の元決定は「初期は匿名で受付、回避常態化(週 3 件)でログイン必須へ移行」だった。本設計はその思想に「同時 1 件」という安全弁を足して戻すものであり、悪用が観測されたら AU-D4(全面必須)へ巻き戻せる構造を保つ(§4)。

## 2. サーバー: 投稿 API ゲートの変更

E15 §2.6 の「登録確認(403 `registration_required`)」を「枠確認」に置き換える。

1. **認証**(Bearer 有効): 無ければ 401 — 変更なし
2. **枠確認(置き換え)**: 未登録(`users.google_sub IS NULL`)の場合のみ、本人の**進行中**提案が既に 1 件以上あれば **403 `{ error: 'anonymous_inflight_limit' }`**。登録済みは無条件通過
3. 停止確認(403)→ 検証(400)→ 重複確認 → 同期保存 — 変更なし

**「進行中」の定義**は既存の部分ユニークインデックス `idx_proposals_inflight_dedupe`(E05 §2.1)と同じ述語を使う:

```
status IN ('screening','implementing')
OR (status = 'failed' AND attempt_count = 0)
```

- 新しい「進行中」概念を作らない。リトライ待ちの失敗提案が枠を占有する挙動も、重複抑止の「自動リトライが再提案に優先」(E05 §2.3)と自然に一貫する。
- 終端(リリース / 却下 / リトライ枠切れの失敗)で枠が空き、次の提案を出せる。回数制限・期間制限は設けない(子供の体験を止めない)。
- イエローカード・提案停止(E06)は全件変更なし。停止中は枠が空いていても提案不可(ゲート順のとおり枠確認 → 停止確認だが、どちらも 403 で意味が異なるため `error` 値で判別する)。

## 3. クライアント: 提案画面・登録導線

文言はすべて仮。実装時に `docs/design/UI文言・情報量ガイド.md` に従い最終化する。

| 場面 | 挙動 |

| 提案画面(未登録・枠あり) | **フォームを表示する**(E15 §2.7 の「未登録はフォーム非表示+ログイン誘導」分岐を撤回)。脇に控えめな説明「とうろくしなくても 1 つずつ ていあんできるよ」 |
| 提案画面(未登録・枠埋まり) | フォームの代わりに、進行中の提案の現在状態+「けっかが出たら つぎの ていあんが できるよ。Google とうろくすると いくつでも ていあんできるよ」+ログイン導線 |

## 4. 安全弁と巻き戻しトリガー

- E06 のインジェクション検査・イエローカード・提案停止は全件そのまま適用される。
- 匿名作り直しの攻撃価値: 新しい匿名 ID を作っても得られるのは「同時 1 件」の枠だけであり、攻撃スループットは上がらない。停止回避も同様に同時 1 件に制限される。
- **巻き戻しトリガー**: 停止回避目的の匿名作り直しが常態化(目安: 週 3 件。E06 §3.3(b) の元トリガーを踏襲)したら、枠確認を AU-D4 の登録確認(403 `registration_required`)へ戻す。ゲート 1 箇所とクライアントの未登録分岐の変更で巻き戻せる構造を維持する。

## 6. テスト

- 未登録+進行中 0 件 → 受理 / 進行中 1 件 → 403 `anonymous_inflight_limit` / 終端確定後 → 再び受理
- 進行中の境界: `failed AND attempt_count=0`(リトライ待ち)は枠を占有し、`attempt_count=1`(枠切れ)は占有しない
- 登録済みユーザーは進行中複数でも通る(E15 で登録済み前提に書き換えた既存テストの維持)
- 停止中は枠が空いていても 403(停止)。ゲート順序: 401 → 枠 403 → 停止 403 → 400 の順で先行ゲートが勝つ
- クライアント: 未登録でフォーム表示・枠埋まり分岐・403 フォールバック・登録導線の文言変更

## 7. スコープ外

- 卓ローカルの「ルールメーカー」(Effect 語彙のパラメタライズ+卓ごとの即時有効化): 将来の Epic 候補として別途検討。本設計では扱わない
- 匿名提案の優先度を下げる・別キューにする等の区別: 設けない(YAGNI。悪用が観測されたら §4 の巻き戻しで対処)
- レート制限の復活: しない(E-18 の決定を維持)
