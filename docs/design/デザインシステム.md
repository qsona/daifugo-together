## 2. React への持ち込み方

### 2.1 トークン

- `design-tokens.css` をそのままアプリのエントリ(例: `src/index.css` の先頭)で import する。トークンはすべて `:root` の CSS カスタムプロパティなので、CSS Modules・Tailwind(`var()` 参照)・styled-components のいずれからも `var(--color-text-primary)` の形で使える。
- 値のコピー(コンポーネント内に `#1C2447` を直書きするなど)は禁止。**hex を書いてよいのは design-tokens.css / design-tokens.json の 2 ファイルだけ**。
- TypeScript から値が必要な場合(Canvas 描画・チャートなど)は `design-tokens.json` を import して参照する。JSON の `ref` はプリミティブへの参照なので、解決ユーティリティを 1 つ用意して使い回す。
- フォントは Web フォント「M PLUS Rounded 1c」(weight 400/700/800)の読み込みを推奨(Google Fonts またはセルフホスト)。読み込み前・失敗時は Hiragino Maru Gothic ProN 以降のフォールバックで成立する設計にしてある。

### 2.2 コンポーネント

- React コンポーネント名は PascalCase(`Button`, `RuleCard`, `ProposalStepper`)。design-system.html の `c-*` クラスは見本実装であり、React 側では各コンポーネントの内部実装として自由に書き直してよい。ただし**見た目の仕様(色・形・状態)は design-system.html の見本を正とする**。
- バリアントは props で表現する(例: `<Button variant="primary" size="small">`)。CSS クラス直書きの `-primary` 修飾は見本上の表記。
- 新しい画面を作るときは、まず design-system.html の部品で組めないか確認する。組めない場合のみ部品を追加する(§5)。

### 2.3 codex(自動実装 AI)への指示に含める規約

フェーズ 2 以降、codex が UI を触る可能性がある。リポジトリの実装規約(CLAUDE.md 等)に次の 3 行を含めること。

1. 色・余白・角丸・影・時間は必ず `design-tokens.css` のカスタムプロパティを参照する(hex・px の直書き禁止)。
2. UI 文言に分かち書きの全角スペースを入れない。都道府県は「報告: ◯◯県」「◯◯県で遊ばれていた報告」「◯◯発」の形で書き、「◯◯県のルール」と断定しない。
3. 新規部品は docs/design/design-system.html に見本を追加してから使う。
4. 画面に説明文を置く前に [UI文言・情報量ガイド.md](./UI文言・情報量ガイド.md) の削除テストを通す。仕組みの説明は画面に書かず、あそびかた・ルール図鑑に置く。

## 3. 命名規約

### 3.1 トークン

```
--{カテゴリ}-{名前}[-{段階}]
  color-blue-500        プリミティブ: 色相 + 明度段階(数字が小さいほど明るい)
  color-text-primary    セマンティック: 用途ベース(bg-/text-/border-/action-/status- など)
  font-size-title-m     タイポ: 役割ベース
  space-4               余白: 4px グリッドの倍数インデックス(space-4 = 16px)
  radius-m / border-bold / shadow-hard-m / duration-base / easing-pop
```

- コンポーネントの CSS からは**原則セマンティックトークンを参照**する。プリミティブ直参照は、意味割り当てが存在しない装飾(ガーランドの旗色など)に限る。
- JSON はキー階層をハイフンでつなぐと CSS 変数名になる(`color.primitive.navy-800` → `--color-navy-800`。semantic も同様に `color.semantic.bg-app` → `--color-bg-app`)。

### 3.2 色の意味割り当て(企画固有)

| 色 | 意味 | 由来 |
|---|---|---|
| 紺 navy-800 | 文字・輪郭。全部品共通のアウトライン | KV の全要素共通の輪郭線 |
| クリーム cream-100 | アプリの地。「真っ白の代わりの温かい明色」 | KV ロゴ縁・タップ導線面 |
| 赤 red-600/500 | 主アクション(600)・ブランド装飾(500)・危険 | ロゴ「大」・コピーリボン |
| 金 gold-400 | 祝祭(人気度・NEW)+ イエローカード(審判の文脈のみ警告) | ロゴ「富」・イエローカード・NEW RULE 面 |
| 緑 green-500/700 | ローカルルール・成功 | ロゴ「豪」・丘・LOCAL RULE 面 |
| 青 blue-500 | 情報・リンク・フォーカス | 深い青空 |

**イエローカードの黄のルール**(「怒られてるのに笑える」を守るため):

- 黄で塗ってよいのは「カードの絵」「警告スロット」「ステッパーの進行中」だけ。**画面や面全体を黄で塗らない**(警報にしない)。
- イエローカードの文言は「審判より:」で始め、罰の内容と一緒に「対戦はそのまま遊べます」の救いを必ず同じ画面に置く。
- 黄面の文字は必ず navy-800(コントラスト 9.55)。黄面に赤文字を置かない。
- 祝祭用途(人気度バー・NEW タグ)と警告用途が同居する画面では、警告側に必ず審判のモチーフ(カードの絵・笛・「審判より」)を添えて文脈で区別する。

### 3.3 都道府県の非断定表現(コンポーネント仕様)

企画書 §4.1 の決定「都道府県は提案者の出自の記録であり、分布実態の断定をしない」を部品仕様に焼き込む。

- タグ: 「報告: ◯◯県」固定(`RulePrefTag` は接頭辞「報告: 」をコンポーネント側で付与し、呼び出し側に文言を組ませない)。
- 説明文: 「◯◯県で遊ばれていた報告」/ 絵の中の短い表記: 「◯◯発」。
- 禁止: 「◯◯県のルール」「◯◯県発祥」などの断定形。フィルタ UI のラベルも「都道府県」とし「産地」等の語を使わない。

## 4. トーン判定の Do / Don't

基準: 全年齢ポップ(桃太郎電鉄水準)。子供がメインターゲットだが、大人が手に取っても子供向けすぎると感じない造形(企画書 §2.3・§6)。

| | Do | Don't |
|---|---|---|
| 造形 | 太い紺輪郭+フラット面塗り+ベタ落ち影。直立の構造的タイポ | グラデーション・光沢・ぼかし影の多用。文字の傾き(傾けてよいのはリボン・札・スタンプ等の少数の脇役だけ) |
| 色 | 深い青空・生成りクリームなど値の締まった地色に高彩度アクセント | パステル地・蛍光色。1 画面に赤金緑青の全アクセントを同格で並べること |
| キャラクター | 眉のある芝居顔(ニヤリ・きりり)。モチーフ(トランプ・旗・切符)と色でにぎやかす | 頬丸+点目のゆるかわ顔。**静的 UI にキャラクターの吹き出し発言を置く**(発言はゲーム内演出の領分) |
| 文言 | 「タップしてはじめる」のように詰める。ひらがな多めでも語彙は大人にも自然に | 分かち書きの全角スペース(「タップして はじめる」)。幼児語(「〜でちゅ」等)、過剰な「!」の連打 |
| 演出 | 登場時に 1 回だけ弾む(easing-pop)。イエローカードは審判の小道具として笑いに | 常時ループのアニメーション。警報的な点滅・全画面の黄・赤 |
| 情報密度 | 1 画面 1 主役(主 CTA は 1 個)。整列・枠・帯の規律 | 紙吹雪や飾りで本文を圧迫する(飾りは空きスペースにだけ) |

迷ったら: 「桃太郎電鉄の画面に混ざって浮かないか」「大人が電車内で開いて恥ずかしくないか」の 2 問で判定する。

## 5. 部品追加のガイドライン

1. **既存部品の変種で表現できないかをまず検討**(例: 新しいバッジはタグの色変種で足りないか)。
2. 追加する場合、design-system.html に「全状態(通常・押下・フォーカス・無効・エラーのうち該当するもの)」の見本を追加し、使用するトークンだけで組む。新しい hex・px が必要になったら、それはトークンの追加提案として design-tokens.css/json を先に更新する。
3. タップ対象は最小 44px(見た目が小さい部品は余白で当たり判定を確保)。テキスト/背景は AA(4.5:1)を満たす組み合わせだけを使う。満たせない装飾色は「装飾限定」と明記する。
4. 都道府県・イエローカード・評価に関わる部品は §3.2/§3.3 の意味ルールに適合するか確認する。
5. 本書 §4 の Do/Don't で自己レビューしてから採用する。

## 6. アクセシビリティ仕様

- **コントラスト**: 本文テキストは WCAG AA(4.5:1)目標。実測値は §8 の表(全て計算済み)。装飾限定色(red-500 上の明色文字、green-500 上のクリーム文字)は本文に使わない。
- **タップターゲット**: 最小 44×44px(`--size-tap-min`)。small ボタン(見た目 36px)は周囲の余白を含めて 44px を確保する。
- **フォーカス可視**: すべての操作可能要素に `outline: 3px solid var(--color-focus-ring); outline-offset: 2px`(blue-500、地とのコントラスト 4.63)。フォーカスリングを消すスタイルは書かない。
- **色だけに頼らない**: 高評価/低評価は選択で文言を「〜済み」に変える。ステッパーは色+文言に加えて、現在地を寸法(太枠・1段大きい文字・影)と「いま」の語で示し、通過済みには✓を付ける。人気度バーは数値ラベルを必ず併記する。
- **モーション**: `prefers-reduced-motion: reduce` では transform 系の演出を fade に落とす。

## 7. ダークテーマ(将来課題)

2A は「昼の祝祭」の世界観のため、**当面ライトテーマのみ**とする。将来ダーク対応する場合はキービジュアル案 2C「ナイトグランプリ」のパレット(夜紺地 #17204A〜#0D1330・金・マゼンタ・ミント)が出発点になるが、セマンティックトークンの再割り当て(bg/text/border 系の反転と AA 再計算)が必要で、単純な明度反転では成立しない。トークンがセマンティック層で分離してあるため、対応時は `:root[data-theme="dark"]` に semantic 層だけを再定義する方式を想定する。
