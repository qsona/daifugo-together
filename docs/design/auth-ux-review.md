### この突き合わせで見えた構造的な発見(一覧には無いもの)

**1. Push は「登録ゼロで遊べる」(E15 §1.1)と衝突する最初の機能である。**

サーバーは購読・通知種別の設定すべてに **Google 登録済み(`google_sub` が非 NULL)を要求する**(`packages/server/src/push/service.ts:118-137` の `#registeredUser` → `push/repository.ts:24-28` の `isRegistered`)。匿名は **403 `registration_required`**。例外は `markInstalled` だけで、これは意図的な設計である(`service.ts:124-128` のコメント: 「追加したが登録していない」層こそ観測したい)。

つまり認証は、これまでの「あってもなくてもよいもの(記録が引き継げるだけ)」から、**「これが無いと使えない機能があるもの」**に変わった。§4.1 が指摘した「アカウントという概念の置き場が存在しない」ことの重みは、この変化のぶんだけ増している — 置き場がないので、**「なぜ使えないのか」を説明する場所も無い**。

**2. iOS では A2HS が Push の前提条件を壊す(三重の交差)。**

通知を受け取るには (a) 登録済み (b) iOS ならホーム画面に追加済み (c) OS の通知許可、の 3 つが要る。ところが **(b) を満たすと (a) が失われる** — ホーム画面アプリはブラウザとストレージを共有せず `userToken` を引き継がないため、未登録の新しいゲストとして立ち上がる(`InstallGuide.tsx:119-121` が自ら「追加したあとは、もう一度Googleでログインしてください」と書いている)。

したがって iOS の素直な経路は次のようになる。

```
通知設定を開く → 「iPhone・iPadではホーム画面に追加したアプリだけが通知を受け取れます」
  → 追加する → ホーム画面アプリを開く(未登録の新ゲストになっている)
  → 通知設定を開く → 購読ボタンを押す → OS 許可を与える → 403 registration_required
  → 「通知を設定できませんでした。」          ← 何が足りないのか一言も出ない
```

**N-8(A2HS 案内から認証を始められるようにする)は、単なる利便性ではなくこの経路の必須要件**である。優先度を上げて work order へ渡すこと。

### J9-1 未登録でも購読ボタンを押せて、OS 許可を与えたあとに 403 で落ちる — **Critical / 817409b で解消済み**

**影響**: ユーザーは OS の通知許可という**取り消しにくい資源**を与えたうえで失敗する。しかも許可を一度拒否すると回復手段が案内されない(J9-7)ため、**「試して失敗する」の代償が不可逆になりうる**。

### J9-2 OS 許可の要求が経路の最初にあり、成功しないと分かっている場合でも消費される — **Important / 817409b で解消済み(不変条件つき)**

**根拠**: `subscribeProposalResults`(`push/client.ts:83-112`)の順序は **`requestPermission`(`:90`)→ `config()`(`:92`)→ `pushManager.subscribe`(`:99`)→ `POST /api/push/subscriptions`(`:103`)**。したがって未登録(403)でも VAPID 未設定(503 `push_unavailable`)でも、**OS 許可だけは先に取られる**。

**この順序は事故ではなく制約である**。`:88-89` のコメントが「WebKit を含むブラウザの user activation を失わないよう、クリックから最初の非同期処理として許諾を要求する」と明記しており、**サーバー往復を許可の前に挟むと user activation が切れて許可ダイアログ自体が出せなくなる**。つまり「登録済みか確認してから許可を求める」を素直に実装することはできない。

### J9-4 端末の通知状態が読まれておらず、「受け取る」と「止める」が常に両方出る — **Important**

**根拠**: `PushSettingsScreen` は `Notification.permission` も `registration.pushManager.getSubscription()` も参照しない。「この端末で通知を受け取る」は `available && !installRequired`(`:122`)で出て、「この端末への通知を止める」(`:144-154`)は**条件なしで常に出る**。したがって次がすべて起きる。

- 一度も購読していない端末に「止める」が出る(押しても `disableThisDevice` は購読が無ければ黙って何もしない。`push/client.ts:150-151`)
- 購読済みの端末に「受け取る」が出る(押すと既存購読を使い回すので実害はないが、状態が読めない)
- **OS 許可を拒否済みの端末にも「受け取る」が出る**(押すと必ず `denied` に落ちる。`push/client.ts:91`)

> **2026-08-02 追記 — 817409b の影響: 範囲は狭まったが指摘は残存。**

### J9-5 購読と解除がブラウザとサーバーの**両方向**にずれる — **Important**

**根拠**: 一覧は購読側だけを挙げていたが、実コードでは**逆方向にもずれる**。

| 操作 | 順序 | 途中で失敗すると |
|---|---|---|
| 購読(`push/client.ts:96-107`) | `pushManager.subscribe()`(:99)→ `POST /api/push/subscriptions`(:103) | POST が投げても**ブラウザ側の購読は解除されない**。端末は購読済みなのにサーバーは知らない状態が残る |
| 解除(`push/client.ts:146-161`) | `DELETE /api/push/subscriptions`(:153)→ **`finally`** で `current.unsubscribe()`(:159) | DELETE が失敗しても `finally` でローカルは必ず解除される。**サーバーに死んだ endpoint が残る**(送信すると 404/410 になる) |

**影響**: 購読側のずれは「設定したのに届かない」、解除側のずれは「止めたのに送信を試み続ける」。どちらも**画面上は成功にも失敗にも見えない**(J9-3 のとおり文言が潰れているため)。

なお `disableThisDevice` の `finally` は**サインアウト経路でも走る**(`App.tsx:1717-1726`)ので、サインアウトのたびにサーバー側に死んだ購読が積む可能性がある。

**改善方向**: 購読側は POST 失敗時に `unsubscribe()` して巻き戻すか、「登録を再試行」を出す。解除側は DELETE の失敗を握りつぶさず、ローカル解除は行ったうえで**サーバー側の取り残しを次回起動時に再試行**する。**サーバー変更は不要**(冪等な upsert / revoke は既にある。`push/repository.ts`)。

### J9-6 「種別の設定」と「この端末の購読」の射程の違いが説明されていない — **Minor / 817409b で論点ごと消滅**

### 1.3 判定の基準

指摘は 3 段階に分ける。

- **Critical** — ユーザーがデータ・対局・操作機会を失う、または仕様上できるはずのことができない
- **Important** — 目的は達成できるが、理解・信頼・トーンを損なう
- **Minor** — 一貫性・仕上げの問題

また、UI 文言ガイドとの関係を 2 種類に区別して書く。

- **(違反)** — ガイドが明示的に禁じていることをしている
- **(不足)** — ガイドに従って文を削った結果、代わりの手段(状態・形・部品)が用意されていない

### 2.1 初見の匿名ユーザーがメニューに来る

#### J1-1 自分が誰なのか、登録済みかどうかが画面のどこにも出ない — **Critical**(不足)

**根拠**: `MenuScreen.tsx:7-18` の props に表示名がない。表示名はクライアント状態として既に存在する(`packages/web/src/multiplayer/client.ts:20,65` の `displayName`)が、メニューへ渡していない(`App.tsx:1383-1400`)。アカウント状態を語る唯一の要素は小ボタンのラベル `MenuScreen.tsx:68` の「登録済み・ログアウト」/「引き継ぎ・ログイン」だけである。画面一覧(`packages/web/src/screens/`)にアカウント画面は存在しない。

**影響**: 「引き継ぎ」という機能は「**この記録は自分のものだ**」という感覚を前提に成立する。その感覚を支える表示(表示名・登録済みバッジ)が 1 つもないため、ボタンだけを見た人には何を引き継ぐのかが分からない。別端末でログインした直後も、切り替わったのかどうかを確認する手段がない(E15 §2.4 ケース 2 は「表示名・記録が切り替わる」ことが受け入れ条件だが、画面上でそれを見る場所がない)。

これはガイド違反ではなく**不足**である。ガイド原則 3 は「文を書く前に状態で伝えろ」と言っているが、その「状態で伝える」表示自体が作られていない。

**改善方向**: メニュー上部に、表示名と登録状態を兼ねた 1 つの**アカウント行**(タップで詳細へ)を置く。文ではなく、名前+バッジ(未登録/引き継ぎ済み)の形で示す。

#### J1-2 認証の入口が 3 か所に分散し、すべて「小ボタン」で同格 — **Important**

**根拠**: 入口は (a) メニュー最下段の小ボタン `MenuScreen.tsx:62-70`、(b) リザルトの小ボタン `SetResultScreen.tsx:134-138`、(c) 提案画面の枠占有パネル内 `ProposalFormScreen.tsx:232-235` の 3 つ。(a) は `screen.body`(`screens/screen.module.css:13-25`、`align-items` 既定=stretch)の直下にあるため、`screen.row` に入った「マイ提案」(`MenuScreen.tsx:52-61`)と同じ全幅の小ボタンとして縦に並ぶ。

**影響**: 「マイ提案(コンテンツへの導線)」と「引き継ぎ・ログイン(アカウント操作)」が同じ重み・同じ形で並ぶため、種類の違う操作が 1 つの列に混ざる。デザインシステム §4「情報密度」の「1 画面 1 主役」は守られているが、脇役どうしの階層が付いていない。

**改善方向**: アカウント操作はナビゲーションの列から抜き、J1-1 のアカウント行に集約する。

### 2.3 登録誘導(セットリザルト)

#### J3-1 リザルトの登録誘導が、対局中のフルページ遷移を引き起こす — **Critical**

**根拠**: 誘導が出るのは `room?.phase === 'setResult'` のとき(`App.tsx:955-966`)、つまり**部屋の中**である。押すと `beginLogin`(`App.tsx:660-682`)→ `auth/client.ts:29-47` の隠しフォーム POST でページごと Google へ遷移する。E15 §2.3 は「部屋がプロセス内メモリである以上、OAuth のフルページ遷移でクライアント状態は失われる。**対局中はログイン導線を出さない**ことで運用上回避する」と書いており、§2.7 のリザルト導線はこの制約と正面から衝突している。

さらに悪いのは、この誘導が出る条件が `!state.registered`(`App.tsx:956`)であるため、outcome は `linked`(自分の行に紐付け)か `switched`(その Google アカウントが既に別の行で登録済み)のどちらかになる点である。**`switched` の場合は別ユーザーとして再接続する**(`App.tsx:990` の `client.switchSession`)ので、同席していた対局から黙って消える。「別端末で登録済みの人が、この端末で匿名で遊んで、リザルトで『きろくをのこす』を押す」は珍しい経路ではない。

**影響**: 一緒に遊んでいた人の卓から突然いなくなる。押した本人にも、何が起きたのかを説明する画面がない。

**改善方向**: リザルト時点では**誘導だけを予約**し、実際の OAuth 遷移は部屋を出たあと(メニュー到達後)に行う。あるいはリザルト導線を廃止し、退室直後のメニューで一度だけ出す。いずれにせよ「押した瞬間に外部サイトへ飛ぶ」は対局中に置けない。

#### J3-2 成功しても、成功したことがどこにも出ない — **Critical**

**根拠**: 完了ハンドラは結果を `authMessage` に入れる(`App.tsx:991-993`)が、`authMessage` を描画しているのは `MenuScreen` だけである(`App.tsx:1398` が唯一の受け渡し、`MenuScreen.tsx:71` が唯一の描画)。完了ハンドラは `go('menu')`(`App.tsx:976`)を呼ぶが、部屋が生きていれば部屋の画面が先に return される(`App.tsx:1090` 以降)ため、`linked` で部屋に戻った人はメッセージを一度も見ない。

**影響**: 引き継ぎ登録という「二度と繰り返さない、成功したか確かめたい操作」に対して、成功の合図がゼロになる経路がある。

**改善方向**: 認証結果はルート直下の通知として表示し、どの画面にいても見えるようにする。成功系は `Toast`(`packages/web/src/components/Toast.tsx`。E15 §2.7・design-system.html §5-13 の用例と整合)。失敗系の部品は §4.2 の正典衝突があるため Q-5 の裁定に従う。

#### J3-3 「きろくをのこす」を押すと、予告なく Google の画面に飛ぶ — **Critical**

**根拠**: `SetResultScreen.tsx:136` のラベルは「きろくをのこす」のみ。押下 → `beginLogin` → 即フォーム POST → Google(`auth/client.ts:29-47`)。間に確認も説明もない。メニューの「引き継ぎ・ログイン」(`MenuScreen.tsx:68`)も同じである。

**影響**: 子どもも遊ぶプロダクトで、ラベルから予測できない外部サイト(Google アカウント選択画面)へ全画面遷移する。何を求められているのか分からないまま個人アカウントの選択を迫られる。

これは**ガイド違反ではない**。ガイド原則 1(`UI文言・情報量ガイド.md:40`)は「どうしても要るなら操作対象の下流に置くか、**要求されたときだけ出す**」と述べ、§3 判断 3「位置テスト」(同 93 行)も下流であれば残してよいとしている。現状は「説明を消した」のではなく「置く場所を作らずに消えている」状態である。

**改善方向**: 押下と外部遷移の間に、目的(記録の引き継ぎ)・取るもの(Google のアカウント ID だけ。メールも名前も取らない = AU-D5)・所要(戻ってくること)を 1〜2 行で示す軽い確認を挟む。ここは `Dialog`(`packages/web/src/components/Dialog.tsx`)の出番である。

#### J3-4 リザルト誘導は端末で永久に 1 回きり、しかも見られなくても消費される — **Important**

**根拠**: `App.tsx:86` の `AUTH_RESULT_PROMPT_KEY` は部屋・セットに依存しないグローバルなキーで、`App.tsx:960-966` は「まだ出していなければフラグを立てて出す」。フラグは**表示の直前に書かれる**ため、リザルトを一瞬で抜けても消費される。以後この端末で二度と出ない。

E15 §2.7 の「毎回は出さず、初回リザルト+以降は抑制(頻度はプロセス 1 で仮決めし記録)」および AU-T2(表示頻度の裁定は未決)に対して、実装は最も強い抑制(生涯 1 回)を採っている。

**影響**: 誘導は「まだ登録の価値が分かっていない初回」に 1 度だけ出て、価値が分かる頃(何セットも遊んで記録が貯まった頃)には二度と出ない。抑制の方向が体験と逆になっている。

**改善方向**: 頻度は「N セットごと」または「提案・記録が一定量たまったとき」に変え、AU-T2 をここで裁定する。表示済みフラグは実際に画面に出た時点で立てる。

### 2.4 登録する(OAuth 往復)

#### J4-1 認証が失敗すると、白い画面に JSON が出て戻れなくなる — **Critical**

**根拠**: クライアントは E15 §2.3 が定める `POST /api/auth/begin` → `{ authUrl }` → `location.href` という経路を使っていない。代わりに隠しフォームでブラウザごと `/auth/google/begin` へ POST している(`auth/client.ts:29-47`)。サーバー側は成功時のみ 303 リダイレクトを返し(`app-server.ts:275-281`)、それ以外は JSON を書く(`app-server.ts:282`)。したがって OAuth 未設定環境(503 `auth_unavailable`、`app-server.ts:260-263`)やトークン無効(401)では、**ブラウザに `{"error":"auth_unavailable"}` が生のまま表示される**。

E15 §2.8 は「begin が 503 → 『いまは使えないみたい』トースト」と定めており、実装はこれを満たしていない。`beginLogin` の `try/catch`(`App.tsx:676-681`)はフォーム送信が同期的に投げた場合しか拾えないので、この経路では働かない。

**影響**: アプリから出たきり戻れない。子どもが英数字の JSON に取り残される。

**改善方向**: 仕様どおり `POST /api/auth/begin` を fetch で叩き、`authUrl` を受けてから `location.href` に入れる。エラーはアプリ内に留める(具体的な部品は §4.2 の正典衝突があるため Q-5 の裁定に従う)。サーバー仕様の変更は不要(エンドポイントは既に存在する)。

#### J4-2 完了時のフィードバックが裸の `<p>` — **Important**(不足)

**根拠**: `MenuScreen.tsx:71` は `{authMessage && <p role="status">{authMessage}</p>}`。`MenuScreen.module.css` には対応するクラスが 1 つもない(定義は `.badge` のみ)ため、ブラウザ既定の余白・書体で表示される。`packages/web/src/components/Toast.tsx` は存在し、`GameScreen.tsx:153-160` で使われている。E15 §2.7 も「トースト」と明記している。

これを UI 文言ガイド §3 判断 4 の**部品テスト**(「画面に生の段落を置いていないか」)の違反とするのは正確ではない。部品テストが対象にしているのは**説明文**の置き場であり、`MenuScreen.tsx:71` は `role="status"` のライブリージョン通知である(`Toast.tsx:19` を見れば分かるとおり、`Toast` 自身の実体も `<p role="status">` である)。したがってこれは説明文の置き場違反ではなく、**design-system.html §5-13(1211-1219 行)が定めるトースト部品を使っていない**という不足である。造形(紺面+明色文字+soft 影・画面下部に 1 件)も退場も、既定の見た目もないまま素の段落が出ている。

**改善方向**: `Toast` を使う。設置場所はメニュー内ではなくアプリのルート(J3-2 と同じ理由)。ただし**失敗系をトーストにしてよいかは未決**である(§4.2・Q-5)。

#### J4-3 メッセージが消えない — **Important**

**根拠**: `authMessage` を `null` に戻すのは `beginLogin` の開始時(`App.tsx:675`)だけ。ログアウト後の「ログアウトしました」(`App.tsx:1395`)はメニューに貼り付いたまま残り続ける。

**影響**: 「いま起きたこと」を伝えるはずの文が、いつ起きたか分からない常設テキストに変質する。ガイド原則 3 の「状態で伝える」という発想とも噛み合っていない(状態表示なら文でなくバッジであるべきで、通知なら消えるべきなのに、どちらでもない)。

**改善方向**: 通知には寿命を持たせる(design-system.html §5-13 は「3 秒で退場」。ただし現行の `Toast` にタイマーはない — §5.1 N-4 の補足 2)。状態(登録済みかどうか)は J1-1 のアカウント行が常時受け持つ。

#### J4-4 失敗の文言が 3 種類の原因に対して 1 つ — **Minor**

**根拠**: `App.tsx:978`(callback の `error`)・`983`(ott 欠落)・`996`(complete の失敗)がすべて「うまくいかなかったみたい。もういちどためしてね」。E15 §2.8 が区別している「Google 側で拒否・中断(`denied`)」「state 期限切れ(`expired`)」「ott 二重使用・期限切れ(410)」が同じ文になる。

ガイド §3「短くしすぎてはいけないもの」は**エラー文言**を明示的に挙げ、「何が起きて何をすればいいかは書く」としている。

**改善方向**: 少なくとも「自分でキャンセルした(`denied`)」は失敗として出さない(何も出さないか「やめました」程度)。「期限切れ」はやり直せば直ることを言う。

### 2.5 別端末でログインする

#### J5-1 「おかえり!」が、別アカウントへの切替にも出る — **Minor**

**根拠**: `App.tsx:991-993` は `outcome === 'linked'` かどうかだけで分岐し、`switched`(E15 §2.4 ケース 2・4)と `already`(ケース 3)を同じ「おかえり!」にまとめている。ケース 4 は「別の Google アカウントで新しいアカウントに切り替わった」場合であり、「おかえり」ではない。

**影響**: 家族で端末を共有して使い分ける(E15 §2.4 の想定用途)場面で、誰のアカウントに入ったのかを文が誤って肯定する。J1-1 のアカウント表示があればこの文自体が要らなくなる。

**改善方向**: 3 outcome を区別するか、文をやめて「表示名が切り替わったこと」を画面の状態で見せる(原則 3)。

#### J5-2 匿名の記録が放棄されることが、切り替わる前に一切示されない — **Important**

**根拠**: AU-D3(マージなし)により、既に別アカウントを持つ人がこの端末でログインすると、この端末で遊んだ匿名の記録は見えなくなる(E15 §2.5「放棄される」)。しかし切替確認が出るのは `state.registered` が真のときだけ(`App.tsx:661-668`)で、**匿名ユーザーには何も出ない**。匿名ユーザーこそが記録を失う側である。

**影響**: 「きろくをのこす」を押した結果、その端末の記録が見えなくなる — ラベルと結果が正反対になりうる。

**改善方向**: 失う可能性の告知はサーバー側では判定できない(begin の前に `sub` は分からない)ため、**完了後**に扱う。`switched` の完了時に「べつのアカウントであそんでいた記録に切り替わったよ」と明示し、直前の匿名セッションへ戻る手段はない旨を 1 行で伝える。ログイン前の予告(原則 4 が禁じる「起きていない結果の予告」)にはしない。

### 2.6 ログアウトする / アカウントを切り替える

#### J6-1 登録済みユーザーはアカウントを切り替えられない(切替確認が到達不能) — **Critical**

**根拠**: メニューのボタンは `onClick={registered ? onLogout : onLogin}`(`MenuScreen.tsx:66`)。したがって登録済みのとき `beginLogin` はメニューから呼べない。他の呼び出し口も条件付きで塞がっている:

- `App.tsx:1349` の `onRegister` は `showResultAuthPrompt` が真のときだけ渡され、その条件は `!state.registered`(`App.tsx:956`)
- `App.tsx:1363` の `ProposalFormScreen.onLogin` は常に渡されるが、ログインボタンが描画されるのは `!registered` の枠占有パネル内だけ(`ProposalFormScreen.tsx:213-235`)

結果として、`App.tsx:661-668` の切替確認(「別のアカウントでログインすると、この端末はそのアカウントに切り替わります」)は**到達不能なコード**になっている。E15 §2.4 ケース 4 と §2.7「登録済み端末での再ログインは切替確認を先に出す」は、UI 側に対応する導線がない。

**影響**: 家族で端末を共有して使い分けるという明示された想定用途が、実際には「一度ログアウトしてから入り直す」でしか実現できない。しかも J6-2 のとおりログアウトは無確認の 1 タップである。

**改善方向**: 登録済み状態でも「べつのアカウントにする」を別項目として持つ。ログアウトと切替を 1 つのボタンに畳まない。

#### J6-2 ログアウトが無確認の 1 タップで、しかも状態表示ボタンと同じもの — **Important**

**根拠**: `App.tsx:1393-1396` は確認なしで `client.switchSession(null)` を呼ぶ。そのボタンは同時に「登録済み」という状態表示を兼ねている(`MenuScreen.tsx:63-69`)。

**影響**: 「自分が誰か確かめようとして触ったらログアウトしていた」が起きる。共有端末(E15 §2.7 がログアウトの理由として挙げている用途)では、他人に 1 タップでログアウトさせられる。

**改善方向**: 状態表示(触っても何も起きない)と、ログアウト(確認を伴う)を分ける。確認は `Dialog` で。

#### J6-3 `window.confirm` を使っている — **Important**(違反)

**根拠**: `App.tsx:663-665`。`packages/web/src/components/Dialog.tsx` は存在する。ここで出しているのは通知ではなく**決断を求める説明文**なので、ガイド §3 判断 4 の部品テスト(「説明を置く先は `Callout` か `Dialog` の中か」)が正面から適用され、そのどちらでもない場所に置いている点で違反にあたる(この点が J4-2 とは異なる)。なお同じパターンは退室確認にも 2 か所あり(待機画面 `App.tsx:1128`・セットリザルトの `onHome` `App.tsx:1338`。どちらも同一文言「部屋から出ますか?」)、認証固有の問題ではなくアプリ全体の癖である。

**影響**: OS のダイアログはオリジン(`daifugo-together.fly.dev は次のように表示しています`)を出し、書体も色もアプリの外側になる。デザインシステム §4「トーン判定」の造形・文言の規律がまるごと効かない領域が、最も緊張する瞬間(アカウント切替)に現れる。

**改善方向**: `Dialog` に置き換える。文言もデザインシステム §4 の文言 Do に合わせる(現状の「切り替わります」は敬体・漢字主体で、他の認証文言のトーンと不統一)。

### 2.7 提案から登録を勧められる

#### J7-1 Callout が 2 枚積まれている — **Important**(違反)

**根拠**: `ProposalFormScreen.tsx:372-377`(未登録向けの注記)と `378-380`(AI 確認の注意書き)が連続する。UI 文言ガイド §3「文を置いてよい場所」は「**`Callout` — 1 画面 1 枚まで。これを 2 枚使いたくなったら、たいてい設計が間違っている**」と明示している。

**影響**: 送信ボタンの下に説明が 2 段積まれ、フォームの終わりが説明で埋まる。

**改善方向**: 2 枚のうち片方を消す。J7-2・J7-3 のとおり、消すべきは未登録向けの 1 枚目である。

#### J7-2 未登録の注記が「まだ起きていない制限」を毎回予告している — **Important**(違反)

**根拠**: `ProposalFormScreen.tsx:373-376` は未登録なら常時「とうろくしなくても 1 つずつ ていあんできるよ。Google とうろくすると いくつでも ていあんできるよ。」を出す。一方、枠が埋まったときのパネル(`ProposalFormScreen.tsx:239-240`)は「ていあんは 1 つずつ。けっかが出たら、つぎの ていあんが できるよ。Google とうろくすると いくつでも ていあんできるよ。」とほぼ同文である。

ガイド原則 4「予告しない、遅らせる」と、原則 1 の根拠である「**問題を経験する前の人はその問題についての情報を処理できない**」に照らすと、1 枚目は読まれないまま場所を取る文である。制限を知る必要が生じるのは枠が埋まった瞬間であり、その瞬間には既に専用のパネルがある。

**改善方向**: 常設の 1 枚目を削除する。枠の状態は「送信できる/できない」という**結果**が語る(原則 3)。

#### J7-3 残る 1 枚(AI 確認の注意)がトーン不統一 — **Important**

**根拠**: `ProposalFormScreen.tsx:379` は「提案はAIが確認します。不正な命令はイエローカードの対象です。都道府県は遊んでいた記録として残ります。」— 敬体・漢字主体・3 文。同じ画面の他の文言(`239-240`、`374-375`)はひらがな主体の常体である。

**改善方向**: 1 文に絞り、文体を画面に合わせる。都道府県の断り書きは都道府県フィールドの下に畳む(デザインシステム §3.3 の非断定表現は維持する)。

#### J7-4 枠占有パネルにログイン以外の出口がない — **Minor**

**根拠**: `ProposalFormScreen.tsx:218-244` は AppBar の戻るボタンと Callout 内のログインボタンだけを持つ。進行中の提案名と状態は出る(`223-228`)が、そこから「マイ提案」へ行く導線はない。

**改善方向**: 進行中の提案行自体をマイ提案への導線にする。

**接続**: J1-1(アカウント状態がどこにも出ない)と同じ欠落の一部。N-1 のアカウント行が入れば同時に解ける。

#### J8-2 名前を変える手段が Web に存在しない(サーバーは実装済み) — **Critical**

**根拠**: サーバー側は完成している。

- Socket 受口: `packages/server/src/room/socket-gateway.ts:642-668`
- 部屋内への反映: `packages/server/src/room/reducer.ts:962-985`(`rename` 関数)・`:1249-1250`(ディスパッチ)
- 永続化: `packages/server/src/persistence.ts:144-152`(`rename`)、`packages/server/src/room/session.ts:55`

対して Web 側は `grep -rn "rename" packages/web/src` が **0 件**である。`multiplayer/client.ts` に送信メソッドすら存在しない。

とくに重要なのは受口の構造である。部屋への反映は `socket-gateway.ts:650-663` の `if (current)` ブロックの中にあるのに対し、**永続化 `sessions.rename` はそのブロックの外(`:664`)にある**。つまり部屋にいてもいなくても永続化は走る。**メニューからの改名をサーバーは既に受けられる**ということであり、必要なのは UI と 1 本の emit だけで、サーバー仕様の変更はいらない。

**影響**: 実装済みの機能が UI 不在で死んでいる。構図は J6-1(切替確認が到達不能)とまったく同じ — サーバーとプロトコルが先に完成し、UI 側の受け皿が作られていない。

#### J8-3 既定名のまま登録・引き継ぎまで進んでしまう — **Important**

**根拠**: 既定名は `packages/server/src/persistence.ts:81-88` で自動付与される。`ゲスト` + **連番**を base36 表現にしてゼロ詰めした 6 桁である。連番の起点は起動時の `users` 件数(`:89-93`)で、以後 1 人ごとに増える。1 人目なら「ゲスト000001」、12 人目なら `(12).toString(36)` = `c` を大文字化してゼロ詰めした「ゲスト00000C」になる。

`displayName` に一意制約はない(`:112-141` の再試行ループは `userId`/`userToken` の衝突用である)。**通常の運用では起動時の `count(*)` 初期化によって重複は起きない**が、重複を防ぐ仕組みが存在しないことは事実であり、少なくとも次の経路では起こりうる — 行を削除して件数が減った状態で再起動すると採番が巻き戻る / 改名(`user:rename`)で既存の誰かと同じ既定名パターンを名乗れる。

そしてこの名前は、E15 §2.5 のとおり引き継ぎでそのまま持ち越される。AU-D5 により Google からも名前は取得しない。したがって**「ゲスト000001」のまま登録すると、それが恒久的なアカウント名になる**。変更手段は J8-2 のとおり存在しない。

**影響**:

1. 卓の 4 人が「ゲスト00000C / 00000D / 00000E」だと誰が誰か区別できない(base36 なので、連番が近い人どうしは末尾 1 文字しか違わない)
2. 連番がそのまま外から見える(何人目のユーザーかが他プレイヤーに分かる)
3. **「きろくをのこす」で残す「きろく」の主語が空欄のまま確定する** — 引き継ぎの価値は「自分の記録である」という感覚に支えられているのに、その自分を指す名前が自動生成の連番のままになる

**接続**: 3 は J3-3(ラベルから何が起きるか分からない)と J1-1 の合流点である。

**改善方向**: 既定名の自動付与は維持する(名前入力を強制すると「登録ゼロで遊べる」= E15 §1.1 が崩れる)。そのうえで、**登録の直前**(N-3 のログイン前確認ダイアログ)に名前の確認・変更を差し込む。恒久化される瞬間は登録であり、その瞬間こそ名前を意識する自然なタイミングである。

#### J8-4 名前の制約がクライアント側に存在しない — **Minor**

**根拠**: 制約は 2 か所で定義済み。`packages/core/src/protocol.ts:206-219`(trim → 1 コードポイント以上 → 10 コードポイント以下 → 制御文字 `code <= 31` と `code === 127` の禁止)と、部屋側の同等判定 `packages/server/src/room/reducer.ts:978-985`。禁止語・重複チェック・文字種制限はない(絵文字も全角も通る。改行は `\n` = 10 が制御文字判定で弾かれる)。

Web 側には対応する検証も入力 UI もない。

**改善方向**: 入力 UI を作るときは、この 3 条件を**そのまま**クライアント検証に写す(提案フォームが `validateProposal` を core から共有しているのと同じ流儀。`ProposalFormScreen.tsx:177`)。UI 側で条件を足さない — サーバーが唯一の正であり、片方だけ厳しくすると「入力できるのに拒否される」または逆が起きる。

## 3. 文言の問題

### 3.1 同じ概念に 5 系統の呼び名がある — **Important**

「Google と紐付ける」という 1 つの操作に、次の呼び名が同時に存在する。

| 呼び名 | 場所 | 使われる状況 |
|---|---|---|
| 引き継ぎ・ログイン | `MenuScreen.tsx:68` | 未登録のメニュー |
| 登録済み・ログアウト | `MenuScreen.tsx:68` | 登録済みのメニュー |
| きろくをのこす | `SetResultScreen.tsx:136` | リザルト |
| Googleでログイン | `ProposalFormScreen.tsx:234` | 提案の枠占有パネル |
| (Google)とうろく | `ProposalFormScreen.tsx:240, 374-375` | 提案の注記 |
| 引き継ぎ登録したよ | `App.tsx:992` | 完了(linked) |

同一機能に対し「引き継ぎ」「登録」「ログイン」「きろくをのこす」「とうろく」の 5 語が使われ、`MenuScreen.tsx:68` に至っては 1 つのラベルの中で「引き継ぎ」と「ログイン」を中黒でつないでいる。

ガイド原則 2「ラベルは最後の手段」は「ラベルを値に畳み込め」と言うが、ここで起きているのは**ラベルの多重化**であり、原則以前の問題である。

**改善方向**: 語を 2 つに整理する。

- ユーザーが得るもの = **「きろく」**(表示名・提案・イエローカード等、`users` 行に紐づく一切)
- 操作 = **「Google でつなぐ」**(登録)/ **「Google でもどす」**(別端末ログイン)/ **「サインアウト」**

「引き継ぎ」は E15 の設計語彙であって、プレイヤーの語彙ではない。実際「引き継ぎ・ログイン」というラベルは、その 2 語のどちらが自分の状況なのかをユーザーに判定させている。

### 3.2 対象年齢とトーンの不統一 — **Important**

同じ認証フローの中で 3 つの文体が混在する。

| 文体 | 例 | 場所 |
|---|---|---|
| ひらがな常体(子ども向け) | 「引き継ぎ登録したよ」「おかえり!」「もういちどためしてね」 | `App.tsx:992-996` |
| 敬体(大人向け) | 「ログアウトしました」 | `App.tsx:1395` |
| 敬体と常体が 1 文内で混在 | 「接続を確認中です。少し待ってからもう一度ためしてね」 | `App.tsx:671` |
| 敬体・漢字主体(硬い) | 「別のアカウントでログインすると、この端末はそのアカウントに切り替わります」 | `App.tsx:664` |
| 敬体・漢字主体(硬い) | 「提案はAIが確認します。不正な命令はイエローカードの対象です。」 | `ProposalFormScreen.tsx:379` |

とくに `App.tsx:992`(「引き継ぎ登録したよ」)と `App.tsx:1395`(「ログアウトしました」)は**同じ `authMessage` スロットに入る文**であり、同じ場所に交互に出る。

**改善方向**: 認証まわりの文体を 1 つに決める。デザインシステム §4 の基準(「ひらがな多めでも語彙は大人にも自然に」)からは、常体・ひらがな主体に寄せるのが整合する。ただし「サインアウト」のような外部語彙は無理にひらがな化しない。

### 3.3 分かち書きの空白 — **Minor**(違反の趣旨)

**根拠**: `ProposalFormScreen.tsx:239-240, 374-375` と `packages/web/src/proposal/client.ts:88-89` は「ていあんは 1 つずつ」「つぎの ていあんが できるよ」「とうろくしなくても 1 つずつ ていあんできるよ」のように単語間に空白を入れている。文字コード上は半角スペース(U+3000 は 0 件)だが、画面上の効果は分かち書きそのものである。

デザインシステム §2.3 の規約 2 は「UI 文言に分かち書きの全角スペースを入れない」、§4 の文言 Don't は「分かち書きの全角スペース(「タップして はじめる」)」を挙げている。文字通りには全角のみを禁じているが、禁じている理由(見た目の間延び・幼児向けの印象)は半角でも同じである。

**改善方向**: 空白を詰める。可読性のためにどうしても区切りたいなら、読点か改行で区切る。

### 3.4 「マイ提案」だけ漢字 — **Minor**

**根拠**: メニューの並びは「あそぶ」「ルールをていあんする」「ルール図鑑」「マイ提案」「引き継ぎ・ログイン」(`MenuScreen.tsx:43-69`)。ひらがな主体の 2 つと漢字の 3 つが混在している。

認証固有の問題ではないが、新設するアカウント表示の語彙を決めるときに一緒に裁定すべき点として記録する。

## 4. 動線・情報設計の問題

### 4.1 入口の分散と、状態の置き場の不在

3 か所の入口(J1-2)がそれぞれ独立した文言・部品で認証を語っており、**「アカウント」という概念の置き場が存在しない**(J1-1)。この 2 つは同じ欠落の裏表である。状態を置く場所がないから、状態を語る役目がボタンのラベル(`MenuScreen.tsx:68`)に押し付けられ、その結果ボタンが状態表示と破壊的操作を兼務し(J6-2)、切替の入口が消える(J6-1)。

つまり **J6-1・J6-2 は J1-1 の症状**であり、ワイヤーフレーム側では「アカウントの置き場を 1 つ作る」ことで一括して解ける。

追補分の **J8-1(自分の名前が見えない)・J8-2(名前を変えられない)も同じ症状**である。表示名は「自分が誰か」を構成する最大の要素であり、置き場がないという 1 つの原因から、登録状態・表示名・アカウント操作の 3 つが同時に行き場を失っている。逆に言えば、置き場を 1 つ作れば 5 つの指摘(J1-1・J6-1・J6-2・J8-1・J8-2)が同時に解ける。ここが次工程の最大の梃子である。

さらに J8-2 と J6-1 は、症状だけでなく**成因も同じ**である。サーバーとプロトコルが先に完成し(`user:rename` の受口、切替確認を要する `switched` 分岐)、UI 側の受け皿だけが作られていない。ワイヤーフレームでは「サーバーに既にある能力のうち、UI から到達できないもの」を洗い出す観点を持つとよい。

### 4.2 フィードバック手段の選択が場当たり

現状の対応は次のとおり。

| 伝えたいこと | 現状の手段 | あるべき手段 |
|---|---|---|
| 登録できた / おかえり | 裸の `<p>`(`MenuScreen.tsx:71`) | `Toast`(E15 §2.7 も「トースト」。DS §5-13 の完了通知の用例と整合) |
| ログアウトした | 同上、消えない | `Toast`(同上) |
| 失敗した | 同上、3 原因で同一文 | **未決**(下記の正典衝突。Q-5) |
| いま登録済みか | ボタンのラベル | 常設のアカウント表示(状態) |
| 切替の確認 | `window.confirm`(`App.tsx:663`) | `Dialog` |
| OAuth 未設定 | ブラウザに生 JSON(§2.4 J4-1) | **未決**(同上。ただしアプリ内に留めることは確定) |

`Toast` も `Dialog` も既に存在する(`packages/web/src/components/`)。**部品がないから使えなかったのではなく、使う判断がされていない**。

#### 正典どうしが衝突している(失敗系の受け皿)

成功通知については 3 つの正典が一致している。design-system.html §5-13(1211-1219 行)は「招待コードをコピーしました」「提案を受け付けました」をトーストの用例として挙げ、E15 §2.7 も完了時のトーストを指定している。ここに争いはない。

**衝突するのは失敗系である。**

- design-system.html §5-13(1218 行): 「**エラーはトーストにせず、その場のフォームエラーかモーダルで返す**」。`Toast.tsx:14-15` のコメントもこの一文をそのまま引いている
- E15 §2.8: 「503 → 『いまは使えないみたい』**トースト**」「ott 二重使用・期限切れ → 同じエラー**トースト**」

認証の失敗は「その場のフォームエラー」に落とせない(フォームがない。OAuth から戻ってきた直後の画面には入力欄が存在しない)ため、DS の規定に素直に従うなら**モーダル**になる。一方 E15 はトーストを指定している。どちらの文書も本レビューの参照正典であり、レビューの側で一方を切り捨てるべきではない。裁定として §5.5 の Q-5 に上げる。

なお、ガイド §3 の部品テストは「説明を置く先は `Callout` か `Dialog` の中か。画面に生の段落を置いていないか」であり、**通知**の受け皿には触れていない(通知の正は design-system.html §5-13 側にある)。ガイドと DS の分担がここで曖昧なので、ガイド側に 1 行の追記余地がある(注記は `Callout`、決断を迫るものは `Dialog`、通知は DS §5-13 に従う)。

### 4.3 認証だけがアプリの外へ出る構造

`auth/client.ts:29-47` の隠しフォーム POST は、成功時のみ 303 を返す前提の実装であり、失敗はすべてアプリの外(生 JSON のページ)に落ちる(J4-1)。E15 §2.3 が定めた `POST /api/auth/begin` → `{ authUrl }` → `location.href` の経路を使えば、失敗はアプリ内に留まる。**サーバー仕様の変更は不要**で、`/api/auth/begin` は既に実装されている(`app-server.ts:264-283`)。

### 4.4 対局中の扱いが 2 つの仕様の間で割れている

E15 §2.3(対局中は導線を出さない)と §2.7(セットリザルト後に導線を出す)は、リザルトが部屋の中である以上そのままでは両立しない(J3-1)。ワイヤーフレームではこの矛盾をどちらかに倒す必要がある。倒し方の候補:

- **A. リザルトでは誘導のみ、実行は退室後**: リザルトでは「あとでメニューから引き継げる」ことを示すだけにし、退室後のメニューに未処理の合図(バッジ)を残す
- **B. リザルト導線を廃止**: 初回退室直後のメニューで 1 回だけ勧める

A は導線が 2 段になる(リザルトで気づかせ、メニューで実行させる)。段が増えれば途中で落ちる人が出ると**推測される**が、これは実測に基づく主張ではなく、本プロダクトで計測した数字もない(E15 §5 のとおり登録率の観測は未実装)。B は単純で、E15 §2.3 の制約と衝突しない。判断は AU-T2(表示頻度の裁定)と合わせて行うのが自然である。

#### N-4 の補足 1: ガイド原則 3 との関係(トーストを許す条件)

ガイド原則 3(`UI文言・情報量ガイド.md:52`)は「押したボタンが塗りに変わって残る = 『送信済み』。**トーストも「〜しました」も要らない**」と述べている。N-4 はこれと衝突しうるので、例外の条件を明文化しておく。

**トーストを許すのは、次の 3 つをすべて満たす操作に限る。**

1. **一度きりで、繰り返して確かめられない** — 引き継ぎ登録は生涯 1 回である。評価ボタンのように「もう一度押して確かめる」ができない
2. **不可逆、または取り消しに別の操作が要る** — `switched` で放棄した匿名の記録は戻らない(AU-D3)。ログアウトは再ログインを要する
3. **結果の状態表示だけでは成功が確認できない瞬間がある** — 認証は外部サイトを往復して戻るため、戻った直後に「いま何が起きたか」を言う主体が画面に存在しない

原則 3 が想定しているのは、状態が**その場に残る**操作(押したボタンが塗りで残る、送信済みの提案が一覧に出る)である。認証はページ全体が破棄されて再構築されるため、「押したボタン」自体が存在しない状態で戻ってくる。ここが例外の根拠である。

逆に言えば、**J1-1 のアカウント表示(N-1)が入れば、成功トーストの必要性は下がる**。表示名+登録済みバッジが常時見えていれば、「登録できたか」は画面を見れば分かる(原則 3 の本来の解き方)。したがって N-4 の成功トーストは、**画面遷移直後の 1 度だけ**という位置づけにとどめ、状態表示の代わりにはしない。

#### N-4 の補足 2: 自動退場は新規実装が必要

design-system.html §5-13(1218 行)は「duration-base で出て **3 秒で退場**」と規定しているが、現行の `packages/web/src/components/Toast.tsx` はタイマーを持たない純粋な表示部品である(`GameScreen.tsx:153-160` の呼び出し側も表示条件で出し入れしている)。N-4 で「自動で消える」を実現するには、**退場タイマーと退場アニメーションの実装が新たに必要**である。ワイヤーフレームの工数見積もりに含めること。

### 5.6 表示名(プレイヤー名)の設計方向 — 2026-07-30 追補

#### どこで見せるか — アカウント行に畳む

名前を独立した「設定」項目として立てない。**N-1 のアカウント行が名前そのものである**、という構造にする。

これはガイド原則 2「ラベルは最後の手段」(`UI文言・情報量ガイド.md:42-46`)の直接の適用である。「なまえ: ゲスト000001」ではなく、行に「ゲスト000001」と登録状態のバッジが並ぶ。ラベル「なまえ」は書式と文脈(アカウント行の主役の位置にある文字列)で自明になる。

同じ理由で、名前とアカウント状態を別々の行に分けない(U-5)。この 2 つは「自分は誰か」という 1 つの問いへの答えであり、分けると J1-2 で指摘した「入口の分散」を新しく作り直すことになる。

#### いつ設定を促すか — 3 案

**制約**: 名前入力を必須にしてはならない。E15 §1.1 の「登録ゼロで遊べる」体験は、既定名の自動付与(`persistence.ts:81-88`)によって成立している。入力を通過儀礼にすると、遊び始めるまでの段差が増える。

| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| **A. 任意のまま** | アカウント画面に「なまえをかえる」を置くだけ。促さない | 最小。段差ゼロ | 既定名のまま登録まで進む人が残る(J8-3 は解けない) |
| **B. 登録の直前だけ促す** | N-3 のログイン前確認ダイアログに現在の名前を出し、その場で直せるようにする | 名前が恒久化される瞬間に一致する。段差は登録時だけ | 登録しない人はずっと既定名 |
| **C. B + 初回の待機画面でも軽く促す** | 待機画面の自席が既定名のとき、名前をタップで編集できることを示す | 対戦相手に名前が見える直前で、動機が最も強い | 待機画面に要素が増える。対局中の改名は部屋の状態変化を伴う(`reducer.ts:962-985`)ため描画の考慮が要る |

**推奨は B**(必要なら C)。理由は 3 つある。

1. **問題を経験する前の人は情報を処理できない**(ガイド原則 1 の根拠、`UI文言・情報量ガイド.md:38`)。初回起動時点では「名前が要る理由」が存在しない。まだ誰にも会っていないからである
2. **原則 4「予告しない、遅らせる」** — 名前が必要になる場面(卓に人が並ぶ / 記録が恒久化する)まで遅らせるのが素直
3. B の位置は**操作の下流**である(登録ボタンを押した**あと**に出るダイアログの中)。原則 1 の位置テスト(同 93 行)を満たす

**やってはいけないこと**: メニューやタイトルに「なまえを決めよう」の説明文や催促バナーを置く。これは操作対象の上流に置いた説明そのもので、読まれないまま画面を圧迫する(原則 1)。促すなら**文ではなく状態**で示す — 既定名のときだけアカウント行の名前を控えめな未設定スタイルにする、程度でよい(原則 3)。

#### 入力 UI

- **制約はサーバーの写し**: trim 後 1〜10 コードポイント、制御文字(`code <= 31`・`127`)禁止(`protocol.ts:206-219`)。それ以上の条件を UI 側で足さない(J8-4)
- **カウンタは既存の流儀に合わせる**: 提案フォームが `countCodePoints` で「n / 上限」を出し、上限超過を入力時点で切り詰めている(`ProposalFormScreen.tsx:304-319`)。同じ部品・同じ見た目を使う。**コードポイント数え**である点が重要で、`String.length` では絵文字で食い違う
- **既定値をプリセットする**: 入力欄を空で開かない。現在の名前を入れておけば、「変える」という操作であることが形で分かり、うっかり空のまま保存する事故も減る
- **説明文は置かない**: 「10文字までで入力してください」はカウンタと重複する(原則 2・3)。エラーは入力欄の下流にその場で出す(ガイド §3「短くしすぎてはいけないもの」はエラー文言を例外として挙げている)
- **保存の合図**: 名前は「その場に状態が残る」典型なので、成功トーストは要らない(原則 3、および §5.1 N-4 の補足 1 の例外条件を満たさない)。アカウント行の表示が変わることが確認そのものである

#### 既定名からの変更動機づけ

既定名「ゲスト000001」は**変えたくなる形をしている**ことを利用する。連番であること・他人にもそう見えていることが分かれば、動機は説明せずとも立つ。

したがって必要なのは説得の文ではなく、**事実の可視化**である。

1. 自分の名前が見える(N-6)。いま何と呼ばれているかを知る
2. 他人にもその名前が見えていると分かる(待機画面で他席に他人の名前が並んでいるのを見れば、対称性から自席も同様だと推測できる)
3. 変える手段がすぐ隣にある(N-7)

この 3 つが揃えば「Google とうろくすると…」のような勧誘文は不要である。

#### 対局中の「あなた」表示との関係

現状は 8 か所すべてで自席が「あなた」に固定されている(J8-1 の表)。これは対局中の視認性としては合理的で、**変えるべきだと断定はしない**。ただし次の 2 点は決めておく必要がある(Q-7)。

- 名前を設定した人にも「あなた」を通すのか。通すなら、名前を確認できる場所はアカウント行だけになる(それで足りるかの判断)
- 待機画面だけ扱いを変えるのか。待機画面は「これから一緒に遊ぶ相手に自分がどう見えているか」を確かめる唯一の機会であり、ここだけ自席を `名前(あなた)` の形にする案は検討に値する

いずれにせよ 8 か所は**同じ規則で**扱う。現在はすべて個別に `'あなた'` をリテラルで書いており(`App.tsx:384, 416, 465, 508, 544, 568, 1178`・`Table.tsx:81`)、規則が変わると 8 か所を独立に直すことになる。しかも対戦画面の席は `App.tsx:465` と `Table.tsx:81` の二重置換なので、片方を直し忘れると表示が食い違う。ワイヤーの段階で「自席をどう名乗らせるか」を **1 つの規則**として明記し、実装側では 1 か所に寄せられる形(view-model を組む時点で決める / `isSelf` を渡して描画側だけで決める、のどちらか)にしておく。
