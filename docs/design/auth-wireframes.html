2. 用語と文体(1 系統に確定)

レビュー §3.1 の指摘(「引き継ぎ / 登録 / ログイン / きろくをのこす / とうろく」の 5 系統)を、名詞 1 語 + 動詞 3 語に畳む。以後この表以外の言い方を画面に出さない。

概念画面に出す語使う場所採った理由
ユーザーが持っているもの(表示名・提案・イエローカード等、users 行に紐づく一切)きろくアカウント画面のタイトル、誘い文プレイヤーが失う/得るものを名指しできる唯一の語。「アカウント」「引き継ぎ」は設計語彙で、子どもが自分の状況に当てはめられない
Google と紐付ける(初回・別端末とも)Googleでつなぐアカウント画面の主 CTA、確認ダイアログ、提案画面・誘いの Callout初回登録(linked)と別端末ログイン(switched)はユーザーには同じ 1 操作。「登録」と「ログイン」に割ると、どちらが自分かをユーザーに判定させることになる(レビュー §3.1)
別の Google アカウントに切り替えるべつのアカウントにするアカウント画面(登録済み)、切替確認共有端末での使い分け(E15 §2.4 ケース 4)。「つなぐ」と同じ語にすると切替が事故になる
この端末からきろくを離すサインアウトアカウント画面(登録済み)、確認、完了トースト外部語彙は無理にひらがな化しない(デザインシステム §4「語彙は大人にも自然に」)。「ログアウト」と混在させずサインアウトに固定
ユーザーの呼び名なまえアカウント行、なまえ入力「表示名」「プレイヤー名」は設計語彙。行の主役の位置に文字列が置かれていれば「なまえ」というラベルすら要らない(原則 2)

文体: 常体・ひらがな主体に統一する(U-3)。敬体(「ログアウトしました」)と常体(「引き継ぎ登録したよ」)が同じスロットに交互に入る現状を解消する。分かち書きの空白は全角・半角とも使わない(デザインシステム §2.3 規約 2・§4 文言 Don't。レビュー §3.3)。「!」は連打しない。

状態バッジ: 未登録 =「この端末だけ」/ 登録済み =「どの端末でも」。バッジで登録の有無ではなくきろくがどこまで届くかを言う。「未登録」は欠落を責める語で、登録ゼロで遊べる(E15 §1.1)という前提と噛み合わない。代替案は「未登録 / つないである」。

      同じ S-b には、登録済みのまま別の"既存"アカウントに入った場合(ケース2)も入る

    → DLG-2 切替確認ダイアログ → Google → 完了 → RES-2 ダイアログ S-b

  アカウント画面 →「サインアウト」→ DLG-3 確認 →「サインアウトする」

  対局中                     → 部屋の画面にアカウント行を出さない(A-7)

5. 裁定事項(Q-1〜Q-8)の仮決めと代替案

#論点本ワイヤーの仮決め根拠代替案(採らなかった側)
Q-1リザルト誘導を A(予約)/ B(廃止)のどちらにするか B: リザルトの導線は廃止。誘いは退室直後のメニューに 1 枚だけ出す(F-1・F-2) リザルトは部屋の中であり、押した瞬間に OAuth のフルページ遷移が起きると同席者の卓から黙って消える(J3-1)。B は E15 §2.3 と衝突せず、導線も 1 段で済む。A は「気づかせる」と「実行する」で 2 段になり、予約状態という新しい状態を 1 つ増やす A(リザルトでは合図だけ残し、メニューにバッジで予約を持ち越す)。段が増えたぶんの脱落は推測で、本プロダクトに実測はない(レビュー §4.4)。登録率を観測できるようになったら再検討する
Q-2登録誘導の表示頻度(現状は端末で生涯 1 回) セットを遊び終えて退室したときに出す。初回 + 以降は 3 セットごと。表示済みフラグは実際に描画された時点で立てる 現状は「まだ価値が分かっていない初回」に消費され、価値が分かる頃には二度と出ない(J3-4)。回数ではなく遊んだ量に連動させる。ダイアログではなく Callout なので、出続けても操作は塞がない (a) 生涯 1 回のまま(いまの実装)。(b)「ていあんが 1 件たまったら」等の到達条件連動。(b) は条件の観測点が増えるため v1 では採らない。AU-T2 の裁定はこの行で足りる
Q-3語彙の最終決定 §2 の表のとおり(きろく / Googleでつなぐ / べつのアカウントにする / サインアウト / なまえ) レビュー §3.1・U-2 の推奨に沿う。「登録」と「ログイン」を分けないのは、ユーザー側にケース判定をさせないため 「Googleでもどす」を別ラベルとして持つ案(レビュー原案)。どちらが自分の状況かをユーザーは事前に知り得ないため 1 語に畳んだ。「もどってくる」感は完了時の文言(「おかえり、ゆうた」)で担保する
Q-4メニューの語彙(「マイ提案」の漢字)を今回あわせて整理するか 今回は触らない。認証まわりの新規文言だけを §2 で統一する 「マイ提案」は認証と独立した既存導線で、変えるとマイ提案画面・未読バッジ・図鑑側の呼称まで波及する。認証の再設計と同じコミットに混ぜると、レビューの対象が二重になる 「じぶんのていあん」へ改称。やるなら独立した文言統一タスクとして、図鑑・ステータス表示とまとめて行う
Q-5失敗系フィードバックをトーストにするか、モーダルにするか(design-system.html §5-13 と E15 §2.8 の衝突) モーダル(Dialog)。ただし denied(自分でやめた)は何も出さない(RES-3) (1) DS §5-13 は「エラーはトーストにせず、その場のフォームエラーかモーダルで返す」と明示し、Toast.tsx のコメントもこれを引いている。(2) 認証の失敗は「その場のフォームエラー」に落とせない(戻ってきた画面に入力欄がない)。(3) 失敗には「もういちど」という次の操作が要り、トーストにはボタンを載せられない。(4) 外部サイトから戻った直後は注意が画面外にあり、3 秒で消える通知を見落とす トースト(E15 §2.8)。裁定後は E15 §2.8 の「トースト」の記述に読み替えノートを入れること(503・ott 失効・denied の 3 行)。逆に本書が負けた場合は RES-3 をトースト化し、「もういちど」はアカウント画面から再操作させる
Q-6なまえの設定をいつ促すか B: 登録の直前だけ。DLG-1 の確認ダイアログにいまのなまえを出し、その場で直せる。あわせて、既定名のときだけアカウント行の名前を控えめな未設定スタイルにする(文では促さない) レビュー §5.6 の推奨。なまえが恒久化される瞬間は登録であり、その瞬間が唯一「なまえが要る理由」を経験している時点である(原則 1)。DLG-1 は登録ボタンを押したあとに出るので位置テスト(下流)も満たす A(促さない)は J8-3 が解けない。C(初回の待機画面でも促す)は動機が最も強い場所だが、対局中の改名が部屋の状態変化を伴うため描画の考慮が要る。C は Q-7 の待機画面表示(なまえが他人に見えている事実の可視化)で代替した。効果が足りなければ C を足す
Q-7対局画面の自席を「あなた」のままにするか(8 か所) 対戦・リザルトの 7 か所は「あなた」のまま。待機画面の自席だけ「ゆうた(あなた)」にする(A-7) 対局中の視認性としては「あなた」が合理的で、変える理由がない。一方、待機画面は「これから遊ぶ相手に自分がどう見えているか」を確かめる唯一の場面であり、ここで他席に他人のなまえが並ぶ対称性から、自分のなまえも見えていると分かる(§5.6 の「説得ではなく事実の可視化」) (a) 全 8 か所を「あなた」で通す(なまえを見る場所はアカウント行だけになる)。(b) 全 8 か所をなまえにする(自席が探しにくくなる)。実装規則: 自席の呼び方は view-model を組む時点で 1 か所に寄せる。App.tsx:465 と Table.tsx:81 は二重置換なので必ず対で直す
Q-8switched の完了通知をトーストにするかダイアログにするか(レビュー §5.4 行12「完了通知 × 3(成功系 = Toast)」との矛盾) ダイアログ。switched の 2 種(S-a / S-b)だけ Dialog にし、linked と already はトーストのまま(RES-1・RES-2)。コントローラー承認済み(2026-07-30) S-a は匿名のきろくの放棄という不可逆な事実(AU-D3: マージなし)を伴い、3 秒で消えるトーストでは見落とす。外部サイトから戻った直後は注意が画面外にあり、見落とすと「記録が勝手に消えた」という誤解だけが残る(J5-2)。S-b は失うものが無いが、誰のきろくに入ったかを取り違えると以後の行動が全部ずれるため、2 種を同じ部品で揃えた。Q-5(失敗系 = モーダル)と同じ判断基準「次の理解が必要なものは消さない」 レビュー原案どおり 3 outcome すべてトースト(部品の使い分けが減る)。中間案として S-a だけダイアログ・S-b はトースト。裁定が覆る場合は本書 RES-2 を直す

裁定が確定したあとに読み替えノートが要る文書(引き継ぎ事項): Q-1 = B を確定させるときは、E15 §2.7 の「セットリザルト後」の行と、AU-03 の受け入れ条件「初回セットリザルト後に未登録者へ登録導線が出る」にも読み替えノートが要る(導線はリザルトではなく退室後のメニューに移る)。Q-8 を確定させるときは、E15 §2.7 の「outcome に応じたトースト」も対象になる(switched だけダイアログ)。Q-5 は §2.8 の 3 行(503・ott 失効・denied)が対象(上表の Q-5 行を参照)。
