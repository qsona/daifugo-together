# UI 文言・情報量ガイド — みんなでつくろう 大富豪

作成日: 2026-07-26 / 対象: 全画面 / 位置づけ: [デザインシステム.md](./デザインシステム.md) の姉妹編

デザインシステム.md が「**どう見せるか**(造形・色・部品)」を持つのに対し、本書は「**どれだけ言うか**(文言の量・文字と視覚の使い分け)」を持つ。値の正は design-tokens.css、見た目の正は design-system.html、**情報量の判断基準は本書**。

## 0. なぜこのガイドが要るか

DS-02 の実装で、画面に説明文を置きすぎた。開発者の指摘:

> 全般的に、文字に極力頼らない・サブテキストを不必要に入れないというふうにしたい。

原因を追うと、単なる書きすぎではなく**構造的な事故**だった。ワイヤーフレーム `wireframes.html:513` の原文はこうなっている:

> 対象はこのセットで発動したルールのみ(**§4.4**)。低評価が集まったルールは排除される(**閾値は未確定 §9-2**)。評価は人気度=優先順位にも反映(**§4.3**)。

節番号が 3 つ入っている。これはプレイヤー向けの文ではなく設計メモである。実装時に **§ 参照だけを削って、残りをそのまま画面に載せた**。つまり「これは設計メモだ」と分かる唯一の目印を消してから清書したことになる。

ワイヤーの `cap` スロットには**プレイヤー向け文言と設計メモが混在**しており、§ 参照の有無が唯一の見分けだった。ここが穴だった。

### この事故が繰り返される理由(実装者が AI の場合)

- **仕様書はテキストである。** 仕様をそのまま画面に写すのが最短経路になる。仕様の完全性を画面の完全性だと取り違える。
- **テキストは確信を持てる唯一のチャネル。** レイアウト・状態変化・演出で伝えるのは実装リスクがあり、レンダリングを見ずに書くなら「文で書けば確実に伝わる」が常に安全側に見える。
- **削るフェーズが存在しない。** 人間のデザイナーは実画面を見て文を削る。描画を見ずに一発で書くと、その工程が丸ごと抜ける。
- **説明的であることへの偏り。** 曖昧さを残さない方向に強化されているが、良い UI は逆で、**操作と繰り返しで曖昧さを解消する**ことを許容する。企画書 §4.5 の「遊んでいたらなんか発動した、というラフな体験でよい」はまさにその宣言。

**対策**: 書いたあとに実画面を 375px で描画して読み返す。文が目に入ったら、まず消せないかを疑う。

## 1. 原則

### 原則 1 — 操作対象の**上流**に説明文を置かない

ユーザーの視線はボタンや入力欄へ直行し、その手前の説明文を跳び越す。一度下流へ流れた焦点は上流に戻りにくい。さらに、**問題を経験する前の人はその問題についての情報を処理できない**([UXmatters](https://www.uxmatters.com/mt/archives/2007/03/instructional-text-in-the-user-interface-some-counterintuitive-implications-of-user-behaviors.php))。

つまりボタン群の上に置いた使い方の説明は、**書いても読まれない**。どうしても要るなら操作対象の下流に置くか、要求されたときだけ出す。

### 原則 2 — ラベルは最後の手段

「ラベル: 値」形式をやめ、ラベルを値に畳み込む。`In stock: 12` ではなく `12 left in stock`([Refactoring UI](https://refactoringui.com/previews/labels-are-a-last-resort))。書式と文脈で分かるものにラベルは要らない。ラベルが要るのは**似たデータを並べて走査させるとき**だけ。

このプロジェクトでは、図鑑の `ローカル` / `オリジナル` がラベル畳み込みの実例。逆に「このセットで発動したルールを評価」は、👍👎 が並んでいる時点で不要なラベル。

### 原則 3 — 書く前に、部品・状態・結果で伝えられないか

すべてのコンテンツは目的を持たなければならない([NN/g ヒューリスティック #8](https://www.nngroup.com/articles/aesthetic-minimalist-design/))。文を書く前に次を試す:

- **状態で伝える** — 押したボタンが塗りに変わって残る = 「送信済み」。トーストも「〜しました」も要らない。
- **結果で伝える** — 「場が流れます」と書く代わりに、場が実際に流れるのを見せる。
- **形で伝える** — 空席は破線の枠。手番は金の太枠。禁止は無効状態。
- **絵で伝える** — 3 段階の評価は文字ラベルより顔のほうが速い。

### 原則 4 — 予告しない、遅らせる

まだ起きていない結果を先に説明しない。稀にしか要らない情報は後ろの画面へ送る([progressive disclosure](https://www.nngroup.com/articles/progressive-disclosure/))。

「低評価が集まると排除される」という知識の置き場は、評価画面ではなく**ルール図鑑の「排除済み」行**(見れば分かる)と**あそびかた**。

### 原則 5 — ゲームは行動で教える

テキストのチュートリアル画面は機能しない。押してみて結果が返るほうが速い。新しい仕掛けは**段階的な遭遇を繰り返して**教える(Nintendo の定石)。最良のチュートリアルはプレイヤーがチュートリアルだと気づかないもの。

このプロジェクトでは「赤リボンが走り込む = ルールが発動した」を最初の 1 回で学習させれば、以後「ルール発動!」の文字は永久に要らない。

## 2. Do / Don't(実例)

| Don't | Do | なぜ |
|---|---|---|
| 👍👎 ボタンの上に「よかったルールには高評価、つまらなかったルールには低評価。」 | 何も置かない | 原則 1・2。ボタンが並んでいれば操作は自明で、上流の説明は読まれない |
| 「対象はこのセットで発動したルールのみ。低評価が集まったルールは排除されます。」 | 何も置かない。知識は図鑑とあそびかたへ | 原則 4。起きていない結果の予告は処理できない |
| 「評価を送信してもう1セットあそぶ」 | 「もう1セットあそぶ」。評価は押した時点で送信済み | 1 ボタン 1 動作。押した状態が残ることが確認そのもの |
| 「ルール発動!「8切り」— 場が流れます」 | リボンに「8切り」だけ。場は実際に流れる | 原則 3・5。文字は事前に分からない**ルール名にだけ**使う |
| 実況ログ「プレイヤーC: ♦8 を出した」 | 場の札山にその札を置く | 原則 3。状態そのものを見せれば実況は要らない |
| 「第1戦(3巡目)」 | 「第1戦」 | 巡目は誰の判断にも使われない。使われない情報は出さない |
| 待機画面の空席の下に「開始した時点で足りない分は AI プレイヤーが入ります。」 | 空席に「開始時にAIが入ります」のタグだけ | 席の絵の上で言えば、離れた場所の 1 行は重複 |
| 「このセットはおもしろかった?」+ 3 つの文字ラベル | 問いは残し、選択肢は顔 3 つ | 原則 3。3 段階評価は絵のほうが速い(空港の顔ボタン端末) |
| ワイヤーの `cap` を § 参照だけ削って画面に写す | § 参照が付いている文は**設計メモ**。画面には出さない | §0 の事故そのもの |

## 3. 判断のしかた

書くかどうか迷ったら、この順に。

1. **削除テスト** — その文を消したら、初見のプレイヤーが**操作に失敗する**か。失敗しないなら消す。「知らないままになる」は失敗ではない。
2. **置き場テスト** — その知識は「あそびかた」か「ルール図鑑」に置くべきものではないか。仕組みの説明(「〜されます」「〜が反映されます」)はたいていそちら。
3. **位置テスト** — 残すと決めたなら、操作対象の**下流**にあるか。上流にあるなら移すか消す。
4. **部品テスト** — 説明を置く先は `Callout` か `Dialog` の中か。画面に生の段落を置いていないか。

### 文を置いてよい場所

- **`Callout`** — 1 画面 1 枚まで。これを 2 枚使いたくなったら、たいてい設計が間違っている。
- **`Dialog`** — イエローカードのように、罰の内容と救い(「対戦はそのまま遊べます」)を必ず同じ画面に置く必要がある場面。デザインシステム.md §3.2 の規律が優先する。
- **コアコンセプトの一文**(メニュー画面)— ワイヤーで意図的に置かれた例外。プロダクトが何かを伝える 1 文は残す。

### 逆に、短くしすぎてはいけないもの

- **ルール名** — 提案ルールの名前は事前に分からないので、文字でしか伝えられない。カットインはここに全振りする。
- **アクセシブル名** — 画面に出す文字を削っても `aria-label` は削らない。顔アイコンにも「おもしろかった」を持たせる。
- **エラー文言** — 何が起きて何をすればいいかは書く。ただしその場・下流に置く。

### 文を消したぶんを別の手段で言い直したもの(2026-07-26 実施)

削除しただけでは情報が落ちる箇所は、文以外の手段で言い直した。見本は design-system.html §5-16 にある。

1. **セット評価の 3 択を顔 3 つにした** — 文字ラベル(おもしろかった/ふつう/つまらなかった)を消し、口の形だけで 3 段階を読ませる。空港の顔ボタン端末と同じ文法。選択は中立の紺で示し(明度の反転 + 拡大なので色相だけに頼っていない)、文言は `aria-label` に残した。
2. **順位行に推移を足した**(`1→1→2`)— 削除した見出し「3 戦の総合結果」が言っていたことを、書式そのものに語らせる。ゲーム間リザルト(1 戦分)では出さない。
3. **自動進行をリングにした** — 「(5 秒後に自動で進む)」という文の代わりに、ボタンの縁を一周する金のリングが残り時間を見せる。押せば即進む。

**注意点として記録**: 3 は待っているだけで画面が変わるので、時間制限に関するアクセシビリティ上の配慮が要る観点ではある(WCAG 2.2.1)。ゲームの戦間のテンポという性質上その場で押して進める逃げ道は常にあり、データを失う操作でもないため、現状は許容と判断した。時間を延ばす/止める要求が出たら再検討する。

**結論**: 既製品はどれも「良い見た目にする」か「良い文を書く」で、「そもそも文を置かない判断」を扱うものが無い。TDD のように確立した手順がある領域と違い、ここは**プロダクトごとの判断**の比重が大きいため、本書のようなプロジェクト固有のガイドを持つほうが実効性が高いと判断した。将来 `ux-writing-skill` を一般層として併用する余地はある。
