# UIライティングガイド — 何を、どう言うか

| 文書 | 受け持ち |

| デザインシステム.md | どう見せるか(造形・色・部品) |

順番が大事。**まず情報量ガイドで「書くか」を判断し、書くと決めた文にだけ本書を適用する**。本書は文を増やす理由にはならない。

値の正: 個別語の表記は §4.2 の統一表、用語は §6 の用語集が正。両方に載っていない判断は §4.1 の手順で行い、決めたら表に追記する。

## 2. 読者とプロダクトの声

### 2.1 読者

- **基本ターゲットは小4〜大人**。文章は小4で理解できる水準にする。平易な表現は大人にとっても損にならない。
- 小学校低学年も遊ぶが、「漢字が分からなくても、調べたり人に聞いたりしてなんとかして遊ぶ子」を想定する。低学年対応は初回ガイド(§8.1)が受け持ち、通常のUI文言は背伸びを許す。
- ただし、**やたらひらがなを増やさない。文中に分かち書きの空白を入れない**(企画書 §6 でもボタン等の分かち書きは禁止済み)。易しさは表記ではなく語彙で作る(§4.1)。

### 2.2 基本の声 — 「となりで進行してくれる、感じのいい大人」

本書で「声」と呼ぶのは**文体・口調**(writing voice)のこと。音声機能とは関係ない。

トーンの参照点は企画書 §2.3 の桃太郎電鉄水準(子供がメインだが、大人が読んで子供向けすぎない)。声は**プロダクト全体で1つ**。画面カテゴリごとに声を変えない。例外は §8 に列挙したものだけで、それ以外の「この画面は子供向けだから」という現場判断での声の切り替えを禁止する(現状の ProposalFormScreen.tsx:239-240 の全ひらがなCalloutのような分岐が、揺れの最大の発生源)。

基本の声の定義:

- 地の文は**やさしい敬体(です・ます)**。常体(だ・である)は使わない。
- 依頼・促しは「**〜してください**」。「〜してね」「〜しよう」「〜だよ」はガイド吹き出しの文体(§8.1)専用。→ 論点1
- プレイヤーの呼称は「**あなた**」。「きみ」はガイド吹き出しの文体専用。
- 遊び心は文末ではなく、**語の選択**(あそぶ・あがり・おかえり!)と**演出**(カットイン・イエローカード)で出す。文末で砕けなくても声は死なない。
- 祝い・イベントの短いトーストに限り「!」で感情を出してよい(「{name}が{rank}位であがり!」GameScreen.tsx:207-209、「おかえり!」App.tsx:1013)。

## 3. カテゴリ別の文体ルール

| カテゴリ | 文型 | 句点 | 長さの目安 | 参照例 |
|---|---|---|---|---|
| ボタン・リンク | 動詞の言い切り(辞書形)か体言止め。敬体にしない | なし | 12字以内 | 「あそぶ」MenuScreen.tsx:44、「もう一度ためす」RuleDexScreen.tsx:174 |
| ボタンの待機状態(disabled中の表示) | 「〜しています」「〜中…」 | なし | 15字以内 | 「ホストの開始を待っています」WaitingRoomScreen.tsx:75 |
| 状態バッジ・タグ | 名詞・体言止め。「…」を付けない | なし | 6字以内 | 「確認中」「開発中」status-labels.ts:4-5 |
| 見出し・ラベル | 体言止め | なし | — | 「招待コード」PlaySheet.tsx:63 |
| 本文・注記・空状態 | 敬体の文 | **全文に付ける** | 1文50字以内、原則2文まで | 「提案が採用されるとここに載ります。」RuleDexScreen.tsx:181 |
| トースト・フィールドエラー・プロンプト | 敬体の文 | 1文なら**なし**、2文以上なら全文に付ける | 2文まで | 「この部屋は満員です」App.tsx:1602 |
| エラー(操作が続けられないもの) | **1文目=何が起きたか、2文目=どうすればよいか**の2文構成 | 全文に付ける | — | 「部屋が見つかりません。コードをたしかめてください」App.tsx:1601(この規則では末尾にも句点が付く) |
| 確認ダイアログ | 質問は「〜しますか?」。選択ボタンは動詞の言い切り | 質問は「?」で終える | — | 「部屋から出ますか?」App.tsx:1225 |

禁止パターン: **1つのメッセージの中で依頼の文末形を混ぜない**。「接続を確認中です。少し待ってからもう一度ためしてね」(App.tsx:685)のように敬体の案内と「〜してね」が同居する形は、基本の声(ください)に揃える。

**同じ並びの表示は同じ書式で**: 同一リスト内に並ぶ項目(順位・件数・日付など)は同じ書式にする。1位だけ「1位」で2位以下が数字のみ、のような非対称を作らない。

字数はいずれも目安。文の形をとるテキストリンク(「〜だと思ったら、…」型)や目的語が必要な誘導ボタン(「みんなのルールであそんでみる」)は超過してよいが、375px 幅(情報量ガイド §0 の確認幅)で1行に収まる長さにとどめる。

## 4. 漢字とひらがな

### 4.1 判断手順(迷ったらこの順)

1. **統一表(§4.2)にあるか** → 従う。表が常に正。
2. **漢語(音読みの熟語: 提案・登録・結果・記録…)はひらがなに開かない。** 「ていあん」「けっか」のような表記は語の切れ目が消えてかえって読みにくく、交ぜ書き・全かな化は禁止。読めない心配があるなら、**表記を開くのではなく語を言い換える**(§5)。言い換えもできない語(固有のゲーム用語)は漢字のまま使い、繰り返しの遭遇で覚えてもらう(§2.1 の「背伸びする子」を信頼する)。
3. **和語(訓読みの動詞・名詞)は、操作の基本語彙だけひらがなにする。** ひらがなにしてよいのは統一表に載せた語のみ。それ以外の和語は普通の漢字表記(出す・待つ・残す・送る)。「読めるか不安だから」という理由でその場でひらがなにしない — 開きたくなったら表に追加してから使う。
4. 新しく決めた表記は統一表に追記する。表にない表記揺れを見つけたら、多数派ではなく**この手順で決め直して**表に載せる。

この手順の狙い: 「小4で読める」を配当表の照合ではなく、**難しい語は言い換える(語彙で解決)・易しい和語だけ開く(表記は最小限)**という2つの操作に落とすこと。

## 5. 語彙 — 言い換え表と残す語

### 5.1 残す語(ゲーム用語・世界観の語)

言い換えない。読めない子は聞くか調べる前提でよい(§2.1)。

- **大富豪・富豪・貧民・大貧民** — 大富豪の伝統語彙。ダークさも含めて原作の味。
- **革命・都落ち・8切り** などのルール名 — 文化そのもの。
- **発動** — カードゲーム文化で定着した語。カットインの核。
- **提案・図鑑・審判・イエローカード・異議** — プロダクトの骨格語。「異議」はサッカーの審判劇(企画書 §5.2)の小道具として残す。ただし動詞は「申し立てる」ではなく「送る」を使う(下表)。

### 5.2 言い換え表

| 現状の語 | 言い換え | 理由 |
|---|---|---|
| 異議を申し立てる(YellowCardModal.tsx:142ほか) | 異議を**送る** | 法律用語的。同モーダルのボタンは既に「異議を送る」(YellowCardModal.tsx:133)であり、動詞をそちらに揃える |
| 区分(ProposalFormScreen.tsx:263、RuleDexScreen.tsx:128) | **種類** | 行政用語的。「ローカル/オリジナル」の見出しなら種類で十分 |
| 上限を超えています(ProposalFormScreen.tsx:29) | **多すぎます** | 「上限」は抽象語。結果をそのまま言う |
| 損なう(MyProposalsScreen.tsx:21) | **成り立たなくなる** | 小4で読めない・意味も取りにくい |
| 実装(プレイヤー向け文中。MyProposalsScreen.tsx:20-26) | **開発** | ステータス語「開発中/開発できず」(status-labels.ts)と同じ工程を2つの名前で呼ばない。図鑑側は→論点5(決定済み: 登場) |
| 誤検出(YellowCardModal.tsx:142) | **間違い** | 技術用語 |
| 現在(プレイヤー向け文中。MyProposalsScreen.tsx:20) | **今** | 抽象的な漢語より日常語。表記を開くのではなく語で易しくする例(§4.1 手順2) |
| 選択しない(ProposalFormScreen.tsx:286) | **えらばない** | 「えらぶ」の統一(§4.2)に合わせる |
| 排除済み(RuleDexScreen.tsx:123ほか) | **引退** | 論点3で決定(2026-08-01)。「排除」は日常会話に出ない硬い漢語 |
| 不正な命令(提案のAI確認案内) | **わるい命令** | 初見の技術的な正しさより、提案文に混ぜてはいけないものをその場で理解できる日常語を優先する |

言い換えの一般則: 言い換え先は**具体的な結果の言葉**を選ぶ(「上限を超えた」→「多すぎる」)。抽象語を別の抽象語に替えない。

## 7. 記号・約物

- **感嘆符・疑問符は半角「!」「?」**。現状一貫しており追認。1メッセージに1個まで。「!」は祝い・イベント告知のみ(§2.2)。
- **括弧は半角「()」に統一**。→ 現状は全角・半角が混在し、同じ文言「県の記載なし」ですら RuleCard.tsx:48(半角)と MyProposalsScreen.tsx:33(全角)で割れている。!?・コロンが半角で統一されている現状に合わせ、半角に倒す。括弧の前後にスペースは入れない。
- **三点リーダーは「…」1個**(「……」にしない)。付けるのは**その場で待てば表示が変わる進行中表示だけ**(「送信中…」「読み込み中…」「考え中…」)。状態の名前であるバッジ(「確認中」「開発中」)には付けない。現状の使い分けはこの規則に合致しており追認。
- **コロンは半角+後ろ半角スペース**(「報告: 東京都」)。現状一貫しており追認。
- **並列は中黒「・」**(「有効 31・排除済み 2」)。
- **数字は半角**。助数詞は直付け(「31件」「4人」「1〜10文字」)。「31 件」のような間のスペースは入れない。
- **句点「。」**は §3 の表に従う(ボタン・ラベル・バッジ=なし / 本文=あり / トースト等=1文ならなし)。

## 8. 意図的な例外(以下に列挙したものだけ)

### 8.1 ガイド吹き出しの文体(GuideMessage)

きほんモード初戦の一言ガイド(GuideMessage.tsx:6-14)は、全ひらがな・分かち書き・「〜だよ」「〜しよう」「きみ」という**別の文体**を持つ。これはチュートリアル設計.md §4 に基づく意図的な設計であり、表記揺れとして「修正」しない。チュートリアルは子供向けに寄せてよい(2026-08-01 開発者判断)。

条件: この文体を使えるのは **GuideMessage 部品の中だけ**。1文以内・初回遭遇の各1回のみ(チュートリアル設計の制約)。他の画面・部品でこの文体を真似ることを禁止する。現状 ProposalFormScreen.tsx:239-240 と proposal/client.ts:89 がこれに似た全ひらがな文体を使っているが、これらはガイドではないので基本の声に戻す(§10)。

分かち書きと開発者制約の衝突は → 論点2。

### 8.2 ステータス語「あそべる」「開発できず」

status-labels.ts:6 の「あそべる」は、体言止めが並ぶ中で1語だけ動詞形だが、2026-07-29 の設計(my-proposals-status-readability-design.md)で「結果そのものを言う」ために意図的に採用された語。同 status-labels.ts:8 の「開発できず」(動詞否定形)も、同設計で「開発中」に語を揃えるために選ばれており、いずれも §3 の名詞バッジ規範の例外として直さない。同様の例外を新設するときは、同ドキュメントのように**理由を設計文書に残すこと**を例外の成立条件とする。

## 9. 論点(全5件・決定済み)

**決定記録**: 2026-08-01、開発者が論点1〜5をすべて下記の推奨どおり採用した。以下の各論点は、判断の経緯の記録として推奨の書き方のまま残す。

1. **依頼の文末形: 「〜してください」に統一(推奨)か、「〜してね」に統一か。**
   現状は「ください」系が多数派(エラー・案内の大半)だが、「ね」系も7箇所ある(App.tsx:685, 694ほか、PlaySheet.tsx:52)。推奨は「ください」。理由: (a)「です」の地の文と混ぜても違和感がなく、§3 の混在禁止が機械的に運用できる、(b) 大人が読んでも幼くない(桃鉄水準は文末ではなく語彙と演出で作れる)、(c)「ね」を選ぶと却下理由・審判まわりの深刻な場面だけ「ください」に戻したくなり、例外が増える。「ね」の温かみはガイド吹き出しの文体(§8.1)が引き受ける。
2. **GuideMessage の分かち書きを維持するか。**
   開発者制約「文中に空白を入れない」と、チュートリアル設計 §4 の分かち書きガイド文が衝突している。推奨は**維持(例外として明文化)**。理由: 対象が文字を読み始めたばかりの子で、表示は一瞬のToast・1文のみという極端に限定された文脈であり、分かち書きの読み上げ補助が最も効く場面だから。制約の本意は「通常UIに分かち書きを広げない」ことと解釈し、§8.1 の「GuideMessage限定」で封じ込める。廃止する場合の代替は、通常表記+ふりがな(ruby)化(チュートリアル設計 §4 の「ふりがな付き」と両立するが、実装コストが増える)。
3. **「排除済み」を「引退」に変えるか。**
   推奨は**「引退」に変更**(フィルタ・タグ・詳細の3箇所+「低評価が集まったため排除」RuleDexScreen.tsx:191 →「低評価が集まって引退」)。配当で言えば「排」は中学配当、「除」「退」は小6配当なので、配当上の差は決め手にならない(§4.1 のとおり本書は配当照合を規範にしない)。決め手は**頻度**: 「引退」は野球・サッカーの報道などで日常的に目にする語で、意味を文脈ごと知っている子が多いのに対し、「排除」は日常会話にほぼ出ない硬い漢語。加えてサッカー(審判・イエローカード)のスポーツ世界観とも揃う。現状維持(ゲーム用語として教える)も成立はするが、頻出のわりに世界観上の見返りが「大貧民」ほどない。
4. **「(変更不可)」を消すか。**
   WaitingRoomScreen.tsx:59 のコメントは「ルールセットは選べないので『変更不可』は書かない」と明記する一方、ActiveRulesScreen.tsx:31 と ActiveRulesModal.tsx:27 は「（変更不可）」を表示しており矛盾している。推奨は**削除**して「◯件・すべての卓に適用」とする。理由: 変更UIが存在しない画面で禁止を予告する必要はなく(情報量ガイド 原則4)、コメントに残る設計意図とも一致する。
5. **図鑑の「実装済みルール」「実装日」をどうするか。**
   マイ提案側の「実装」→「開発」統一(§5.2)は推奨確定でよいが、図鑑サマリ(RuleDexScreen.tsx:161-163)と詳細の「実装日」(RuleDexScreen.tsx:237)が残る。工程名に揃えて「あそべるルール ◯件」とする案は採らない — この集計は排除済み(引退)のルールを含むため、「あそべる」と書くと嘘になる。つまり図鑑サマリが数えているのは工程の状態ではなく**「図鑑に載った」という出来事**であり、§6 の「同じ工程を2つの名前で呼ばない」には当たらない(呼ぶ対象が別)。そこで掲載の出来事を指す語として**「登場したルール ◯件」「登場日」**を推奨する(図鑑=登場する場所というメタファーで、桃鉄トーンにも合う)。現状維持でも矛盾はしないため優先度は低い。

## 11. 運用

### 11.1 新規文言のチェックリスト(書いたら5問)

1. **量**: そもそも書く必要があるか(情報量ガイド §3 の削除テストを先に通したか)。
2. **声**: 敬体+「ください」になっているか。「ね/だよ/きみ」を使っていたら、それは GuideMessage の中か。
3. **表記**: 統一表(§4.2)の語と食い違っていないか。漢語を開いていないか。分かち書きの空白がないか。
4. **語彙**: 小4が読めなさそうな語はないか。あるなら、ひらがなにするのではなく §5.2 の方針で言い換えたか。用語は §6 の正式表記か。
5. **記号と重複**: !?()は半角か。「…」は進行中表示だけか。句点は §3 のとおりか。同じ文言が既にコードにないか(あれば定数を共有)。

### 11.2 レビュー時の観点

- 差分に日本語リテラルが含まれるPRでは、上のチェックリストをそのまま観点にする。
- 統一表・用語集にない新しい語・表記が入っていたら、「多数決」ではなく §4.1 の手順で決めて**本書の表を更新する**ことをマージ条件にする(表が更新されない限り、次の揺れが必ず起きる)。
- ルール名・説明文などAIが動的に生成する文言(rules_repository経由)は本書の表を生成プロンプト側の規範として参照させる(§6 の用語・§7 の記号)。

### 11.3 文言の一元管理

同一文言のハードコード重複が既に多数ある(棚卸しで確認されたもの: 「うまくいかなかったみたい。〜」5箇所 / 「評価を送れませんでした。〜」2箇所 / 「提案一覧を取得できませんでした」2箇所 / 「友だちの部屋にはいる」2箇所 / 「ルールをていあんする」3箇所(MenuScreen.tsx:47 含む) / 「ルールの区分」「ルール名」「ルールの内容」各2箇所)。表記統一のたびに一部だけ直る事故を防ぐため:

- **繰り返し使うメッセージ(エラー・リトライ促し)は定数モジュールに集める**(例: `packages/web/src/messages.ts`)。i18n基盤の導入までは不要。まず重複が確認済みの上記から着手する。
- 称号(大富豪〜大貧民)が `core/game/types.ts:15-18` と `core/snapshot/snapshot.ts:16-19` で二重定義されている点も、文言変更時の取り残しリスクとして同様に扱う。
