## 1. Epic 概要

### 1.1 目的

招待コード文化(E03)では、再訪は「集まれるか」で決まる。現状は同卓した相手との関係がセッション終了とともに消え、毎回コードを外部連絡手段で配り直す集合コストが再訪の摩擦になっている(施策提案 §3 Why)。本 Epic は「もう一度この人たちと遊ぶ」コストを下げる。

1. **フレンド成立**: 同卓した相手・現実で連絡を取れる相手と、相互承認でフレンドになれる。
2. **再会の導線**: 部屋への誘い(通知でワンタップ入室)・リマッチ・オンライン表示。
3. **コアループ接続**: フレンドの提案ルールが見える(「フレンド◯◯の提案」バッジ)。友達のルールを遊んで評価する二次的な当事者性を生む。

同時に、子供メインターゲットのため「知らない人と繋がる経路を構造的に作らない」ことを絶対条件とする(§2.1)。

## 2. 技術仕様

### 2.1 【原則】子供安全: 知らない人と繋がる経路を構造的に作らない

個別の悪用対策(§2.8)より先に、**設計の形そのもの**で次を保証する。以後の全仕様・全実装はこの表に反してはならない。

| # | 構造的保証 | 実現方法 |
|---|---|---|
| 1 | フレンドになれるのは「実際に同卓した人」か「現実でコードを伝え合える人」だけ | 成立経路が FR-D1 の 2 つしか存在しない。ユーザー検索 API・おすすめ生成・公開プロフィール画面を**作らない**(FR-D2)。該当エンドポイント自体が存在しないので、UI の消し忘れでは破れない。**残余リスク**: 本人がフレンドコードを SNS 等で公に晒せば未知の他者から申請が届きうる — これは構造では塞げないため、承認制・コード再生成・申請レート制限(§2.8)で緩和する |
| 2 | 同卓自体が招待コード(5 桁・非公開)経由でしか起きない | E03 の実装済み構造。公開マッチングは E03 §1.3 でスコープ外のまま |
| 3 | フレンド間でも自由文の対人コミュニケーションが存在しない | チャット無し(FR-D2)。誘い・申請・承認はすべて**定型アクション**で、ユーザーが入力した自由文が相手に届く経路がない(表示名は E03 実装済みのサーバー側正規化 1〜10 文字のみ) |
| 4 | 個人を特定できる情報が相手に渡らない | 配るのは表示名とオンライン状態だけ。`userId`・Google 情報(E15 AU-D5 でそもそも `sub` 以外取得しない)・メール(非取得)・プレイ統計は配らない |
| 5 | 望まない接触を本人が止められ、止めたことが相手に伝わらない | 承認制・ブロック(§2.8)。拒否・ブロックの事実は相手に通知しない(報復の火種を作らない) |
| 6 | 通知が接触の増幅器にならない | 誘いの頻度上限(§2.8)+ E17 の夜間 Push 抑止(WP-D5)+ Push 既定 OFF(WP-D3/§2.3) |

### 2.2 データモデル

E15 §2.2 適用後(`users.google_sub` あり)を前提とし、既存の起動時マイグレーション方式(`persistence.ts` の `CREATE TABLE IF NOT EXISTS` + `PRAGMA table_info` 列追加)に従う。

```sql
-- フレンドコード(登録済みユーザーが初めてフレンド画面を開いたときに採番。再生成可)
ALTER TABLE users ADD COLUMN friend_code TEXT;
CREATE UNIQUE INDEX IF NOT EXISTS idx_users_friend_code
  ON users(friend_code) WHERE friend_code IS NOT NULL;

-- 申請と成立(方向つき。requester → addressee)
CREATE TABLE IF NOT EXISTS friendships (
  id           TEXT PRIMARY KEY,
  requester_id TEXT NOT NULL REFERENCES users(user_id),
  addressee_id TEXT NOT NULL REFERENCES users(user_id),
  status       TEXT NOT NULL CHECK (status IN ('pending', 'accepted', 'declined')),
  created_at   INTEGER NOT NULL,
  responded_at INTEGER,
  UNIQUE (requester_id, addressee_id)   -- 存命行がある間の再申請不可(FR-D6)を DB 制約で担保(下記の行削除仕様と対)
);
CREATE INDEX IF NOT EXISTS idx_friendships_addressee
  ON friendships(addressee_id, status);

-- ブロック(方向つき・フレンド状態と独立)
CREATE TABLE IF NOT EXISTS friend_blocks (
  blocker_id TEXT NOT NULL REFERENCES users(user_id),
  blocked_id TEXT NOT NULL REFERENCES users(user_id),
  created_at INTEGER NOT NULL,
  PRIMARY KEY (blocker_id, blocked_id)
);

-- 部屋への誘い(頻度上限の台帳 + 通知の冪等キー元)
CREATE TABLE IF NOT EXISTS room_invites (
  id           TEXT PRIMARY KEY,
  room_id      TEXT NOT NULL,            -- プロセス内 Map の roomId(部屋消滅で自然失効)
  invite_code  TEXT NOT NULL,            -- E03 の 5 桁コード(入室はこれで行う)
  from_user_id TEXT NOT NULL REFERENCES users(user_id),
  to_user_id   TEXT NOT NULL REFERENCES users(user_id),
  created_at   INTEGER NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_room_invites_pair
  ON room_invites(from_user_id, to_user_id, created_at);
```

- 承認済み決定の「`friendships`(申請中/成立/ブロック)」は、実装上は **`friendships` + `friend_blocks` の 2 テーブルに正規化**する。ブロックは方向を持ち、成立前後いずれでも掛けられる独立の状態のため、`status` に混ぜると遷移が曖昧になる(決定の意味は変えない実装詳細)。
- 「同一相手への再申請不可」(FR-D6)は、**`pending`/`declined` の存命行がある間の制約**と定義する。`declined`・`pending` の行は消さずに残すことがその実体である(UNIQUE 制約)。逆方向(B→A)の申請は別行として可能 — 「向こうからの申請なら受けたい」を自然に許す。
- **フレンド解除は `accepted` 行を削除し、以後の再申請を可能にする**(仲直り経路を意図的に残す。裁定済みデフォルト — 塞ぐ選択肢は FR-T5)。解除→即再申請のスパムは申請レート制限と承認制(§2.8)で抑止される。成立済みフレンドへのブロックも同様に `accepted` 行を削除する(関係解消。ブロック解除後も自動復活せず、再申請から)。
- 「フレンドである」の定義は「どちらかの方向に `accepted` 行があり、かつ両者間に `friend_blocks` 行がない」。ブロックはフレンド表示・誘い・バッジのすべてを両方向で止める(§2.8)。
- **放棄された匿名行(E15 AU-D3)にフレンド関係が付くことは構造的に無い**: 申請・承認とも登録済み(`google_sub IS NOT NULL`)必須(FR-D4・§2.4 のゲート)であり、放棄される行は定義上未登録の匿名行だからである。一方、E15 §2.4 の分岐 2/4(別アカウント切替)では**同一人物が複数の登録済みアカウントを持ちうる**ため、フレンド一覧に同じ人の別アカウント(別表示名)が並ぶことはありうる。家族の端末共有ケースの自然な帰結として許容する(名寄せはしない)。
- `room_invites` は招待の**記録**であり、入室権限ではない(入室は従来どおり `room:join` + 招待コード。部屋が破棄済みなら通常の `ROOM_NOT_FOUND`)。行削除は不要(部屋がプロセス内メモリなので、行が残っても無害)。

### 2.3 フレンド成立フロー

**(1) 同卓履歴からの申請(結果画面)** — E03 の「他メンバーの `userId` 非配信」原則(§2.3)を守るため、クライアントは相手を**部屋ローカルの `memberId`** で指す。

1. セットリザルト画面(部屋の `setResult` フェーズ中。部屋はまだ生きている)で、同卓の人間メンバー(`isAI: false`・自分以外)に「フレンド申請」ボタンを出す。
2. `POST /api/friends/requests` body `{ via: 'seat', roomId, memberId }`。サーバーは `RoomManager` から当該部屋を引き、`memberId → userId` を**サーバー内で**解決して申請行を作る。申請者がその部屋のメンバーであることを検証する(他室の memberId は指せない)。
3. 相手には通知 `friend_request`(§2.5)とフレンド画面の「承認待ち」リストで届く。承認(`accepted`)で成立、拒否(`declined`)は**申請者に通知しない**(§2.1-5)。
4. 申請ボタンの活性はサーバーが返す**申請可否フラグ**(`canRequest: boolean`。ビューの各メンバーに付与)に従う。不可の理由(相手が未登録/ブロック関係/申請済み/上限)は**開示しない**(登録状況やブロックの存在を悟らせない)。自分が未登録の場合はボタンの代わりに E15 の登録導線(AU-03 と同じ流儀)。

対象は「セットを完走した人間メンバー」である。**注意**: 実装上、途中離脱者は `departed: true` のまま `setResult` 中も `members` に残っており、除去されるのは次セット開始時である(2026-07-29 に `room/reducer.ts` で確認)。したがって申請ボタンの出し分け(`canRequest` 算出)とサーバー側の申請検証の**両方で `departed`(および `isAI`・本人)を除外**する — 完走した相手にだけ申請できる。これは仕様とする。

**(2) フレンドコード交換**

1. フレンド画面に自分のコードを表示(コピー可)。「あたらしいコードにする」で再生成(旧コード即失効。FR-D6)。
2. `POST /api/friends/requests` body `{ via: 'code', friendCode }`。以降は (1) と同じ承認フロー。自分のコード宛は 400。存在しないコードは「コードが見つからない」の 1 種類のエラーのみ返す(失効・ブロックを区別して開示しない)。

### 2.4 HTTP API

既存 `app-server.ts` のハンドラ連鎖(`handleProposal` 等)と同型の `handleFriends` を追加する。認証は既存 Bearer。**全エンドポイントの先頭で登録確認(未登録は 403 `registration_required`。E15 §2.6 と同語彙)**。

| エンドポイント | 役割 |
|---|---|
| `GET /api/friends` | フレンド一覧(表示名 + オンライン状態 §2.6)+ 承認待ち(受信)一覧 + 自分のフレンドコード(未採番なら採番) |
| `POST /api/friends/requests` | 申請(§2.3 の 2 経路)。レート制限・再申請不可・上限超過は 429/409 |
| `POST /api/friends/requests/:id/accept` / `:id/decline` | 受けた申請への応答 |
| `DELETE /api/friends/:friendUserId` | フレンド解除(`accepted` 行を削除。相手に通知しない。以後の再申請は可能 — §2.2) |
| `PUT /api/friends/blocks/:userId` / `DELETE 同` | ブロック / 解除。ブロック対象はフレンド・申請中・同卓相手(memberId 経由でも指定可)に限る — **無関係の任意ユーザー ID を探索的にブロックする口にしない** |
| `POST /api/friends/invites` | 部屋への誘い(§2.5)。body `{ toFriendUserId }`。自分が waiting 中の部屋にいることをサーバーが確認する |
| `GET /api/friends/rule-badges?ruleIds=…` | 指定ルールのうちフレンドの提案分を `{ ruleId, friendDisplayName }` で返す(§2.7) |

- レスポンスでフレンドを指す ID は `user_id` そのものを使う(フレンド成立 = 相互承認済みの関係であり、E03 が `userId` を隠す理由(無差別な追跡材料)は成立後の相手には当たらない。ただし**成立前・部屋内の相手は引き続き `memberId`** で指す)。なお、成立後も `user_id` を露出せず関係スコープの不透明 ID(`friendshipId`)で代替する選択肢がある — 採否は FR-02 実装レビューの論点とする。

### 2.5 通知(E16 レジストリへの登録)

E16 §2.2 の拡張点仕様に従い、種別レジストリへ次を登録する。3 種別とも E16 §2.2 の一覧に予約済みで、本 Epic がレジストリエントリを実装する(E16 の表の読み替えは §4.2)。

| 種別コード | 意味 | 対象 | チャネル | 優先度 | payload / タップ遷移 |
|---|---|---|---|---|---|
| `friend_invite` | フレンドの部屋への誘い | 誘われた人 | センター+Push(E17 後) | 高 | `{ fromDisplayName, inviteCode, roomInviteId }` / タップで `room:join(inviteCode)` を実行し待機画面へ(**ワンタップ入室**)。**受け手が別の部屋に在室中**(E03 の 1 ユーザー 1 部屋。`setResult` 残留中を含む)なら、「いまの部屋を出て ◯◯ の部屋に入る?」の確認を挟み、承諾で `room:leave` → `room:join` を合成実行する(キャンセルなら何もしない)。部屋消滅済み・満員なら通常のエラートースト |
| `friend_request` | フレンド申請が届いた | 申請された人 | センターのみ | 中 | `{ fromDisplayName, friendshipId }` / フレンド画面(承認待ち) |
| `friend_accepted` | 申請が承認された | 申請した人 | センターのみ | 中 | `{ friendDisplayName }` / フレンド画面 |

- 冪等キー(E16 §2.3 `dedupe_key`): `friend_invite` = `roomInviteId`、`friend_request`/`friend_accepted` = `friendshipId`。
- payload は表示名以外の個人情報を含めない(E16 §2.2 のペイロード規律。Push 文面と共通)。**拒否・ブロック・解除の通知種別は作らない**(§2.1-5)。
- Push(E17)側: 種別ごとの設定は持たない。E18 で `friend_invite` を `center_push` としてレジストリへ登録すると、Push 購読済みの端末は自動的に送信対象になる。追加の Push API・設定 UI・個別確認は作らない(E17 §2.3 の 2026-08-02 改訂)。
- 発行は誘い・申請・承認の各 API ハンドラ内から `NotificationService.publish()`(E16)を呼ぶだけで、センター保存・Socket.IO 配信・(E17 後の)Push 送信は E16/E17 の基盤に乗る。

### 2.6 オンライン表示

新規インフラなし(FR-D7)。表示は 3 値で、`GET /api/friends` の取得時スナップショットのみ(リアルタイム購読はしない — フレンド画面を開き直せば足りる。必要が観測されたら §5)。

| 状態 | 判定(実装済み機構の流用) |
|---|---|
| プレイ中 | `RoomManager.findByUser(userId)` が部屋を返し、その `phase` が `playing` |
| オンライン | `socket-gateway.ts` の `activeByUser` に接続がある |
| オフライン | 上記いずれでもない |

`activeByUser` は現在 `attachRoomSocketGateway` のクロージャ内にあるため、gateway の戻り値(`RoomSocketGateway`)に在席照会の口(`presenceOf(userId)`)を追加し、`bin.ts` で `handleFriends` へ配線する(§4.1)。オンライン状態を見られるのは**成立済みフレンドのみ**(ブロック関係があれば常にオフライン表示)。

### 2.7 リマッチと提案バッジ

**リマッチ(セット終了画面「この卓のフレンドと再戦」)**: 同卓メンバーに成立済みフレンドがいるときだけ表示。押下でクライアントが (1) `room:leave` → (2) `room:create` → (3) 同卓フレンド全員へ `POST /api/friends/invites` を順に実行する(既存プリミティブの合成。サーバーに複合 API は作らない — E03 の 1 ユーザー 1 部屋制約 `ALREADY_IN_ROOM` を leave で先に解消する)。誘われた側には通常の `friend_invite` が届く。**受け手側の導線**: E16 §2.7 によりベルは対局系画面(待機・対局・リザルト)に置かれないため、旧部屋の `setResult` に残留中の受け手はその場では通知に気づけない — 気づくのは「ホームへ」で部屋を出た後で、そのとき在室中ならタップ時の確認 → leave → join(§2.5)で合流する。したがって**リマッチの主導線はセット終了画面のボタン(送り手側)であり、誘い通知は部屋の外にいる受け手が主対象**という役割分担になる。

**提案バッジ(「フレンド◯◯の提案」)**: `rules.proposal_id → proposals.author_id`(実装済みスキーマ)とフレンド関係の突き合わせで判定する。表示箇所はルール一覧(図鑑・有効ルール)とセット評価画面(発動ルールの投票行)。対局内ビュー(E03 §2.3: ルールは ID と名前のみ配信)には**手を入れず**、クライアントが画面表示時に `GET /api/friends/rule-badges?ruleIds=…` で注記だけ取得して重ねる。フレンドでない提案者の表示名はこの API からは一切返さない(公開プロフィールを作らない原則の帰結。全員向けの提案者表示は C-2/E19 の領分)。

### 2.8 悪用・スパム対策(FR-D6 の具体化)

| 対策 | 仕様 |
|---|---|
| 承認制 | 申請は相手の明示的な承認まで `pending`。承認するまで申請者には何の権限も生じない |
| 再申請不可 | 同一相手(同一方向)への申請は、`pending`/`declined` の行が残っている間は不可(`UNIQUE(requester_id, addressee_id)`)。フレンド解除・関係解消後は行が消えるため再申請できる(仲直り経路。§2.2)— 解除→即再申請の往復スパムは下のレート制限と承認制が抑止する。拒否されても「拒否された」ことは分からない(申請側の表示は出しっぱなしにしない — 申請直後の完了トーストのみで、以後「承認待ち一覧」を申請側には見せない) |
| 申請レート制限 | ユーザー単位・時間窓(既定値は FR-T3)。実装は既存 `FixedWindowRateLimiter`(`room/rate-limit.ts`)の流用 |
| ブロック | どちらか一方でも `friend_blocks` にあれば: フレンド表示・誘い・バッジ・オンライン状態がすべて両方向で消え、**以後の同卓時も結果画面の申請ボタンが互いに非表示**(`canRequest: false`。理由非開示)。ブロックした事実は相手に通知しない |
| 誘い頻度上限 | 同一相手への `friend_invite` は時間あたり N 回(既定値は FR-T4)。超過は API 側 429(E16 に汎用レート属性は足さない — E16 NC-T4 と同じ「発行側で個別制御」の整理) |
| コード再生成 | フレンドコードは何度でも再生成でき、旧コードは即失効(晒し対策)。成立済みのフレンド関係には影響しない |
| フレンド数上限 | 成立数に上限(既定値は FR-T2)。無差別収集の抑止と一覧 UI の破綻防止 |

### 2.9 E15 前の先行分(FR-01: 端末ローカルの同卓履歴)

- クライアントのみで完結する。セットリザルト表示時に、同卓した人間メンバーの表示名を localStorage(`daifugo.recentPlayers`)へ `{ displayName, lastPlayedAt, count }` で記録(自分と AI は除く)。`userId`・`memberId` は保存**しない**(memberId は使い捨てで意味がなく、userId はそもそも配信されない。E03 §2.3)。
- メニューから開く「さいきん いっしょに あそんだ人」一覧に表示するだけで、**タップしても何も起きない**(申請 UI の布石。E15 後、この場所が「フレンド」画面に置き換わる)。
- 表示名は永続 ID ではない(改名で追えなくなる)が、表示専用なので許容。保持期間・件数の既定値は FR-T6。サーバー・DB への変更はゼロ。

### 2.11 テスト戦略

- リポジトリ/API 単体: 申請の 2 経路・承認/拒否・存命行への再申請拒否(UNIQUE)と解除後の再申請成功(§2.2)・双方向ブロックの全遮断(一覧/誘い/バッジ/オンライン/`canRequest`)・`departed` メンバーへの申請拒否(§2.3)・未登録 403・レート制限 429・フレンド数上限・コード再生成で旧コード失効・`memberId` 解決の部屋所属検証(他室の memberId 拒否)。
- 通知結合: 誘い→ `friend_invite` が E16 センターに 1 件(冪等キー)・頻度上限超過で発行されない・拒否/ブロックで通知が出ないこと。E17 の FakePushTransport 結合は E17 実装後に追加(チャネル属性で自動送信されることの確認)。
- クライアント: FR-01 の localStorage 記録と表示(AI・自分の除外)・結果画面の `canRequest` 出し分け(`departed` 除外を含む)・誘い通知タップ→入室(在室中の確認 → leave → join、キャンセル時の現状維持を含む)・リマッチの leave→create→invite 連鎖・375×812 の実画面で導線一式を目視確認(既存 Epic と同じ検証水準)。

## 3. ストーリー詳細・受け入れ条件

### FR-01: 最近いっしょに遊んだ人(端末ローカル・E15 前)

「プレイヤーとして、この前いっしょに遊んだ人の名前をあとから思い出したい」

受け入れ条件:

- [ ] セット完走時に同卓した人間プレイヤーの表示名が localStorage に記録される(自分・AI は記録されない)
- [ ] メニューから履歴一覧が開け、直近に遊んだ順で表示される(タップしても操作は発生しない)
- [ ] サーバー・DB への変更が一切ない(通信・スキーマ差分ゼロ)
- [ ] localStorage が使えない環境でもプレイに影響しない

### FR-02: フレンド申請・承認・一覧・コード・ブロック

「いっしょに遊んで楽しかった人と、また会える関係を残したい。嫌な相手は自分から見えなくしたい」

受け入れ条件:

- [ ] 結果画面から同卓の人間メンバーに申請でき、相手の承認で成立する。`userId` がクライアントに渡らない(申請は `memberId` 経由。E03 §2.3 の非配信原則が保たれる)
- [ ] フレンドコードで申請でき、コードの再生成後は旧コードで申請できない
- [ ] 承認待ち・拒否済みの相手への再申請ができない。フレンド解除後は再申請できる(§2.2 の仲直り経路)。拒否は申請者に通知されず、申請者からは未応答と区別がつかない
- [ ] 未登録ユーザーはフレンド API が 403 `registration_required` になり、UI はログイン導線を出す
- [ ] ブロックすると、以後の同卓時も互いの申請ボタンが出ず、一覧・オンライン状態からも互いに消える。ブロックした事実は相手に通知されない
- [ ] 申請レート制限・フレンド数上限が機能する(既定値は §6)

### FR-03: 部屋への誘いとオンライン表示

「部屋を立てたとき、コードを配り直さずにフレンドを呼びたい。誘われた側はワンタップで入りたい」

受け入れ条件:

- [ ] waiting 中の部屋からフレンドに誘いを送ると、相手の通知センター(E16)に `friend_invite` が届き、タップだけで待機画面に入室する
- [ ] 受け手が別の部屋に在室中(`setResult` 残留中を含む)にタップした場合、「いまの部屋を出て入る?」の確認を経て leave → join で合流できる。キャンセルなら現状維持で、`ALREADY_IN_ROOM` エラーがユーザーに露出しない
- [ ] 部屋が消滅・満員のときは既存のエラー表示に合流し、アプリが壊れない
- [ ] 同一相手への誘いが頻度上限で止まる。同一の誘いが通知に二重に積まれない(冪等キー)
- [ ] フレンド一覧にプレイ中/オンライン/オフラインが表示される(ブロック関係では常に見えない)
- [ ] E17 未実装の環境で Push が送られず、センターのみで完結する(E17 実装後は E18 側の変更なしで Push が乗る)

### FR-04: リマッチと「フレンド◯◯の提案」バッジ

「この卓が楽しかったから、同じフレンドとすぐもう一度遊びたい。友達が作ったルールなら遊んで応援したい」

受け入れ条件:

- [ ] セット終了画面に同卓フレンドがいるときだけ「この卓のフレンドと再戦」が出て、押すと新しい部屋が立ち、同卓フレンド全員に誘いが届く
- [ ] 旧部屋の `setResult` に残留中の受け手が、部屋を出たあと通知から(在室中なら確認 → leave → join を経て)新しい部屋に合流できる(§2.7 の受け手側導線)
- [ ] ルール一覧(図鑑・有効ルール)とセット評価画面で、フレンドの提案ルールに「フレンド◯◯の提案」バッジが付く
- [ ] フレンドでない提案者の表示名はバッジ API から取得できない
- [ ] 対局中の画面(E03 の配信ビュー)には変更がない(バッジは HTTP での後付け注記)
