## 1. Epic 概要

### 1.1 目的

増えていくルールをプレイヤーが把握できる 2 つの閲覧面を提供する(企画書 §4.5)。

- **卓の有効ルール一覧(RV-01)**: 対局前・対局中に「いま何が発動しうるか」だけをラフに確認する。ルール名だけの軽い表示。
- **ルール図鑑(RV-02)**: これまで実装された全ルールを、区分・状態・人気度・優先度つきで眺める資産カタログ。

企画書 §4.5 が定めた温度差 —— **対局まわりはラフに、図鑑はちゃんと** —— をそのまま 2 画面の責務分割にする。「遊んでいたらなんか発動した」という体験を壊さず、確認したい人だけが図鑑へ降りていける導線を置く。

### 1.2 担当ストーリー

| ID | 概要 | フェーズ | 依存 |
|---|---|---|---|
| RV-01 | 卓の有効ルール一覧(ルール名のみ・優先順位順・図鑑導線) | 2 | CX-05 |
| RV-02 | ルール図鑑(フィルタ・排除済み表示・詳細・人気度/優先度) | 2 | CX-05 |

いずれも段階成立を前提とする。RV-01 は PR-01 完了前は順序なしで、RV-02 は PR-01/PR-02/EV-03 完了前は該当表示なしで、それぞれ受け入れ条件を満たす(バックログ §4「並び順の設計意図」)。

### 1.3 他 Epic との接続

| 接続先 | この Epic が前提にすること |
|---|---|
| **E1(ゲームエンジン)** | ルールレジストリがセット開始時に固定する「有効ルールの優先度降順チェーン」(E12 §4.6(3))。RV-01 はこの固定結果を表示する。スナップショットに含める公開情報の確定(E12 §4.3 が E1/E3 に委譲)に、RV-01 用の有効ルール一覧を含める(§5.1) |
| **E9(優先度・人気度: PR-01/PR-02)** | RV-01 は優先度を**並び順にのみ**使う(数値非表示)。RV-02 は優先度・人気度を**数値表示**する。どちらも PR 完了までは非表示で成立する段階実装(§2.4) |
| **E8(評価・淘汰: EV-03)** | RV-02 の「排除済み」状態。排除されたルールも図鑑から消さず残す。排除の発生は EV-03 完了後(§2.4) |
| **E5/E7(提案・実装)** | 図鑑・一覧が読むルールメタデータ(名称・説明・区分・状態・優先度・人気度)は E5/E7 のパイプラインが書き込む(E12 §4.4)。保存済み都道府県は公開 API に残るが、RV-02 は表示・絞り込みに使わない。説明文の出どころは §3.2(d) で決定 |

**この Epic はすべて読み取り専用**である。ルールメタデータの生成・更新(状態遷移・人気度算出・優先度更新)は E5/E7/E8/E9 の責務であり、E11 はその結果を表示するだけに徹する。書き込み経路を一切持たないことで、閲覧機能が本体の整合を壊すリスクをゼロにする。

## 2. Epic 横断の技術仕様

### 2.1 【決定】ルール表示データの 2 つのソース

閲覧面が 2 つあるのに対応して、データソースも 2 つに分ける。**同じ「ルール一覧」でも、卓の有効ルール(RV-01)と図鑑(RV-02)は別ソースから取る**。

| 閲覧面 | ソース | 理由 |
|---|---|---|
| **卓の有効ルール一覧(RV-01)** | **卓のスナップショット(WebSocket ルーム状態)** | セット開始時に固定された有効ルール集合(E12 §4.6(3))を反映する必要がある。図鑑 API(=グローバル最新)を叩くと、セット中に別の卓や運用で排除・追加が起きたときに**その卓で実際に発動する集合とズレる**。卓で「何が発動しうるか」の唯一の正はサーバーが固定したスナップショットである |
| **ルール図鑑(RV-02)** | **HTTP API(`GET /api/rules`)** | 卓に紐づかないグローバルな全実装済みルールのカタログ。フィルタ・ページング・ソートを伴う read。WebSocket ではなく素の HTTP リクエストが素直(E12 §3 の HTTP API 層) |

この分離が本 Epic の設計上の要点である。**卓の一覧は「この卓で固定された集合」、図鑑は「グローバル最新の全集合」**であり、両者が食い違うのは仕様どおり(§3.1(b) の整合ケースで詳述)。

#### スナップショットへの追加(E1/E3 へ確定を委譲)

RV-01 のために、卓の状態に有効ルールの公開リストを含める。E12 §4.3 は「スナップショットに含める公開情報の確定は E1/E3 で行う」としており、そこへ次を追加する(§5.1 の修正提案):

```ts
// 卓の状態(スナップショット)に含める公開フィールド
activeRules: Array<{ id: string; name: string }>;
// サーバー側で優先度降順に整列済み(PR-01 完了後)。PR-01 前は安定順(ルール登録の古い順)。
// name はユーザー入力(サニタイズ済み。§2.5)。クライアントは並べ替えず順序どおり表示する。
```

**配信タイミング**: `activeRules` は次の 3 契機でイベント配信する。

1. **卓参加時**: 初期配信(待機中に参加したら現時点のグローバル有効ルールのプレビュー、対局中に再接続したら固定済みセット)。
2. **待機中のルール変動時**: セット未固定の待機画面では、グローバル有効ルールがリリース・排除で変わりうるので、変動のたびにプレビューを更新する(§3.1(b) の待機中追随)。
3. **セット開始時**: この時点で有効ルールが固定され、以降そのセット中は不変(E12 §4.6)。

**手番ごとの状態スナップショットには含めない** —— 対局中(固定後)は静的で再送不要であり、静的データを毎手番送るとルール数増加でメッセージが肥大するため。この配信方針は E12 §4.3 の全量スナップショット方針への補足として §5.1 に挙げる。クライアントは受け取った `activeRules` を保持し、画面4 はそれを表示する。

### 2.2 図鑑一覧 API(RV-02)

読み取り専用・認証不要(ユーザー固有データを含まない公開カタログ)。公開の読み取り API として、一般的な DoS・スクレイピング対策の IP ベースのレート制限を併設する(E12 §4.9 の提案系 API 濫用対策とは目的が異なり、ここは公開 read そのものの保護)。

```
GET /api/rules
```

**クエリパラメータ**(すべて任意。省略時は「すべて」):

| パラメータ | 値 | 既定 | 備考 |
|---|---|---|---|
| `status` | `active` / `removed` / 省略 | すべて | 無効(一時無効化=DB `disabled`)は初期スコープ外。**初期は `GET /api/rules` の結果に含めない**(§5.2) |
| `kind` | `local` / `original` / 省略 | すべて | 区分 |
| `sort` | `popularity` / `priority` / `recent` | §2.4 参照 | 並び順 |
| `order` | `desc` / `asc` | `desc` | |
| `limit` | 1–100 | 30 | 1 ページ件数 |
| `offset` | ≥0 | 0 | ページ送り(§2.2 末尾) |

**レスポンス**:

```ts
interface RuleDexResponse {
  summary: {           // 全体集計(フィルタ非依存。画面8 ヘッダの「34 件(有効 31・排除済み 3)」)
    implemented: number;        // 実装済み総数
    active: number;
    removed: number;
  };
  page: { total: number; limit: number; offset: number }; // 現フィルタでの総数とページング
  items: RuleDexItem[];
}

interface RuleDexItem {
  id: string;
  name: string;              // ユーザー入力のルール名(サニタイズ済み。§2.5)
  description: string | null; // 図鑑表示用の説明(出どころは §3.2(d) で決定)
  kind: 'local' | 'original';
  prefecture: string | null; // ローカルかつ入力ありのときのみ。それ以外は null
  status: 'active' | 'removed';
  priority: number | null;   // PR-01 完了後のみ非 null。表示は順位に変換(§2.4)
  popularity: number | null; // PR-02 完了後のみ非 null(0–100 想定)
  implementedAt: string;     // ISO 日付。新着ソート・「◯◯ リリース」表示に使う
  removedAt: string | null;
}
```

- `summary` はフィルタに関係なく全体値を返す(ヘッダ表示は「いま何がどれだけあるか」の全体像であるべきため)。`page.total` はフィルタ適用後の件数(「…ほか N 件」の算出元)。
- **ページング方式**: 規模(E12 §6: 実装済みルールは数十〜数百件オーダー)を踏まえ、初期は `offset`/`limit` とする。無限スクロールは `offset += limit` で追加取得。人気度ソートは値が変動しうるが、この規模では offset のズレは実害にならない。件数が数千に育ったら keyset ページング(安定ソートキー + カーソル)へ移行する(§5.2)。過剰設計を避け、初期は offset で始める。

### 2.3 都道府県情報の非表示規約

都道府県は投稿者本人の記録として保存し、公開 API のルール項目にも互換性のため残す。ただし、ルール図鑑・対局内詳細・卓の有効ルール一覧では表示・絞り込み・集計に使わない。図鑑の区分表示は `ローカル` / `オリジナル` のみとし、都道府県の有無で文言を変えない。

### 2.4 【決定】段階成立(フィーチャーフラグ)設計

RV-01/RV-02 は依存する下流 Epic(PR-01/PR-02/EV-03)の完了前でも成立させる。実装は**3 つのフラグ + 「データがあれば出す」ルール**で組む。over-engineering を避け、フラグは環境変数か設定 1 か所で切り替える。

| フラグ | 解禁するもの | 対応 Epic | 未完了時の挙動 |
|---|---|---|---|
| `FEATURE_PRIORITY` | RV-01 の優先度順ソート / RV-02 の優先度(順位)表示・優先度ソート | PR-01 | RV-01 は登録順で表示。RV-02 は順位列を出さず、並び順から「優先度」を除く |
| `FEATURE_POPULARITY` | RV-02 の人気度バー・人気度ソート | PR-02 | 人気度バーを出さず、並び順から「人気度」を除く。既定ソートは `recent` |
| `FEATURE_ELIMINATION` | RV-02 の状態フィルタ「排除済み」選択肢・排除済み行の表示 | EV-03 | 状態フィルタは `すべて / 有効` の 2 択。排除は発生しないので `removed` 件数は常に 0 |
| `FEATURE_RULE_DEX` | RV-01 の「図鑑でくわしく」導線 | RV-02 リリース | 導線ボタンを非表示(RV-01 単体で成立) |

**実装の芯**: API は存在するフィールドをそのまま返し(`priority`/`popularity` は未算出なら `null`)、UI は `値が null なら該当 UI を描画しない`。フラグはソート選択肢と既定ソートの出し分け、および導線・フィルタ選択肢の出し分けにだけ使う。「データが来たら出る」を基本にすることで、PR-01/PR-02/EV-03 の完了とほぼ同時に、UI 側のフラグ切り替え 1 行で表示が増える。

**既定ソート**: `FEATURE_POPULARITY` オンなら `popularity`(画面8 の想定)、オフなら `recent`(新着 = `implementedAt` 降順)。新着ソートはフラグに関係なく常に選べる(初期のカタログ体験の最低線)。

### 2.5 ルール名・説明のサニタイズ

`name`/`description` はユーザー提案由来のテキストを起点に持つ(§3.2(d) で説明の出どころを決定)。表示側で以下を最低線とする:

- React の既定エスケープに任せる(`dangerouslySetInnerHTML` を使わない)ことで XSS を防ぐ。図鑑は Markdown 等のリッチ描画をしない(プレーンテキスト表示)。
- 表示上限: `name` は 1 行・全角 20 文字程度で省略(…)。`description` は図鑑一覧の説明スロットでは 1 行クランプ(§3.2(c) の出し分けに従う)、詳細で全文。改行は一覧では詰める。
- インジェクション検査(E6)は codex 保護のためのものであり、**表示安全とは別レイヤ**。図鑑は不特定多数が見る公開面なので、表示側でもこの最低線を独立に持つ。

## 3. ストーリー別詳細仕様

### 3.1 RV-01 — 卓の有効ルール一覧

#### (a) 原文引用

> **[RV-01]** プレイヤーとして、対局前・対局中に、いま有効なルールをさっと確認したい。それは基本は「遊んでいたらなんか発動した」というラフな体験のまま、何が起こりうるかだけ把握してカオスを楽しむためだ(§4.5)。
> - 受け入れ条件:
>   - 卓の準備時(待機画面)と対局中の両方から、有効なルールの一覧を開ける
>   - 一覧はルール名だけの軽い表示とする(人気度・都道府県・優先度の数値はこの画面では出さない §4.5)
>   - ちゃんと確認したい人向けにルール図鑑(RV-02)への導線を置く(RV-02 完了までは導線なしで成立させる)
>   - PR-01 完了後は優先順位を並び順として使う(数値は表示しない。完了までは順序なしの一覧で成立させる)

#### (b) 挙動仕様

- **0 件(追加ルールなし)**: 初期の「素の大富豪」は基本ルール(エンジン内蔵)だけで、提案由来の有効ルールが 0 のことがある。件数は「有効ルール 0」、一覧は空状態「追加ルールはまだありません(いまは基本ルールだけです)」を出す。基本ルールは提案ルールではないので**この一覧には載せない**(この画面の対象は「増えていく提案ルール」。基本進行の説明は別途「あそびかた」の領分)。
- **大量件数**: ルール名だけの縦リストを単純スクロール。1 行が軽いため数百件でも仮想化は不要(必要になってからで足りる)。待機画面(画面2b)・対局画面(画面3)のヘッダには件数のみ(例「31 件」)を出す。
- **排除直後の整合(重要)**: セット進行中に、別の卓や運用でルールが排除(EV-03)・追加されても、**当該卓の固定セットは変わらない**(E12 §4.6: セット開始時に固定)。対局中の画面4 は固定セットを表示し続ける。一方、図鑑(画面8)はグローバル最新を映すので、この瞬間**画面4 と画面8 の集合は食い違う**が、これは仕様どおり。「この卓で発動しうるのは画面4 が正、全体のカタログは画面8」と役割が分かれている。
- **待機画面と対局中の差**: 待機画面(セット未開始)の一覧は「現時点のグローバル有効ルール(開始で固定される予定)」のプレビュー。開始ボタンを押した瞬間に集合が固定される。待機表示中はルールのリリース・排除で件数が変わりうるので、ルーム状態の更新で追随する。
- **同一画面の二経路**: 待機画面からも対局中からも同じ画面4 を開く。データ源は両方とも `roomState.activeRules`(§2.1)で共通。1 コンポーネントで両経路を賄う。

#### (c) 画面仕様(wireframes 画面4)

- アプリバー: 「← いまの有効ルール」。対局中は戻ると対局画面(画面3)、待機からは待機画面(画面2b)へ。
- ヘッダキャプション: 「N 件・すべての卓に適用(変更不可 §4.5)。優先順位の高い順にならぶ。」— **PR-01 未完了時は「優先順位の高い順にならぶ」の一文を出さない**(順序なしのため)。
- 本体: `rul slim` 行(ルール名のみ)。順位バッジ・人気度・都道府県は**一切出さない**(ラフ表示 §4.5)。
- 末尾: 「図鑑でくわしく → 画面8」ボタン。`FEATURE_RULE_DEX` オフ時は非表示。
- 呼び出し元: 待機画面(画面2b)の「いまのルール」ボックスの「一覧を見る」、対局画面(画面3)アプリバーの「有効ルール N → 画面4」。

#### (d) API・データ定義

- **専用 API を持たない**。§2.1 のとおり `roomState.activeRules`(WebSocket スナップショット)を読む。
- 画面4 は深いリンク先を持たず、必ず待機/対局の卓コンテキスト(= アクティブな WebSocket ルーム)から開かれる。ゆえに一覧のための追加フェッチは不要。
- 表示に使うのは `activeRules[].name` と `activeRules.length` のみ(`id` は将来の詳細遷移・キー用に保持)。順序はサーバー整列済みをそのまま使い、クライアントで並べ替えない。

#### (e) 実装方針

- 共有コンポーネント `<ActiveRuleList variant="rough">` を作り、待機・対局の両方から呼ぶ。props は `rules: {id,name}[]`、`showDexLink: boolean`(= `FEATURE_RULE_DEX`)、`ordered: boolean`(= `FEATURE_PRIORITY`。ヘッダ文言の出し分けのみに使用。並び自体はサーバー責務)。
- `activeRules` は Zustand ストア(E12 §4.2)のルーム状態に保持。卓参加時/待機中のルール変動時/セット開始イベントで更新(§2.1 の 3 契機)。
- 画面3・画面2b のヘッダ件数は同ストアの `activeRules.length` を参照(単一ソース)。

#### (f) 受け入れ条件の精緻化

1. 待機画面(画面2b)と対局画面(画面3)の両方から画面4 を開け、同一の `activeRules` を表示する。
2. 各行はルール名のみ。順位・人気度・都道府県・優先度の数値要素が DOM に存在しない(スナップショットテストで検証)。
3. `FEATURE_RULE_DEX` がオンのとき図鑑導線を表示し、オフのとき非表示でも画面が成立する。
4. `FEATURE_PRIORITY` オンでサーバー整列順(優先度降順)どおりに、オフで登録順で表示し、数値順位は**どちらでも**表示しない。
5. 有効ルール 0 件で空状態を表示し、エラーにならない。
6. 対局中にグローバルでルールが排除されても、当該セットの画面4 の一覧が変化しない(固定セットの表示維持)。

#### (g) 未解決事項

- 画面4 の行タップで図鑑の該当ルール詳細へ飛ばすか(ラフのまま留めるか)。初期は**飛ばさない**(ラフ体験優先)。要望が出たら `id` を使って図鑑詳細へディープリンクできる余地は残す。

### 3.2 RV-02 — ルール図鑑

#### (a) 原文引用

> **[RV-02]** プレイヤーとして、これまでに実装された全ルールを「ルール図鑑」として一覧したい。それはみんなの提案で育ってきたカオスの全体像を眺めるためだ。
> - 受け入れ条件:
>   - ホームから図鑑を開け、実装済みルールごとに名称・区分・状態(有効/排除済み)が表示される
>   - 状態・区分で絞り込める。排除済みルールも削除せず「排除済み」として図鑑に残る(排除の発生は EV-03 完了後)
>   - 人気度・優先度の表示は PR-01・PR-02 の完了後に追加する(完了までは表示なしで成立させる)

#### (b) 挙動仕様

- **0 件**: 実装済み 0 のとき空状態「まだ実装されたルールはありません。提案が採用されるとここに載ります。」`summary` は全 0。フィルタ UI は出す(操作しても 0 件)。
- **大量件数**: `offset`/`limit`(既定 30)でページング。無限スクロールで追加取得。ヘッダの `summary` は全体、リスト末尾の「…ほか N 件」は `page.total - 表示済み` から出す。
- **排除直後**: 排除ルールは物理削除されず `status='removed'` で残る。状態フィルタ「有効」では出ず、「すべて/排除済み」で出る。`removedAt` を持ち、行に「低評価が集まったため排除(§4.4)」を添える。閲覧中に排除が起きても図鑑はリアルタイム同期しない(HTTP プル)。次回取得/リロードで反映される(図鑑にリアルタイム性は要らない)。
- **フィルタ組み合わせ**: 状態・区分・並び順は AND。並び順はフィルタと独立に効く。
- **段階表示**(§2.4 のフラグに従う):
  - PR-01 前: 優先度(順位)列なし、並び順から「優先度」除外。
  - PR-02 前: 人気度バーなし、並び順から「人気度」除外、既定ソート = 新着。
  - EV-03 前: 状態フィルタは「すべて/有効」のみ、`removed` は常に 0 件。

#### (c) 画面仕様(wireframes 画面8)

- アプリバー: 「← ルール図鑑」。呼び出し元はメニュー(画面1b)と画面4 の「図鑑でくわしく」。
- フィルタ行: 状態 / 区分 / 並び順(いずれもセレクト)。
- 集計キャプション: 「実装済みルール 34 件(有効 31・排除済み 3)」。
- ルール行(`rul`): 順位バッジ(優先) / 名称 + 状態タグ + 区分バッジ / **説明行(1 行)** / 人気度バー。排除済みは `rul dead`(打ち消し線 + グレー)+「排除済み」タグ。
- **説明行(1 行)の中身**: 排除済みは排除理由「低評価が集まったため排除(§4.4)」、それ以外は codex 生成 `description` の 1 行クランプ(なければ非表示)。codex `description` 全文は詳細(展開)で見せる。
- 段階表示に応じて順位バッジ・人気度バーは条件付きレンダリング(§2.4)。

**ルール詳細**: 画面8 は一覧。詳細は同画面内の展開(アコーディオン)か個別画面のどちらでもよいが、初期は**行タップで展開して `description` 全文 + メタ情報を見せる軽い実装**を推奨(画面遷移を増やさない)。詳細で見せる項目: 名称・区分・状態・説明文(§3.2(d))・実装日/排除日・(フラグに応じ)優先度順位・人気度。

#### (d) 【決定】説明文(`description`)の出どころ

**codex が実装時に `meta.json` へ生成した図鑑表示用の説明文を一次表示とする。**(提案者の生の提案文ではない)

- **理由 1(実装結果への忠実性)**: 図鑑が示すべきは「実際にゲームに入った挙動」。提案意図(提案文)と実装結果はズレうる(E12 §4.6(2) の都落ちの発火タイミング例のように、提案どおりに書けず調整されるケースがある)。codex 生成説明は実装済み挙動に基づく。
- **理由 2(表示品質)**: 提案文は検査(E6)通過済みでも生の入力で、長文・散文・体裁不整合になりうる。codex に「図鑑表示用の 1〜2 文の説明」を生成させることで、公開カタログの表示品質を一定に保てる。
- **実装への織り込み**: `meta.json` に図鑑表示用 `description`(短文)フィールドを設けることを、E1 のルール契約(`RuleMeta`)と E7 の codex プロンプトテンプレートに明記する(§5.1 の E12 修正提案)。生成物ゆえの不正確・逸脱は、E7 の CI/レビュー(Stage 0 の人手確認)で他の生成物と一緒に見る。
- **名称の扱い**: `name` は**ユーザー入力のルール名をそのまま使う**(サニタイズ §2.5)。発動演出(画面3 の「ルール発動!『8切り』」)・マイ提案(画面7)・図鑑で名称が一致している必要があるため、名称は提案由来で一貫させる。説明だけを codex 生成にする。
- **原文の保全**: 提案文の原文は提案レコードに残り、提案者本人はマイ提案(画面7、E5)で確認できる。図鑑詳細に「提案時の説明(原文)」を折りたたみで併記する余地は残すが、初期の主表示は codex 生成説明とし、原文併記の要否は運用を見て判断(§3.2(g))。

#### (e) API・データ定義

- §2.2 の `GET /api/rules`。読み取り元は E12 §4.4 の `rules` テーブル(ルールメタデータ)。
- サーバー実装は Drizzle(E12 §4.4)で `rules` に対する `where`(フィルタ)+ `orderBy`(ソート)+ `limit`/`offset`。`summary` は別途 `count` 集計クエリ。規模的にインデックスは `status`・`kind`・`popularity`・`implementedAt` に張れば十分。

#### (f) 受け入れ条件の精緻化

1. メニュー(画面1b)と画面4 から図鑑を開ける。実装済みルールごとに名称・区分・状態が表示され、都道府県は表示されない。
2. 状態・区分でフィルタでき、AND で効く。
3. 排除済みルールが物理削除されず `removed` として残り、状態フィルタで出し分けられる(EV-03 完了後)。
4. `FEATURE_PRIORITY`/`FEATURE_POPULARITY` のオン/オフで優先度・人気度の表示と並び順選択肢が段階的に増減し、オフでも画面が成立する。
5. ページングで 30 件超のルールを追加取得でき、`summary` は全体・`page.total` はフィルタ後件数を返す。
6. 0 件でもエラーにならず空状態を返す。

#### (g) 未解決事項

- 図鑑詳細に提案文の原文を併記するか(初期は codex 生成説明のみ。§3.2(d))。
- 無効(一時無効化・ロールバック中 = DB `disabled`)の図鑑での見せ方(§5.2)。
- ルール詳細を同画面展開にするか個別画面にするか(初期は展開推奨、遷移増やさない)。

## 4. テスト観点

**RV-01(卓の有効ルール一覧)**

- 待機画面・対局画面の両経路から同一の `activeRules` を表示する。
- 行がルール名のみで、順位・人気度・都道府県の数値/バッジが DOM に存在しない。
- `FEATURE_PRIORITY` オン: サーバー整列順どおり。オフ: 登録順。どちらも数値順位を出さない。
- ヘッダ文言「優先順位の高い順にならぶ」が `FEATURE_PRIORITY` オフ時に出ない。
- `FEATURE_RULE_DEX` オン/オフで図鑑導線が出/非表示、どちらでも成立。
- 有効ルール 0 件で空状態。
- **固定セットの維持**: 対局中にグローバルでルールが排除・追加されても、当該セットの画面4 の一覧・件数が変わらない(スナップショットが固定セットを保持していることの検証)。
- 待機画面中にルールがリリースされると件数が更新される(未固定プレビューの追随)。

**RV-02(ルール図鑑)**

- 都道府県を持つ API 応答でも、一覧・詳細の DOM に都道府県名や関連文言が現れない。
- フィルタ各種(状態/区分/並び順)単独 → 期待どおりの絞り込み・並び。
- フィルタ組み合わせ(AND)。
- ページング: `limit`/`offset` で境界(0 件・1 ページ ちょうど・端数)。`summary`(全体)と `page.total`(フィルタ後)が別値で正しい。
- 段階表示: `FEATURE_PRIORITY`/`FEATURE_POPULARITY` のオン/オフで優先度・人気度の表示と並び順選択肢・既定ソートが切り替わる。
- 排除済み表示: EV-03 完了後、`removed` が残り・出し分けられ・排除理由を添える(`FEATURE_ELIMINATION` オフ時は状態フィルタ 2 択で `removed` 0)。
- 説明文が codex 生成 `description` 由来で表示される(null 時のフォールバック)。
- サニタイズ: 長い name/description の省略・クランプ、HTML を含む文字列がエスケープされる(XSS 非発火)。

## 5. 未決事項・E12 への修正提案

### 5.1 E12 への修正提案

1. **スナップショットへの有効ルール一覧の追加(§2.1)**: E12 §4.3 は「スナップショットに含める公開情報の確定は E1/E3 で行う」とする。ここに **RV-01 用の `activeRules: {id, name}[]`(優先度降順整列済み)を公開情報として含める**ことを明記する。あわせて、この一覧は**手番ごとの状態スナップショットに含めず、卓参加時・待機中のルール変動時・セット開始時(固定)のイベントで配信する**(対局中=固定後は静的なので、毎手番の全量スナップショットには載せない)ことを E12 §4.3 に補足する。ルール数増加時のメッセージ肥大を避けるため。
2. **`meta.json` への図鑑表示用説明の追加(§3.2(d))**: E12 §4.6(1) の `meta.json` 項目(id・名称・説明・区分・都道府県・提案 ID)のうち「説明」を、**図鑑表示用に codex が生成する短文説明**として定義することを明記し、E1 の `RuleMeta` 契約と E7 の codex プロンプトテンプレートに反映する。名称はユーザー入力のルール名を一貫して使う(codex 生成対象は説明のみ)。

### 5.2 E11 内の未解決事項

- **無効(`disabled`)状態の図鑑での扱い**: E12 §4.4 の状態は 有効/無効/排除済みだが、図鑑の初期スコープは 有効/排除済み の 2 値(§2.2)。**初期は `disabled` を `GET /api/rules` の結果に含めない**(一時無効化=ロールバック中という運用状態を公開カタログに晒さない)。CX-04 による一時的な無効化・ロールバック中のルールを将来どう見せるか(隠す/「一時停止中」で見せる)は、CX-04 と EV-03 の運用が固まってから決める。
- **ページング方式の移行(§2.2)**: 初期は offset/limit。実装済みルールが数千件規模に育ったら keyset ページングへ移行する判断ポイントを持つ。
- **図鑑詳細の原文併記・遷移形態(§3.2(g))**: codex 生成説明のみで始め、原文併記の要否と詳細の同画面展開/個別画面化は運用を見て判断。
- **RV-01 行から図鑑詳細へのディープリンク(§3.1(g))**: 初期は飛ばさない(ラフ体験優先)。`id` は保持し、後日の導線追加余地を残す。
