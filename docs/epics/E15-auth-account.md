## 1. Epic 概要

### 1.1 目的

「登録ゼロで遊べる」体験(E12 §4.9 案 A、実装済み)を保ったまま、次の 2 つを足す。

1. **引き継ぎ**: 匿名で遊んだ記録(表示名・提案・イエローカード等、`users` 行に紐づく一切)を、Google アカウント紐付けによって別端末・別ブラウザへ引き継げる。
2. **提案のログイン必須化**: ルール提案(E05)を登録済みユーザー限定にする。イエローカード停止(E06)の「匿名作り直しで回避」問題を入口で解消する。

チュートリアル・通常プレイ・観戦・ルール閲覧・評価は従来どおり**登録なしで全部できる**。登録が要るのは提案と引き継ぎだけである。

## 2. 技術仕様

### 2.1 【決定】コンセプト: 「ログイン機構」ではなく「紐付け」

認証は今までどおり**トークン提示**である。本 Epic が足すのは次の 2 点だけ。

- **登録**: いまの匿名ユーザー行に `google_sub` を紐付ける(その場で登録完了。履歴・イエローカードもそのまま)。
- **ログイン(復元)**: Google OAuth を通過したら、その `sub` を持つ既存ユーザー行の `user_token` をクライアントへ渡し、localStorage を差し替える(端末の匿名行は放棄。AU-D3)。

「登録済みユーザー」の定義は **`users.google_sub IS NOT NULL`** である。

### 2.2 データモデル

```sql
ALTER TABLE users ADD COLUMN google_sub TEXT;           -- Google の安定ユーザー ID。NULL = 匿名
ALTER TABLE users ADD COLUMN registered_at INTEGER;     -- 紐付け日時(エポックミリ秒)
CREATE UNIQUE INDEX IF NOT EXISTS idx_users_google_sub ON users(google_sub) WHERE google_sub IS NOT NULL;
```

- 既存の起動時マイグレーション方式(`PRAGMA table_info` による列追加。`persistence.ts` の既存パターン)に従う。
- トークンは既存の `user_token`(1 ユーザー 1 トークン)を維持。別端末ログイン時は**既存トークンをそのまま返す**(両端末が同一ユーザーとして動く)。ローテーション・失効管理は持たない(§5)。

### 2.3 OAuth フロー(Authorization Code + PKCE)

`openid-client` を使う。トークンや認可コードを**クエリ文字列に載せない**ため、開始は POST、完了は単回・短命の引換コード(ott)で行う。

| エンドポイント | 役割 |
|---|---|
| `POST /api/auth/begin` | Bearer(現端末のトークン)必須。`state`・PKCE verifier・現ユーザー ID・フロー nonce をプロセス内ストア(TTL 10 分・単回)に保存する。nonce は `__Host-daifugo-auth-flow` Cookie にも設定し、`{ authUrl }` を返す。クライアントは `location.href = authUrl` で遷移 |
| `POST /auth/google/callback` | Google から `response_mode=form_post` で戻る。`state` とフロー nonce Cookie の照合 → code 交換 → ID トークン検証(`iss`/`aud`/署名/期限。openid-client の標準検証)→ `sub` で分岐(§2.4)→ 結果を ott ストア(TTL 60 秒・単回)に置き、`/#/auth/complete?ott=...` へリダイレクトする。Cookie は成功・失敗とも削除する |
| `POST /api/auth/complete` | body の `ott` を引き換え、`{ outcome, userToken, displayName }` を返す。クライアントは localStorage を差し替えて Socket.IO を張り直す |

- state ストア・ott ストアはプロセス内 Map で足りる(E12: 単一 Node プロセス)。再起動で消えるのは許容(やり直せばよい)。
- 部屋(対局)がプロセス内メモリである以上、OAuth のフルページ遷移でクライアント状態は失われる。**対局中はログイン導線を出さない**(§2.7)ことで運用上回避する。

### 2.4 callback の分岐仕様

`sub` と、begin 時に保存した「現ユーザー」の状態で分岐する。

| # | 条件 | 動作 | outcome |
|---|---|---|---|
| 1 | `sub` が未登録・現ユーザーは匿名 | 現ユーザー行に `google_sub` と `registered_at` を書く(**引き継ぎ登録**) | `linked` |
| 2 | `sub` が登録済み | その既存行の `user_token` を返す(**別端末ログイン**)。現ユーザー行には触れない(放棄。AU-D3) | `switched` |
| 3 | `sub` が登録済み・それが現ユーザー自身 | no-op。現トークンを返す | `already` |
| 4 | `sub` が未登録・現ユーザーは**別の** `sub` で登録済み | 現行への上書きはしない。**新規ユーザー行を作成**して `sub` を紐付け、そのトークンを返す(端末はその新アカウントに切替) | `switched` |
| 5 | begin 時のユーザーが実在しない・state 不一致・検証失敗 | ott を発行せずエラー画面用フラグメント `/#/auth/complete?error=...` へ | — |

ケース 4 は「家族で端末を共有し、別の Google アカウントで使い分ける」場合に相当する。登録済み端末でさらにログイン操作をするときは、クライアントが begin の**前に**「別のアカウントでログインすると、この端末はそのアカウントに切り替わります」の確認を出す(§2.7)。

### 2.5 引き継がれるもの・引き継がれないもの

- **引き継がれる**: `users` 行に紐づく一切 — 表示名、提案(`proposals.author_id`)、イエローカード・提案停止(E06)、seen 状態。テーブルの付け替えは発生しない(同じ行を使い続けるだけ)。
- **放棄される**(AU-D3): ケース 2/4 で端末に残っていた匿名行のデータ。行自体は削除しない(提案の author 参照が残るため)。
- **停止の洗浄は不可**: 登録は同じ行への紐付けなので、イエローカード・停止期限はそのまま残る。別の Google アカウントを新規に作れば回避できるが、匿名の作り直しよりはるかに敷居が高い(E06 の回避懸念への回答。§4.2)。

### 2.6 提案のログイン必須化(E05 ゲート改訂)

実装済みの投稿 API(E-18 反映後: 認証 → 停止確認 → 検証 → 重複確認 → 同期保存)の**先頭ゲートを強化**する。

1. 認証(Bearer 有効): 無ければ従来どおり **401**
2. **登録確認(新設)**: `google_sub IS NULL` なら **403 `{ error: 'registration_required' }`**
3. 以降は従来どおり(停止確認 403 → 検証 400 → 重複確認 → 保存)

- マイ提案一覧・seen・イエローカード表示などの**読み取り系は変更しない**(匿名でも自分の過去データは見える。ログイン必須化以前に作られた匿名の提案が存在するため)。
- 評価(E08)・投票系は**匿名のまま**(AU-D4 の適用範囲は提案の作成のみ)。

### 2.7 UX 導線

文言・トーンは `docs/design/UI文言・情報量ガイド.md` に従う(ここに書く文言は仮)。

| 場面 | 挙動 |
|---|---|
| **セットリザルト後** | 未登録なら「きろくをのこす(Google で引き継ぎ)」の控えめな 1 行導線。登録済みなら出さない。毎回は出さず、初回リザルト+以降は抑制(頻度はプロセス 1 で仮決めし記録) |
| **メニュー** | 「引き継ぎ・ログイン」を常設。登録済みなら「登録済み」表示とログアウト。**対局中(部屋に入っている間)は非表示**(§2.3 の制約) |
| **提案画面** | 未登録なら提案フォームの代わりに説明とログインボタン(API の 403 に頼らず入口で案内。403 も同じ誘導にフォールバック) |
| **ログイン開始** | begin → `location.href`。登録済み端末での再ログインは切替確認(§2.4 ケース 4)を先に出す |
| **完了** | `/#/auth/complete` で ott を引き換え、outcome に応じたトースト(「引き継ぎ登録したよ」「おかえり!」)→ 元画面(タイトル/メニュー)へ。`error` フラグメントなら「うまくいかなかったみたい。もういちどためしてね」で匿名のまま継続 |
| **ログアウト** | localStorage の `daifugo.userToken` を消し、新規匿名ユーザーとして再接続(共有端末対応)。サーバー側の失効はなし(v1) |

### 2.8 エラー・エッジケース

| ケース | 挙動 |
|---|---|
| Google 側で拒否・中断 | callback に `error` パラメータ → `/#/auth/complete?error=denied`。匿名のまま継続 |
| state 期限切れ・不一致 | 同上(`error=expired`)。やり直しで解決 |
| ott 二重使用・期限切れ | `POST /api/auth/complete` が 410 → 同じエラートースト |
| begin 時にトークン無効 | 401。クライアントはセッション再取得(既存フロー)後に再試行 |
| OAuth 未設定の環境(§2.9) | begin が 503 `{ error: 'auth_unavailable' }` → 「いまは使えないみたい」トースト |
| 対局中のログイン | 導線を出さないことで防ぐ。URL 直叩き等で begin された場合も拒否はしない(自己責任でページ遷移するだけ) |

### 2.9 設定・シークレット

| 変数 | 内容 |
|---|---|
| `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` | Google Cloud Console の OAuth クライアント(Web アプリ種別) |
| `PUBLIC_ORIGIN` | コールバック URL の組み立てに使う(例 `https://daifugo-together.fly.dev`)。既存に同等設定があればそれを使う |

- 未設定なら認証機能だけ無効(§2.8)。開発は FakeAuthProvider(§2.11)で進められるため、実クレデンシャルなしで全ストーリーが完了できる。
- **開発者タスク**: [E15 Google OAuth 受入 runbook](../runbooks/E15-google-oauth.md)に従い、Google Auth Platform で Web client を作成し、リダイレクト URI (`http://localhost:3000/auth/google/callback` と `https://daifugo-together.fly.dev/auth/google/callback`)を登録して Fly secrets を設定する。

### 2.10 セキュリティ

- CSRF: `state`(単回・TTL 10 分)に加え、開始ブラウザだけが持つフロー nonce Cookie を照合する。Cookie は `HttpOnly; Secure; SameSite=None; Path=/` とし、callback の成功・失敗時に削除する。
- コード横取り: PKCE S256。ID トークン検証は openid-client の標準(署名・`iss`・`aud`・期限)。
- `user_token`・認可コードを URL クエリに載せない(begin は POST、Google callback は `form_post`、完了はフラグメント + 単回 ott)。
- リダイレクト先は固定(`/#/auth/complete`)。open redirect なし。
- 認証エンドポイントのレート制限は初期は設けない(Google 側の摩擦と state 単回性で足りる想定。悪用が見えたら §5)。

### 2.11 テスト戦略

- サーバーは `AuthProvider` インターフェイス(authUrl 生成・code→sub 解決)に切り、実装を `GoogleAuthProvider`(openid-client)と `FakeAuthProvider` の 2 つにする(FakeCodexRunner と同じ流儀)。
- 単体テスト: §2.4 の分岐 1〜5 全部、ott 単回性・期限、begin 未認証、503(未設定)、提案 API の 403(§2.6)、ログアウト後の新規匿名発行。
- クライアント: 完了ハンドラ(localStorage 差し替え・再接続・トースト)、提案画面の未登録分岐、切替確認ダイアログ。
- 実 Google での通し確認は開発者タスク(§2.9)完了後に手動 1 回(結果は `docs/status.md` の該当項目を更新)。

## 3. ストーリー詳細・受け入れ条件

### AU-01: Google で引き継ぎ登録・別端末ログインができる

「匿名で遊んできたプレイヤーとして、Google アカウントに紐付けて、別の端末でも同じ記録で遊びたい」

受け入れ条件:

- [ ] 匿名ユーザーが登録すると、同じ表示名・提案・イエローカード状態のまま登録済みになる(分岐 1)
- [ ] 登録済みの `sub` で別端末からログインすると、その端末が既存アカウントの表示名・記録に切り替わる(分岐 2)。元の匿名行のデータは端末から見えなくなる
- [ ] 分岐 3(再ログイン no-op)・分岐 4(別アカウント切替)・分岐 5(失敗系)が §2.4 どおりに動く
- [ ] トークン・認可コードが URL クエリ・サーバーログに現れない
- [ ] OAuth 未設定環境では 503 になり、他機能に影響しない
- [ ] FakeAuthProvider で上記が全部自動テストされている

### AU-02: ルール提案がログイン必須になる

「運営として、提案者を Google 紐付き ID に限定して、停止回避の匿名作り直しを防ぎたい」

受け入れ条件:

- [ ] 匿名ユーザーの投稿 API は 403 `registration_required`(401・停止 403 との順序は §2.6)
- [ ] 提案画面は未登録時にフォームを出さず、説明とログイン導線を出す
- [ ] 登録済みユーザーの提案は従来どおり通る(既存の E05 テストが登録済みユーザーで成立し続ける)
- [ ] 匿名時代の既存提案はマイ提案で見え続ける

### AU-03: 導線の仕上げ(リザルト誘導・メニュー・ログアウト)

「プレイし終えたプレイヤーとして、自然なタイミングで引き継ぎ登録を勧められたい。共有端末では自分のアカウントから抜けたい」

受け入れ条件:

- [ ] 初回セットリザルト後に未登録者へ登録導線が出る。登録済みなら出ない。しつこくない(表示頻度の仮決めを記録)
- [ ] メニューに「引き継ぎ・ログイン」が常設され、対局中は出ない
- [ ] ログアウトで新規匿名ユーザーになり、再ログインで元アカウントへ戻れる
- [ ] 375×812 の実画面で導線一式を目視確認(既存 Epic と同じ検証水準)
