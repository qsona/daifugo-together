## 1. Epic 概要

### 1.1 目的

企画書 §6 の確定方針「ポップなトーン(桃太郎電鉄水準の全年齢家庭用ゲーム)を確立し、タイトルから全画面に適用する」を、実装可能な仕様に落とす。トーンの基準ビジュアルは **案 2A「グランドフェス」で確定済み**(企画書 §6・キービジュアル提案.md)であり、本 Epic は「新しいデザインを決める」フェーズではなく、**確定済みデザイン決定を仕様化し、受け入れ検証手順を定義する** フェーズである。

トーンの水準は企画書 §2.3 の「子供がメインターゲットでありつつ大人も普通に楽しむ」に置く。過度なゆるかわ・幼児向けデフォルメは避ける(2A で「子供っぽさを一段抜く」調整として反映済み)。

### 1.2 担当ストーリー

| ID | 要旨 | フェーズ | 依存 |
|---|---|---|---|
| DS-01 | タイトル画面(画面 1a)に 2A キービジュアルを適用し、トーンガイドを文書化して以後の全画面の基準にする | 1 | なし(最初期から並行着手可) |
| DS-02 | 主要画面(ロビー・対局・結果)を DS-01 のトーンガイドで統一し、逸脱がないことをレビューで確認する | 1 | DS-01, GE-02 |

DS-01 は依存がなく、トーンガイドが以後の全画面の基準になるため **最初期から並行着手する**(バックログ §4「並び順の設計意図」)。

### 1.3 スコープと非スコープ(デザインシステム成果物との分担)

本 Epic は次の 2 者を **別成果物** として扱い、責務を分ける。混同すると重複記述・二重管理になるため明示する。

| 成果物 | 誰が作るか | 内容 | 本設計書の関わり方 |
|---|---|---|---|
| デザインシステム成果物(トークン CSS/JSON・部品カタログ HTML・トーンガイド MD) | 並行作業(DS-01 の「トーンガイド」受け入れ条件を満たす実体) | 2A から抽出した配色・タイポ・角丸・影・余白のトークン、UI 部品の定義・見本 | **要件と受け入れ検証手順を定義する側**。中身(具体的なトークン値や部品実装)はここに重複記述しない |
| 本設計書(E04) | 本担当 | 資産の管理方式、トークン→React 接続、トーン準拠運用、DS-01/DS-02 の仕様と受け入れ条件の精緻化、テスト観点 | デザインシステム成果物と wireframes を「入力」として参照し、実装着手可能な仕様に束ねる |

**非スコープ**(他 Epic が担当。本 Epic はトーン準拠の「基準」だけを提供する):

- 各画面の機能ロジック・状態遷移(E1/E3 ほか)。ワイヤーの遷移は `wireframes.html` が持つ。
- フェーズ 2 以降の画面(提案フォーム・図鑑・イエローカード演出など)の実装。これらは各機能 Epic(E5/E6/E11)が **DS-01 のトーンガイドに沿って** 作る(§3.2 の対応表で責務を明示)。
- 演出のアニメーション実装(カード移動・ルール発動 CX-06・イエローカード YC-02)。部品としての見た目はデザインシステムが提供し、発火タイミングは各 Epic が持つ。

## 2. Epic 横断の技術仕様

前提スタック(E12 §4.2 / §5): **React + Vite の SPA、DOM/CSS 描画(Canvas 不使用)、状態は Zustand + サーバースナップショットの写し、演出は CSS transform/transition**。モノレポの `packages/web` がフロントエンド(E12 §4.1)。以下はこの前提に整合させる。

### 2.1 デザイン資産の管理方式

#### 2.1.1 キービジュアル SVG の配置とビルド取り込み

- **原資産**: `docs/design/key-visual-2a.svg`(viewBox 1080×1920 = 9:16、完全自己完結。外部画像・外部フォント・外部 CSS への参照ゼロ)。これをレビュー・履歴管理の正本とする。
- **実装リポジトリへの取り込み**: `packages/web/src/assets/key-visual-2a.svg` として取り込む(原資産のコピー。原資産を更新したら差し替える。同期の実体は TS-02 の雛形整備で決める小さな手順)。Vite の静的アセットとして扱う。
- **描画方式**: DOM/CSS 描画方針(E12 §4.2、Canvas 不使用)に沿い、**タイトル画面(画面 1a)の全面背景として `<img src=…>` または `background-image` で 1 枚絵として使う**(SVG をインライン展開して DOM ノード化する必要はない。1a では内部要素を個別操作しないため、`<img>` が最も軽く単純)。ラスタライズせず SVG のまま配れば、9:16 を保ったまま任意解像度で破綻しない。
- **注意(字形の端末依存)**: 現行 SVG のロゴ「大富豪」「みんなでつくろう」・コピー・導線は **ライブテキスト**で、丸ゴシック系フォールバック(M PLUS Rounded 1c → Hiragino Maru Gothic ProN → Hiragino Sans)に依存する。この字形は閲覧端末のインストール済みフォントで変わる(特に Android/Windows でロゴの見えが変化する)。ブランドの核であるロゴの見えを固定するには、**タイトル用途では「大富豪」ロゴ文字をアウトライン(パス)化した派生 SVG を用意する**ことを推奨する(自己完結性を保ちつつ端末非依存にできる)。UI 本文フォントの統一(Web フォント同梱の要否)は別論点で §5 に送る。
- **ゲーム内 UI 部品の切り出し**: 2A の中の再利用部品(ルールカード=金/緑、赤リボン見出し、審判キャラ、手札の扇)は、SVG から個別部品として切り出し、デザインシステム成果物(`design-system.html`)側で管理する。**本設計書では部品の実体を再定義しない**(キービジュアル提案.md「ゲーム内 UI への展開」が対応関係の一次情報)。

#### 2.1.2 favicon / OGP 画像の生成方針

いずれも **2A から派生生成し、事前生成した PNG をリポジトリにコミットする**(実行時の外部サービス・外部フォント依存を持たない。判断基準: E12 §2 の運用物最小)。

- **favicon**: 2A のロゴ/意匠から縮小視認性の高いモチーフを 1 つ選んで正方形の派生 SVG を作り、そこから PNG を書き出す。候補は「大富豪」の 1 文字(赤/金/緑の 1 色)か、赤黄緑 3 色の意匠、またはスート 1 つ。サイズは `favicon-32.png` / `apple-touch-icon-180.png` / `icon-192.png` / `icon-512.png`(PWA を見据えた標準セット)。
- **OGP**: 企画書 §6 の「横長(16:9)は告知・共有用」に沿い、**横長構図の共有画像**を用意する。OGP 標準サイズは 1200×630(≒1.9:1)。現状 `docs/design/key-visual-a/b/c.svg`(ラウンド 1 の横長 3 案)は **旧トーン**なので流用できない。**2A トーンの横長派生を新規に作る必要がある**(§5 の未決事項)。当面はタイトル 9:16 を横長カンバスに中央配置+左右を 2A ベース色 `#2B6FC2` で埋める暫定でも成立する。
- **生成手段**: SVG→PNG のラスタライズは `resvg`(resvg-js)または `sharp` をローカル/CI のワンショットスクリプトで実行する。ビルド時に毎回生成する必要はなく、**生成物を成果物としてコミットする**方が単純で確実(過剰設計しない)。

### 2.2 デザイントークン → React の接続(E12 §4.2 と整合)

デザインシステム成果物のうち、機械が消費するのは **`design-tokens.css`(CSS カスタムプロパティ)** と **`design-tokens.json`(同値の機械可読版)** の 2 つ。接続の規約を次のとおり定める。

1. **CSS 変数を単一の消費経路にする**: `design-tokens.css` は `:root { --color-…; --radius-…; --shadow-…; --space-…; --font-… }` 形式で全トークンを定義する。`packages/web` はこれを **アプリ起点で 1 回だけグローバル import** する。全コンポーネントの色・角丸・影・余白・書体は **`var(--…)` 経由でのみ参照する**(生の 16 進カラー・px 直値の直書きを禁止。§2.3 と §4 で機械検査する)。DOM/CSS 描画(E12 §4.2)と CSS 変数は素直に噛み合い、Canvas を使わないので画面上の見た目は全てトークンで表現できる。
2. **JS 側で値が要る場合だけ JSON を使う**: CSS transition/transform で完結しない、**JS が値を読む必要のある演出**(例: CX-06 のルール発動でクラス付与のタイミングを JS が制御し、CSS 側の duration と一致させたい場合)には、`design-tokens.json` をビルドで TS モジュール(`export const tokens = …` と型)に変換して import し、**CSS と JS が同じ値の単一の出所を共有する**。Zustand ストアや演出フックが時間・イージング値を持つときはここから取る(ハードコード禁止)。
3. **物理配置**: `design-tokens.css` / `.json` の正本は `docs/design/`(DS-01 のデザインシステム成果物)。ビルドの入力にするための取り込み方(相対 import・prebuild でのコピー・小さな内部パッケージ化のいずれか)は TS-02(モノレポ雛形)側の実装詳細として決める。**正本を 1 つに保ち、`packages/web` はそれを複製・参照するだけ**という一方向を守る(二重管理を作らない)。
4. **境界**: トークンは「色・寸法・書体・影・余白・アニメーション基本値」まで。**部品の構造(HTML/JSX とレイアウト)はトークンではなく部品**(`design-system.html` のカタログ)側が持つ。React 実装はカタログの部品定義を写して作る。

### 2.3 トーン準拠を保つ運用(新画面追加時のチェックフロー)

新しい画面・部品を追加するとき(特にフェーズ 2 で各機能 Epic が画面を足すとき)に、トーンを崩さないための手順。**軽量・機械検査中心**にして、個人開発の運用負荷を上げない。

1. **既存部品を先に探す**: `design-system.html` のカタログに使える部品があれば再利用する。無ければ「新部品の追加提案」としてデザインシステム成果物側に部品を足してから画面を作る(画面ごとに独自スタイルを生やさない)。
2. **トークン経由のみで書く**: 色・角丸・影・余白・書体は `var(--…)` のみ。生の 16 進カラー・px 直値を直書きしない。
3. **機械検査(CI)**: PR で `packages/web/src` 配下の CSS/TSX に対し、生の 16 進カラー(`#[0-9a-fA-F]{3,8}`)や色関数の直書き・レイアウト外の px 直値を検出して fail させる(stylelint の `declaration-property-value-disallowed-list` 等。§4 のテスト観点と同じ検査)。トークン化された値だけが通る状態を保つ。
4. **逸脱レビュー(目視)**: 主要ブレークポイント(スマホ縦 375 / タブレット 768 / PC 1280)で描画し、`design-system.html` を基準に「カタログにない見た目の要素がないか」「セーフエリア内に重要要素が収まるか」を目視確認する(§3.2 の逸脱チェック手順に接続)。
5. **記録**: トーンに関わる決定(新部品の追加・トークンの追加/変更)はデザインシステム成果物側の履歴(コミット)に残す。画面単位の準拠確認は各 Epic の PR レビューで完結させ、専用の台帳は作らない(過剰運用を避ける)。

## 3. ストーリー別詳細仕様

### 3.1 DS-01 — タイトル画面への 2A 適用

#### (a) 原文引用(product-backlog.md より)

> **[DS-01]** プレイヤーとして、開始画面で桃太郎電鉄のようなポップなキービジュアルに迎えられたい。それは「カオスをみんなで笑う」というゲームのトーンを最初の一画面で伝えるためだ。
> - 受け入れ条件:
>   - タイトル画面に縦長(9:16)のキービジュアルが表示される(§6。メニューは次の画面に分離する)
>   - トーンガイド(配色・フォント・イラストのタッチ)が文書化され、以後の画面デザインの基準になる
>   - 開発者がポップなトーンとして承認済みである

#### (b) 仕様

**対象画面**: `wireframes.html` の画面 1a(タイトル)。メニュー(画面 1b)は別画面に分離済み(ワイヤーで確定)。

**レイアウト**:

- 画面 1a は **2A キービジュアル 1 枚を全面(フルブリード)**に敷く。SVG は viewBox 1080×1920(9:16)。ロゴ「みんなでつくろう 大富豪」・コピー「毎日どこかで、新ルール。」・導線「タップしてはじめる」は SVG に内包済み(2A で確定)。1a では追加の DOM オーバーレイを原則置かない。
- **端末アスペクト差の吸収**: 画面のビューポートは 9:16 とは限らない(縦長スマホは 9:19.5 等)。ページ背景を 2A のベース色 `--kv-base`(`#2B6FC2`)で塗り、SVG は横幅 100% で上下中央に置く方式を基本とする(横幅基準でスケールし、上下に余った領域はベース色で埋まって放射光・丘が自然に続く見えになる)。重要要素(ロゴ・コピー・導線)は SVG 内でセーフバンドの内側(下記)に配置済みなので、上下が多少切れても欠けない。
- **セーフエリア**: 端末のステータスバー/ホームインジケータと重なりうる **上下約 6%(1920px 中 約 115px)には重要要素を置かない**(2A で担保済み。ロゴ・コピー・導線は内側にある)。実装では `<meta name="viewport" content="…, viewport-fit=cover">` とし、コンテナに `padding: env(safe-area-inset-top) … env(safe-area-inset-bottom)` を効かせて、システムの下端ジェスチャ領域と視覚要素が競合しないようにする。

**タップ領域**:

- ワイヤー画面 1a の仕様どおり **「画面のどこを押しても進む」**。全面を 1 つのインタラクティブ要素で覆い、タップ/クリックで画面 1b(メニュー)へ遷移する。
- アクセシビリティ: 全面要素に `role="button"`(または `<button>` / `<a>`)と `aria-label="はじめる(タップして進む)"` を与え、キーボード(Enter/Space)でも進めるようにする。可視のアフォーダンスは SVG 内の「タップしてはじめる」ピル(クリーム面+点線内枠、幅 600px)が担う。
- 下端ジェスチャ競合の回避: タップ判定は全面のままでよいが、可視のピルはセーフエリア内(SVG y≈1745、下端から約 175px)にあり、ホームインジケータ領域と重ならない。

**トーンガイド=デザインシステム成果物の受け入れ検証手順**(DS-01 受け入れ条件 2「トーンガイドが文書化され基準になる」の検証):

デザインシステム成果物が「DS-01 のトーンガイド」として成立していることを、次のチェックで確認する。**中身の値は成果物側に置き、ここでは満たすべき条件だけを定義する**。

1. **4 ファイルの存在**: `docs/design/design-tokens.css` / `design-tokens.json` / `design-system.html` / `デザインシステム.md` が揃っている。
2. **配色**: 2A の主要 7 色 + 補助色がトークン化されている。少なくとも下表の役割がプリミティブトークンとして 2A の色値にトレースでき、セマンティックトークンがそのファミリーを参照している(トレーサビリティ。セマンティック層は用途に応じて同ファミリーの明度違いを使ってよい)。

   | 2A の色 | 役割 | 想定トークン(名称は成果物側で確定) |
   |---|---|---|
   | `#2B6FC2` | ベース(深い青空) | `--kv-base` / `--color-bg-brand` |
   | `#4585D4` | 放射光線 | `--kv-ray` |
   | `#1C2447` | 輪郭線・文字(全要素共通アウトライン) | `--color-outline` / `--color-ink` |
   | `#FFF4DC` | クリーム(明色。真っ白の代替) | `--color-cream` / `--color-surface` |
   | `#FFC53D` | 金(NEW RULE・イエローカード・強調) | `--color-gold` / `--color-accent-warning` |
   | `#E14B3B` | 赤(アクション・リボン) | `--color-red` / `--color-accent-action` |
   | `#2FA36B` | 緑(LOCAL RULE・成功) | `--color-green` / `--color-accent-success` |

## 4. テスト観点(ビジュアルリグレッションの要否と軽量な代替)

**結論: フェーズ 1〜2 初期はフルなビジュアルリグレッションテスト(VRT)を導入しない。** 部品数・変更頻度に対して Chromatic 等の VRT 基盤は運用過剰で、個人開発の運用物最小方針(E12 §2 判断基準 2)に反する。代わりに以下の軽量検査で「トーン崩れ」を実務上十分に捕まえる。

1. **トークン準拠の静的検査(CI・自動)**: `packages/web/src` の CSS/TSX に生の 16 進カラー・色関数・レイアウト外の px 直値が混入していないかを stylelint/grep で検出し、違反を fail。「色・寸法はトークン経由のみ」を機械的に強制する。トーン崩れの最大の原因(場当たりの色直書き)をここで止める。
2. **キービジュアル SVG の静的検証(CI・自動)**: `key-visual-2a.svg`(と派生 SVG)に対し、`xmllint --noout`(well-formed)+ 外部参照 grep(`http`/外部 `xlink:href` がゼロ=自己完結)+ ラスタライズ目視(例: 1200px と 380px で書き出し、タイトル・コピーの縮小可読性と要素の重なり/はみ出しなしを確認)。**この手順はキービジュアル提案.md で既に確立済み**なので流用する(qlmanage/resvg いずれでも可)。
3. **部品カタログ目視(手動・低頻度)**: `design-system.html` を単一の基準として、主要ブレークポイント(375 / 768 / 1280)でスクリーンショット目視。部品を変更したときだけ実施すればよく、画面ごとの全数目視は不要。
4. **スモークチェックリスト(手動)**: DS-01/DS-02 の受け入れ条件を箇条書きの手動チェックリスト化(§3.1(c)・§3.2(c) の表がそのまま使える)。画面が描画され、セーフエリア内に重要要素が収まることを確認。

**再検討トリガー**: 部品数が増えて回帰が頻発する、または CX-06 の発動演出など動きのある画面が増えるフェーズ 2 後半で、**主要 3〜4 画面に限定した** Playwright のスクリーンショット比較の導入を検討する。全画面 VRT は最後まで避け、対象を絞る。
