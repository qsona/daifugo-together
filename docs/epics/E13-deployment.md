## 1. Epic 概要

### 1.1 目的

E12 §4.5 で選定済みのホスティング(Fly.io 1 台 + 永続ボリューム)に**実際にデプロイし、公開 URL で遊べる状態を作る**。E12 が「決めた」ことを E13 が「動かす」という関係で、E13 は新しい技術判断をほとんど持たない。

この Epic を**フェーズ 1 に置く理由**は 2 つある。

1. **素の大富豪が完成した時点で人に遊んでもらえる**。フェーズ 2 のコア体験(自分の提案でゲームが変わる)を作る前に、土台が実機で遊ばれる状態にしておく。
2. **フェーズ 2 の前提そのものである**。E12 §4.6 の改訂により**ルールの反映は通常のサーバーデプロイ**になった。つまり CD(main マージ → デプロイ)が動いていないと、E7 の codex パイプラインは最後の一歩(反映)を持てない。CD をフェーズ 1 で先に作っておくことで、E7 は「PR を作って auto-merge するところまで」に集中できる。

**アプリ側はすでにデプロイ可能な形になっている。** E3(MP-01/MP-02)の実装で、SIGTERM による draining(Core `requestDrain` 接続)、同一オリジンでの SPA 配信、`PORT` / `DATABASE_PATH` / `WEB_DIST_DIR` の環境変数化が揃っている(`f37817a`)。E13 が足すのは**箱(Fly.io のアプリ・ボリューム)と配線(Dockerfile・fly.toml・CD ワークフロー)と、落ちたときに気づいて戻す手段**である。

## 2. Epic 横断の技術仕様

### 2.1 【決定】単一マシン構成を制約として明示する

**このアプリは水平スケールできない。** 理由は 2 つあり、どちらもフェーズ 1 の設計上の意図的な選択である。

1. 進行中の `RoomState` は**プロセス内の `Map`** にある(E3 の設計。永続化するのは受理アクションとセット結果だけ)。2 台目に振られた参加者は同じ部屋を見られない。
2. SQLite ファイルは**1 個の永続ボリュームの上**にあり、Fly のボリュームは 1 台のマシンにしか同時アタッチできない。

したがって `fly.toml` と運用手順で次を固定する。

- **マシン数は常に 1**。`fly scale count 1` から動かさない。
- **`auto_stop_machines = false` / `min_machines_running = 1`**。Fly の自動停止は「リクエストが来たら起こす」モデルで、**常駐して部屋とタイマーを保持する本アプリとは両立しない**(停止時に全部屋が消える)。既定値に任せず明示的に切る。

この制約は E12 §4.3 の「動くものは 1 台の Node プロセスに集約する」という方針の裏返しであり、隠れた前提にせず `fly.toml` のコメントにも残す。

### 2.2 実行構成と環境変数

| 項目 | 値 | 根拠 |
|---|---|---|
| リージョン | `nrt`(東京) | E12 §4.5 |
| マシン | shared-cpu、512MB〜1GB で開始 | E12 §6(不足したらサイズ変更) |
| ボリューム | 1GB、マウント先 `/data` | SQLite + WAL の置き場 |
| `PORT` | `8080` | `fly.toml` の `internal_port` と一致させる。既定は 3000(`packages/server/src/bin.ts`) |
| `DATABASE_PATH` | `/data/daifugo.sqlite` | **ボリューム上を指すこと**。既定の `data/daifugo.sqlite` はコンテナのレイヤ上で、再デプロイで消える |
| `WEB_DIST_DIR` | イメージ内の `packages/web/dist` の絶対パス | `bin.ts` が `resolve()` するので相対でも動くが、作業ディレクトリ依存を避けて絶対で渡す |

スキーマは起動時に `CREATE TABLE IF NOT EXISTS` で作られ(`persistence.ts`)、`journal_mode = WAL` が設定される。**フェーズ 1 ではマイグレーション手順を持たない** — 破壊的なスキーマ変更が要る段になったら、そのとき手順を作る(§5-2)。

### 2.3 Dockerfile の要点

E12 §4.5 は「Dockerfile は自動生成に任せてよい」としているが、このリポジトリには自動生成が外しやすい事情が 3 つあるので、**手書きして固定する**。

1. **pnpm workspaces のモノレポ**。`@daifugo/server` は `@daifugo/core` / `@daifugo/ai` を `workspace:*` で参照しており、単純な `npm install` では解決できない。
2. **`better-sqlite3` はネイティブモジュール**。ビルドステージにビルドツールが要り、かつ**ランタイムステージと同じ Node ABI**でなければならない。ビルドと実行の Node バージョンを `.node-version`(26.5.0)で揃える。
3. **web の成果物が要る**。`pnpm build` が `packages/web/dist` を作り、サーバーがそれを配信する。ビルドステージで作ってランタイムステージへ持ち込む。

マルチステージ(builder / runtime)とし、ランタイムには `node_modules` の本番依存・`dist` 群・`packages/web/dist` だけを置く。イメージサイズより**再現性**を優先し、`pnpm install --frozen-lockfile` を使う。

### 2.4 【決定】デプロイ時の挙動と、受け入れるダウンタイム

`fly deploy` は SIGTERM を送り、`bin.ts` の `shutdown()` が `app.beginDrain()` → `app.close()` を実行する。ボリュームは 1 台にしかアタッチできないため、**新旧のマシンは同時に走らない**。したがって次の順序になる。

```
fly deploy
  → 旧マシンに SIGTERM
  → beginDrain(): 新規の create/join/start/continue を拒否。進行中のゲームは完走
  → 進行中ゲームが終わったら close → exit(最長 kill_timeout = 300 秒)
  → 新マシン起動(イメージ pull + Node 起動)
  → 復帰
```

ここから導かれる**受け入れる帰結**を、隠さず明記する。

- **デプロイのたびに短いダウンタイムがある**。drain(進行中ゲーム ≒ 2 分が上限)+ 起動時間。E12 §4.5 が「active_sets=0 を待つ deploy gate は採らない」と決めた以上、これは設計どおりのコストである。
- **drain 中は新しい部屋を作れない・入れない**。既に対局中の人は最後まで遊べるが、その間に来た人は失敗する。**このときの UI 文言は decision-log B-3(未決)**であり、DP-01 の受け入れ条件には含めない(E1/E3 側の決定を待つ)。
- **進行中のセットは途中で打ち切られる**(ゲーム単位でしか完走を保証しない)。E12 §4.5 の決定どおり。

デプロイ頻度が上がるフェーズ 2(ルール反映がデプロイ)では、この窓が体感に効いてくる。**「遊ばれている時間帯を避けてキューを流す」ことが OP-01 のレート制御の副次的な役割になる**ことを E10 へ申し送る(§5-3)。

### 2.5 【決定】`/health` は drain 中も 200 を返す

Fly のヘルスチェックが失敗するとマシンは**再起動される**。drain 中に `/health` が落ちると、**Fly が進行中のゲームごとマシンを叩き直す**ことになり、graceful restart の設計が無意味になる。したがって:

- `/health` は **drain 中も HTTP 200 を返す**。状態は本文で区別する(`{"status":"ok"|"draining","db":"ok"}`)。
- 200 を返さないのは「DB が開けない」など**再起動で直る見込みがある壊れ方**に限る。
- ヘルスチェックの `grace_period` は起動時間(イメージ pull を含まない、プロセス起動〜listen)より余裕を持たせる。

「ヘルスチェックは再起動の引き金であって、状態表示ではない」という原則をこの Epic の設計判断として置く。

### 2.6 【決定】外部の監視・通知サービスは入れない

E12 §2 の判断基準 2(運用物を増やさない)に従い、Sentry などの監視 SaaS もアラート通知も**初回には入れない**。手段は次の 2 つに絞る。

- **自動復帰**: ヘルスチェック失敗 → Fly がマシンを再起動する。
- **事後の追跡**: 構造化ログを `fly logs` で読む。

**トレードオフ(明示)**: **落ちたことは開発者に通知されない。** 自分で見に行くか、遊んでいる人から言われるまで気づかない。フェーズ 1 の趣味規模ではこれを許容する(2026-07-27 開発者決定)。通知が要ると感じた時点で、まず Fly の組み込み機能で足りるかを確認してから外部サービスを検討する。

## 3. ストーリー別詳細仕様

### 3.1 DP-01 — 本番環境の構築と初回公開

#### (a) バックログ原文

> **[DP-01]** 開発者(運営)として、Fly.io に本番環境を立てて素の大富豪を公開 URL で遊べるようにしたい。それはフェーズ 1 の成果を実機で人に遊んでもらうためであり、フェーズ 2 のルール反映(=デプロイ)の土台でもあるからだ。

#### (b) やること

1. Fly.io にアプリを作成(リージョン `nrt`)し、1GB の永続ボリュームを `/data` にマウントする。
2. `Dockerfile` を書く(§2.3)。
3. `fly.toml` を書く。`internal_port = 8080`、`kill_timeout = 300`、`auto_stop_machines = false`、`min_machines_running = 1`、`[[mounts]]` でボリューム、環境変数(§2.2)。単一マシン制約の理由をコメントで残す(§2.1)。
4. 初回デプロイし、公開 URL を確定する。
5. 確定した URL で `packages/web/index.html` の `og:image` を絶対 URL に差し替える(`docs/archive/impl-progress.md` 仮定 17 の解消)。同ファイルの「デプロイ先未定」コメントも消す。

#### (c) 受け入れ条件

- Fly.io 東京(nrt)に**マシン 1 台 + 永続ボリューム**が作成され、`DATABASE_PATH` がボリューム上を指し、**再デプロイをまたいで対局履歴(`replay_records` / `set_results`)が残る**ことを確認できる
- 公開 URL にブラウザから入ると SPA が配信され、Socket.IO が**同一オリジンで**接続し、人間 1 人 + AI 3 席で**1 セット(3 戦)完走できる**
- `Dockerfile` と `fly.toml` がリポジトリに入り、`kill_timeout` が draining に足る値で、`auto_stop_machines` が無効化されている
- `og:image` が確定した公開 URL の絶対 URL になっている

#### (d) 実装上の注意

- **ボリュームのマウント前に DB を開かないこと**。`DATABASE_PATH` を誤って `/data` 以外にすると、デプロイのたびに静かにデータが消える(エラーにならない)。受け入れ条件の「再デプロイをまたいで残る」は、この事故を検出するために入れている。
- WAL モードでは `daifugo.sqlite-wal` / `-shm` が同じディレクトリにできる。**ボリューム上に置く**必要がある(`DATABASE_PATH` を `/data` 配下にすれば自動的に満たされる)。

### 3.2 DP-02 — main マージでの自動デプロイ

#### (a) バックログ原文

> **[DP-02]** 開発者(運営)として、CI を通った main へのマージが自動でデプロイされるようにしたい。それは手動デプロイの手間と事故をなくすためであり、フェーズ 2 でルールの反映がデプロイになる(E12 §4.6)前提だからだ。

#### (b) やること

`.github/workflows/deploy.yml` を追加する。既存の `ci.yml`(TS-02)は変更しない。

- トリガーは既存`CI`の`workflow_run`(`completed` / `branches: [main]`)とし、job条件で`conclusion == success`、元イベントが`push`、`head_branch == main`の3点を要求する。成功したCIの`head_sha`をcheckoutしてデプロイする。**CIを二重実行せず、失敗コミットのイメージビルド費用も発生させずに、検証済みSHAとデプロイ対象を一致させられる**ため、この方式を採る。`workflow_run`はsecretへ到達できるイベントなので、元イベントを`push`へ限定するjob条件を防御として必須にする。
- Fly の API トークンは **GitHub Environments のシークレット**に置く。リポジトリレベルのシークレットにしない。

#### (c) リポジトリ public に伴う必須の防御

decision-log A-2 で**リポジトリは public** と決まっている。デプロイワークフローは次を満たすこと。

- **fork からの PR でデプロイジョブが動かない**。トリガーを `push` に限り、`pull_request` / `pull_request_target` を使わない。
- **シークレットは Environment 経由でのみ露出する**。Environment に protection rule(main ブランチ限定)を設定する。
- ワークフローの `permissions` は最小(`contents: read`)にする。

#### (d) 受け入れ条件

- CI(format / lint / lint:design / typecheck / test / build)が通った **main へのマージだけ**がデプロイされ、CI が落ちたコミットはデプロイされないことを確認できる
- Fly の API トークンが GitHub Environments に隔離され、**fork PR から到達できない**ことをワークフロー定義で説明できる
- **対局中に実際にデプロイして、進行中のゲームが最後まで進むことを確認する**(E12 §4.5 のゲーム単位 graceful restart の実地検証)。あわせて drain 中の新規参加が拒否されること、復帰後に新しいバージョンで部屋を作れることを確認する

#### (e) 実装上の注意

3 番目の受け入れ条件は**この Epic で唯一「本番で実際に壊してみる」検証**である。省略しないこと。draining は E3 のユニットテストで検証済みだが、「Fly が実際に送る SIGTERM が Node プロセスまで届くか」「`kill_timeout` の窓に収まるか」はコンテナと PaaS の挙動であり、テストでは確認できない。

### 3.3 DP-03 — 落ちたことに気づけて、戻せる

#### (a) バックログ原文

> **[DP-03]** 開発者(運営)として、本番が正常かを確認でき、壊れたら直前のリリースへ戻せるようにしたい。それは自動デプロイを続ける以上、壊れたものが本番に入るのは避けられない前提だからだ。

#### (b) やること

1. `/health` を `app-server.ts` に追加する(§2.5)。**drain 中も 200**、本文で `status` と `db` を返す。
2. `fly.toml` にヘルスチェックを設定する。`grace_period` は起動時間より余裕を持たせる。
3. ログの読み方を文書化する。既存の構造化ログ(未捕捉例外、Socket 層の `INTERNAL`、AI の `ai_fallback_total` など)が `fly logs` でどう見えるかを実際に確認して書く。
4. ロールバック手順を文書化し、**実際に 1 回戻して確認する**。

#### (c) 受け入れ条件

- `/health` が DB 接続と drain 状態を返し、Fly のヘルスチェックに接続されている。**drain 中に 200 を返し続ける**ことをテストで確認できる
- 未捕捉例外・Socket 層の `INTERNAL`・AI fallback が `fly logs` で追えることを、実際に発生させて確認済みである
- 直前のリリースへ戻す手順が**実コマンド付きで**文書化され、**一度実行して戻せることを確認済み**である

#### (d) 実装上の注意

- ロールバック手順は Fly CLI のバージョンで変わりうる。**着手時に実際のコマンドを確認して書く**(「リリース一覧を見る → 直前のイメージを指定してデプロイし直す」という筋は変わらないが、コマンド名を推測で書かない)。
- **DB のスキーマは戻らない**。フェーズ 1 は `CREATE TABLE IF NOT EXISTS` のみで破壊的変更がないため問題にならないが、スキーマ変更を入れた後のロールバックは別問題になる(§5-2)。手順書にこの但し書きを入れること。
