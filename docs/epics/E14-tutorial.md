## 1. Epic 概要

### 1.1 目的

大富豪未経験のプレイヤーが、**大人の付き添いなしで 1 セット(3 戦)を完走し、2 セット目を自分から始める**状態を作る。専用のチュートリアルモードや練習画面は作らず、**素の大富豪(きほんモード)の最初の 1 戦そのものを教材にする**(チュートリアル設計 §1)。

教える中身は 2 つだけ:**強さの順序(3 が最弱 → 2 が最強)**と **全員パスで場が流れる仕組み**。それ以外は UI の造形(光る・沈む・演出)で吸収する(同 §2)。

次の 4 本を縦切りの単位と一致させる。**2026-07-27 に `product-backlog.md` へ登録済み**(企画書 §3.5 の追記とあわせて実施)。

## 2. Epic 横断の技術仕様(契約差分)

### 2.1 ルームのモード

**表現**: きほん = 有効ルール 0 件。「ルールが 0 件になった結果きほんに見える」のではなく、**モードが先にあり、きほんなら有効ルールを空にする**という向きで実装する(将来ルールが増えても、きほんの意味が壊れないため)。

```ts
// packages/core/src/protocol.ts(E3 所有の契約への追加)
export type RoomMode = 'basic' | 'community'; // basic=きほん / community=みんなのルール

export const clientPayloadSchemas = {
  // 現状は z.object({}).strict()。mode を任意で受け、未指定は 'community'(既存挙動)
  'room:create': z.object({ mode: z.enum(['basic', 'community']).optional() }).strict(),
  // …
};

export interface PlayerRoomView {
  // …既存
  mode: RoomMode; // 参加者・再接続者にも見える。V2/V4 の出し分けはこの値で行う
}
```

**サーバー側の変更点**(既存コードの事実に基づく):

| 箇所 | 変更 |
|---|---|
| `packages/server/src/room/types.ts` の `RoomState` | `mode: RoomMode` を追加。`CreateRoomInput` にも追加 |
| `packages/server/src/room/reducer.ts` `createRoomState`(55 行付近) | `availableRules` を `mode === 'basic' ? [] : (input.availableRules ?? [])` に |
| `packages/server/src/room/manager.ts` `RoomManager.create`(219 行付近) | `create(user, { mode })` を受け、`availableRules` の解決をモードでゲートする |
| `packages/server/src/room/manager.ts` `apply`(293〜302 行) | **見落としやすい要所**。`continue` / `leave` / `expireSetResult` の 3 アクションで `availableRules()` を毎回注入している。ここを通すと **きほんの部屋が 2 セット目でみんなのルールに化ける**。同じモードゲートを掛ける |
| `packages/server/src/room/view.ts` `viewFor` | `mode` を `PlayerRoomView` に載せる |
| `packages/web`(`MultiplayerClient.createRoom`・`PlaySheet`) | モードを引数で渡す。メニューの「あそぶ」→ ChoiceSheet →(下記「導線」の 2 段ウィザード)→ 作る/はいる |
| `packages/server/src/room/manager.ts` `RoomManager.join` | **きほんは 1 人練習専用**(2026-08-01 追加)。`room.mode === 'basic'` の部屋への入室を `ROOM_SOLO_ONLY` で拒否する。`ErrorCode` に `ROOM_SOLO_ONLY` を追加 |

**現時点で挙動差は出ない**。`app-server.ts` は `availableRules` を設定しておらず(`RoomManagerOptions.availableRules` 未指定 → 既定 `[]`)、全部屋が実質きほん状態である。V1 は「E7 がルールを供給し始めた瞬間にきほんが守られる」ための**構造の先置き**であり、この時点では **モードが state / view / UI を正しく流れることだけが検証対象**になる。

**導線**(チュートリアル設計 §3):

**2026-08-01 更新**: 選択の軸をモード名から「だれとあそぶか」へ組み替え、きほんを 1 人練習専用にした。旧案(1 画面のモード 2 択 + 未プレイ端末でのタグ・並べ替え)は採らない。理由と受け入れたトレードオフはチュートリアル設計 §3。

- メニューの「あそぶ」→ ChoiceSheet の **2 段ウィザード**。
  - 1 段目: 「みんなのルールであそぶ」(primary・先頭)→ 2 段目 / 「きほんルールで練習する」(若葉アイコン + キャプション「大富豪がはじめての人はこちら」)→ `room:create({ mode: 'basic' })` してそのまま `room:start`。
  - 2 段目: 「部屋を立てる」(primary)→ `room:create({ mode: 'community' })` / 「友だちの部屋にはいる」→ 招待コード入力 / 「もどる」。
- **並びは常に同じ**。未プレイ端末での並べ替えも「はじめてのひとはこちら」タグも実装しない。常設キャプションが同じ道案内を、端末状態に依存せず果たす。
- **きほんは待機室を挟まない**。作成直後に開始するため招待コードを出さない(フォールバックで待機室に落ちた場合も `showInvite` を偽にする)。
- 既プレイ判定は端末ローカル。`localStorage` キー `daifugo.playedBefore`(既存の `daifugo.userToken` の命名に揃える)。1 戦でも完了したら `true` を書く。**用途はガイド文言と強さ目盛りの出し分けだけ**で、導線の並びには使わない。
- 部屋に**入る**側はモードを選ばない。みんなのルールの部屋にだけ入れる(きほんは `ROOM_SOLO_ONLY` で拒否)。エラー文言は「この部屋はひとりで練習する部屋です。友だちの部屋の招待コードをたしかめてください。」

### 2.2 きほん AI 戦のターンタイマーと AI の間合い

チュートリアル設計 §4 は「きほんの部屋(ひとりで練習する)にターンタイマーは付けない / AI の思考時間はゆっくりめ」と定める。現状はどちらもルーム単位で変えられない。きほんが 1 人固定になった今も、実装側の分岐は「きほん + 人間 1 人」のまま安全側に残す。

- **ターンタイマー**: `reducer.ts` の `deadlineAtForTurn`(410 行付近)が `options.turnLimitMs ?? 60_000` を返している。ここに `state.mode` と「人間が 1 人だけか」を見る分岐を足し、**きほん + 人間 1 人のときだけ `null`** を返す。
  - **切断中の 15 秒(`disconnectedTurnLimitMs`)は残す。** これを外すと、切断した人間の手番でゲームが永久に止まる。
  - タイマーを外すと「接続中の人間が放置した部屋」を閉じる仕掛けが無くなる。`abandonAt` は**接続中の人間が 0 人になったとき**だけ設定される(`reducer.ts` 789 行付近)ので、この経路では働かない。V3 の未解決事項として §5 に挙げる。
- **AI の間合い**: `timers.ts` の `aiDelayMinMs=800` / `aiDelayMaxMs=2500` は `attachRoomSocketGateway` のオプションでプロセス全体に効く。ルーム単位で伸ばすには `RoomTimerCoordinator` が対象ルームのモードを参照できる必要がある。**ゲートウェイ全体の既定値を変えない**こと(みんなのルール側のテンポを巻き添えにしない)。

### 2.3 出せるカード案内(dim の導出)

サーバーは自分の手番のときだけ `legalMoves: Play[]` を送っている(`snapshot.ts` 94 行の `isTurn ? enumerateLegalPlays(...) : null` → `view.ts` 232 行 → `MultiplayerGameView.legalMoves`)。クライアントは現在これを「選択が合法手か」の判定にしか使っていない(`App.tsx` 493 行付近)。同じ入力から dim を導出できる。

```ts
// packages/web/src/game/hints.ts(新規・純関数。サーバーは使わないので core には置かない)
export type CardHint = 'playable' | 'dimmed';

export function deriveCardHints(
  hand: readonly { id: string }[],
  legalMoves: readonly Play[] | null, // 手番でなければ null
  selectedIds: readonly string[],
): Map<string, CardHint>;
```

規則:

1. `legalMoves === null`(自分の手番でない)→ **全部 `playable`**(dim を出さない)。手番外で沈ませると「出せない」ではなく「壊れている」に見える。
2. 選択なし → いずれかの合法手に含まれるカードが `playable`、残りが `dimmed`。
3. 選択あり → **選択中の全カードを含む**合法手だけを残し、その和集合が `playable`。これで「ペアの相方以外が沈む」が自然に出る。選択中のカード自身は常に `playable`(解除できる必要がある)。
4. 3 の絞り込み結果が空(選択がどの合法手の部分集合でもない)→ 選択中カード以外は全部 `dimmed`。

`dimmed` のカードはタップしても選択に入らず、**小さく首を振る**(文字なし)。V3 のはじめての 1 戦でだけ、その 1 回に限り理由の一言を添える。`prefers-reduced-motion` のときは首振りの代わりに短い縁の点滅にする。

### 2.4 はじめての 1 戦の配牌

**発動条件**: 未プレイ端末 × きほんの部屋(1 人練習)。みんなのルールでは発動しない(チュートリアル設計 §4)。きほんが 1 人固定になったため、「人間マルチが初プレイ」の分岐は消えた。

**シードの仕込み**。配牌は `startGame`(`packages/core/src/game/start-game.ts`)が `seedRng(config.gameSeed)` で決めており、`gameSeed` は `set/set-reducer.ts` 37 行で `setSeed` と `gameIndex` を `:` で連結して作られる(第 1 戦は `gameIndex=0`)。`setSeed` は `attachRoomSocketGateway` の `createSetSeed`(既定 `randomUUID`)が作る。**つまり seed を差し替えるだけで配牌を仕込める。エンジンの改造は要らない。**

事前探索で保証できるのは**静的な条件だけ**である。ここを混同しないこと。

| 条件 | 保証の質 |
|---|---|
| 自分が先頭手番(= ♦3 が自分に配られる。`start-game.ts` 164 行が ♦3 保持者を先頭にする) | **静的に保証できる** |
| 手札に同ランク 2 枚以上のペアがある | **静的に保証できる** |
| 勝ち切れる手札の強さ(2・A・K の枚数などの指標が上位) | **静的に近似できる**(勝敗そのものは保証できない) |
| 中盤までに全員パスで場が流れる | **保証できない**。AI の実際の打ち回し次第 |

保証できない理由: AI(`packages/ai`)は `DEFAULT_THINK_BUDGET`(`hardMs: 200`)の時間予算付き探索で、期限切れ時は `partial-search` に落ちる。**同じ seed でも実機の負荷で着手が変わりうる**ため、事前探索でゲームの筋を確定させることはできない。したがって:

- 探索スクリプトは静的条件で候補 seed を絞り、動的条件(場流れの発生・自分の順位)は **AI を実際に走らせて N 回試行し、発生率の高い seed を選ぶ**という位置づけにする(保証ではなく確率の底上げ)。
- ガイドは**遭遇ベース**なので、場流れが起きなければその一言が出ないだけで破綻しない。この性質が唯一のフォールバックであり、設計上の安全弁である。

**座席の問題(要注意)**。`reducer.ts` の `withSeats`(177 行)は `Math.random` で席順をシャッフルしてから `setSeed` を使う。座席が先に決まるため、「seat 0 用の seed」を選んでも人間が seat 0 に座るとは限らない。対処は 2 つのうち**前者を採る**:

1. **はじめての 1 戦の部屋では席シャッフルを行わず、人間を seat 0 に固定する**(reducer にモード分岐)。AI 戦なので席順に意味はなく、探索も seat 0 の 1 通りで済む。
2. 座席 index ごとに 4 本の seed を用意し、実行時に人間の seat に応じて選ぶ。順序上、席が決まった後に seed を選び直す必要があり、`startSet` の中で seed の決定が完結しないため複雑になる。

**探索スクリプト**は既存の `scripts/*.mjs` + 同名 `*.test.ts` の慣習に合わせて `scripts/find-tutorial-seed.mjs` / `scripts/find-tutorial-seed.test.ts` に置く。選ばれた seed は定数としてサーバーに埋め込む(実行時探索はしない — 起動を遅くする理由がない)。

### 2.5 ガイドの状態機械

クライアント側の純粋な reducer にする。表示部品(Toast / Callout)から独立させ、テストを部品描画に依存させない。

```ts
// packages/web/src/game/guide.ts(新規)
export type GuideCue =
  | 'firstTurn'      // 最初の手番
  | 'followTurn'     // 場にカードがある状態の自分の手番
  | 'pairAvailable'  // ペアが出せる手番(legalMoves に count>=2 がある)
  | 'noLegalMove'    // 出せる手がない(パスしかない)
  | 'illegalTap'     // 出せないカードをタップした
  | 'fieldCleared';  // 全員パスで場が流れ、次が自分

export function reduceGuide(state: GuideState, input: GuideInput):
  { state: GuideState; cue: GuideCue | null };
```

- 入力は `PlayerRoomView` の差分(`game.turn?.seat === you.seatId`・`game.field.cards.length`・`legalMoves`・`events` の `fieldCleared`)と UI イベント(出せないカードのタップ)。
- **各 cue は 1 戦につき 1 回だけ**。表示済みの集合を state に持つ。2 戦目以降は状態機械ごと無効化する(残るのは造形だけ — チュートリアル設計 §5)。
- 同時に 2 つ出さない。優先順は遭遇順(先に条件を満たしたものを出し、他は次の機会へ持ち越す)。
- 文言は 1 文以内・ふりがな付き。`ruby` 要素を使うため、Toast / Callout の children は `ReactNode` のまま扱う(既にそうなっている)。文言案はチュートリアル設計 §4 の表を初期値とし、実画面 375px で読み返して確定する(UI文言ガイド §0 の対策)。
- **強さ目盛り**は状態機械の外。初戦のみ HandTray の端に「よわい ← → つよい」を出す。根拠は `CARD_RANKS`(`cards/card.ts` 4 行)が `3,4,…,K,A,2` の**強さ昇順**であること。

## 3. 実装の縦切り

各切りは implementation-workorder §3 の「プロセス1(縦に通す)→ 方向性レビュー → プロセス2(仕上げる)」で回す。**V1 → V2 → V3 → V4 の順**。V2 は V1 に依存しない(モードに関係なく手番の案内は出せる)ので、V1 のレビュー待ちの間に着手してよい。

### V1: ルームのモード(TU-01)

**範囲**: §2.1 の契約差分と導線。タイマー・AI の間合いは V3 に回す。

**やること**:

1. `packages/core/src/protocol.ts` に `RoomMode`・`room:create` ペイロード・`PlayerRoomView.mode` を追加。
2. `RoomState.mode` / `CreateRoomInput.mode` / `createRoomState` / `RoomManager.create` / `manager.apply` の 3 アクション / `viewFor` を通す。
3. `MultiplayerClient.createRoom(mode)`、メニュー → ChoiceSheet の 2 段ウィザード(§2.1 導線)→ 作る/はいる。きほんは作成後に即開始。
4. `localStorage` の既プレイ判定(用途はガイドの出し分けのみ。導線の並びには使わない)。
5. きほんの部屋への入室を `ROOM_SOLO_ONLY` で拒否する。

**受け入れ条件**:

- [ ] `room:create` にモードを指定でき、`PlayerRoomView.mode` として自分にも参加者にも見える。
- [ ] きほんの部屋は `availableRules` が空で固定される。**`RoomManagerOptions.availableRules` が非空を返す状態でも空**であること(この検証がこの切りの本体)。
- [ ] **2 セット目でモードが化けない**。`continue` / `expireSetResult` / `leave` を経ても、きほんの部屋の有効ルールは空のまま。
- [ ] モード未指定の `room:create`(旧クライアント)は `community` として扱われ、既存の挙動が変わらない。
- [ ] メニューの「あそぶ」→「きほんルールで練習する」できほんの部屋が作られ、待機室を挟まずに対局が始まる。→「みんなのルールであそぶ」→「部屋を立てる」でみんなのルールの部屋ができる。
- [ ] 並びは端末の既プレイ状態によらず常に同じ(タグ・並べ替えを行わない)。
- [ ] きほんの部屋の招待コードで入ろうとすると `ROOM_SOLO_ONLY` で拒否され、理由が伝わる文言が出る。

**テスト方針**:

## 5. リスク・未確定事項

**リスク**

1. **仕込み seed の効果が保証できない**(§2.4)。AI が時間予算付き探索で partial-search に落ちるため、場流れ・勝敗は再現しない。**保証できるのは静的条件だけ**であり、「はじめての 1 戦」の教育効果は設計が想定するより弱くなりうる。緩和はガイドの遭遇ベース設計(起きなければ出ないだけ)。**この前提が崩れる(=場流れを確実に起こしたい)なら、エンジンに配牌注入か AI の決定性モードが要る = 設計の変更**であり、そのときは E1/E2 へ戻す。
2. **条件を満たす seed が見つからない可能性**。♦3 + ペア + 強さ上位は同時に満たしやすいと見込むが、実測前に断定できない。フォールバックは V3-b の段階的緩和。
3. ~~**マルチプレイ時のモード互換が未確定**~~ → **2026-08-01 に解消**(C-10)。きほんを 1 人練習専用にし、入室は `ROOM_SOLO_ONLY` で拒否して理由を文言で伝える形にしたため、「招待コードだけではモードが分からない」も「きほんの部屋に経験者が入ったときの体験」も発生しなくなった。代わりに**素の大富豪の人間マルチを提供しない**というトレードオフを受け入れている(チュートリアル設計 §3)。
4. **タイマーなしの部屋が閉じない**。接続中の人間が放置すると `abandonAt` が働かず(§2.2)、部屋がメモリに残る。長い上限(例: 手番 30 分で自動退室)を置くか、`lobbyExpiresAt` に相当する上限を playing にも設けるかは未決。**きほん AI 戦は 1 人しか巻き込まないので優先度は低いが、放置を放置しない仕掛けは要る**。
5. **出せるカード案内をみんなのルールに広げるかが保留**(チュートリアル設計 §5)。提案ルールで合法手が複雑化したときの挙動と絡む。V2 ではきほん限定にしてフラグで広げられる形にする。
6. **契約変更を伴う**(`room:create` ペイロード・`PlayerRoomView`)。implementation-workorder §4-1 の「設計書に定義された契約は勝手に変えない」に該当するため、**着手前に開発者の承認を取る**。E03・E12 の該当記述の更新も要る(下記)。
7. **ガイド文言が増殖しやすい**。UI文言ガイド §0 の事故(設計メモをそのまま画面に載せる)がまさに起きやすい場所である。**7 個の cue すべてを実装する義務はない**。実画面で読み返して、消しても操作に失敗しないものは消す(同 §3 の削除テスト)。
