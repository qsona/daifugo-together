## 1. Epic 概要

### 1.1 目的

ルール提案の当事者性(「自分の一言がゲームを変える」)を、リリース瞬間の一度きりでなく**継続的な報酬**に変える(施策提案 §4 C-3)。提案者は自分のルールの「その後」——何卓で遊ばれ、どれだけ高評価され、いま何位か——を見に戻ってくる。

1. 自分の**リリース済み提案**の詳細(マイ提案画面のカード)に「遊ばれた卓数・高評価率・現在の優先順位」を表示する。
2. マイルストーン(閾値)到達時に E16 の予約種別 `stats_milestone` で通知する(週 1 上限)。

集計はすべて**既存テーブルの読み取り**で成立する(§2.2)。書き込み系の新規追加は、通知レコード(E16 の `notifications` テーブル)と閲覧計測の最小ログ(§2.6)に限る。

## 2. 技術仕様

### 2.1 【決定】コンセプト: 「数字はすでに DB にある。提案者の視点で束ねて見せる」

3 指標はいずれも実装済みテーブルから導出できる(2026-07-29 実コード確認)。鍵は `rules.proposal_id`(UNIQUE、`proposals.id` 参照)と `proposals.author_id` で、**提案者 → 提案 → ルール → 対局/評価**が既存スキーマだけで辿れること。E19 が足すのは集計クエリ・API のレスポンス拡張・画面表示・マイルストーン通知だけで、ゲーム・評価・パイプラインの挙動は一切変えない。

### 2.2 3 指標の算出(実スキーマに基づく)

| 指標 | 算出 | 源泉(実装済み) |
|---|---|---|
| **遊ばれた卓数** | `SELECT COUNT(*) FROM set_rules sr JOIN game_sets gs ON gs.id = sr.set_id WHERE sr.rule_id = ? AND sr.was_active = 1 AND gs.ended_at IS NOT NULL` — ルールが有効ルールとして固定され、終了(打ち切り含む)まで到達したセット数 | `set_rules(set_id, rule_id, was_active, did_fire, …)` は毎セット開始時に `EvaluationRepository.beginSet` が全有効ルール分を書き、`game_sets.ended_at/completion` は `completeSet` が確定する(`persistence.ts` の `commit`) |
| **高評価率** | `rules.rating_up / (rating_up + rating_down)` を百分率表示。分母 0 のときは「評価待ち」表示(0% と区別) | `rules.rating_up/rating_down` は評価保存のたびに `EvaluationRepository.#recomputePopularity` が **latest-wins のユーザー単位重複除去付き**で再集計・更新する(E09 PR-02 実装済み)。E19 独自の集計クエリは持たず、この列を読む |
| **現在の優先順位** | `priorityRank`(有効ルールを `popularity_score DESC, activated_at ASC, id ASC` で並べた 1 始まりの順位)。`status != 'active'`(disabled/removed)は `null` → 「—」表示 | `RuleRepository.priority()` / `#priorityRank` が実装済み(図鑑 API と同じ導出値)。DB に順位列は持たない(E09 §2.1 の設計どおり導出) |

- **不足データはない**。3 指標とも新規の記録開始を待たずに、リリース時点まで遡って正しい値が出る(`set_rules` はリリース後の全セットに書かれている)。
- 唯一の実装上の不足は**索引**: `set_rules` の既存索引は PK `(set_id, rule_id)` と `idx_set_rules_set_active(set_id, was_active)` のみで、`rule_id` 起点の COUNT に効く索引がない。`idx_set_rules_rule(rule_id, was_active)` を追加する(差分-1)。現規模ではフルスキャンでも動くが、毎表示・毎セット終了時(§2.4)に走るクエリなので先に足しておく。
- 「遊ばれた卓数」の定義は `was_active = 1`(卓に入った数)をデフォルトとし、`did_fire = 1`(実際に発動した卓数)への変更・併記は未決(PS-T2)。
- 鮮度は**表示時集計**(リクエスト時に SQL を打つ。キャッシュ・集計テーブルなし)をデフォルトとする(PS-T3)。

### 2.3 API(mine レスポンスの拡張)

新規エンドポイントは作らない。`GET /api/proposals/mine`(実装: `app-server.ts` → `ProposalSubmissionPort.mine` → `ProposalRepository.mine`)の各 item に、**`status = 'released'` かつ `rule_id` があるものだけ** `stats` を付ける。

```ts
// mine レスポンス item の拡張(released のみ。それ以外は stats なし)
stats?: {
  setsPlayed: number;        // 遊ばれた卓数(§2.2)
  ratingUp: number;          // 高評価数(rules.rating_up)
  ratingDown: number;        // 低評価数(rules.rating_down)
  priorityRank: number | null; // 現在の優先順位。非 active は null
  ruleStatus: 'active' | 'disabled' | 'removed';  // 「—」表示・排除注記の判定用
}
```

- 高評価**率**はクライアントで `ratingUp / (ratingUp + ratingDown)` から導出する(分母 0 の表示分岐があるため生の票数を返す)。
- 認証は既存の Bearer(匿名トークン)のまま。他人の提案のスタッツを返す口は作らない(集計値は図鑑でも見えるが、「自分の提案に束ねた表示」は本人のみ)。
- 1 リクエストあたりのクエリはリリース済み提案数ぶんの COUNT(+ `priority()` 1 回)。個人の提案数は高々数十で問題にならない。

### 2.4 マイルストーン通知(`stats_milestone`・週 1 上限)

E16 種別レジストリに 1 エントリ追加する(audience: `user`(提案者宛)、優先度: 中、チャネル: センター+Push(E17 実装後))。ペイロードは `{ proposalId, ruleId, ruleName, kind: 'rating' | 'sets', threshold: number }`、タップ遷移先はマイ提案(`/proposals/mine`)。表示名以外の個人情報を含めない(E16 §2.2 の規律)。

**マイルストーン系列(値は仮。PS-T1)**:

| 系列 | 判定 | 閾値(デフォルト案) |
|---|---|---|
| `rating` | `rules.rating_up` が閾値に到達(「あなたのルールが◯人に高評価」) | 3, 10, 30, 100 |
| `sets` | 遊ばれた卓数(§2.2)が閾値に到達(「あなたのルールが◯卓で遊ばれました」) | 10, 50, 100, 500 |

**判定タイミング(既存イベントに相乗り。ポーリングなし)**:

1. **評価保存後**: `app-server.ts` の評価ルートハンドラ(`handleEvaluation` → `EvaluationService.update`)の保存成功後に、対象ルールの `rating_up` が閾値を**跨いだか**確認(`rating` 系列)。
2. **セット確定後**: セット確定は `SqlitePersistence.commit()`(`persistence.ts`)の SQLite トランザクション内で `completeSet` が走るため、**コミット後にフック**し、そのセットの `set_rules(was_active=1)` の各ルールについて卓数閾値を確認(`sets` 系列)。

いずれも E16 の流儀(§2.4)に従い、リポジトリ層でなく**呼び出し元**に `NotificationService.publish()` を差し込む。`status = 'active'` のルールのみ判定対象(排除・停止済みルールには発行しない。PS-T5)。

**跨ぎ検知には前回値が要る**ことに注意: 実装は保存前後の値の比較(rating は 1 票ごとに ±1、sets は 1 セットごとに +1 しか動かないため、**更新後の値が閾値と等しいか**の等値判定で足りる)。「現在値 ≥ 閾値」方式は、週 1 上限で破棄した後の次イベントで同じマイルストーンを再送してしまい、PS-T4(破棄・後追いなし)と矛盾するので採らない(dedupe_key は再送を最終的に防ぐが、破棄分は notifications 行が無いため防げない)。

**冪等化と週 1 上限(専用テーブルなし。PS-D3)**:

- **到達済みの記憶** = E16 `notifications` の冪等キーに相乗りする。`dedupe_key = '{ruleId}:{kind}:{threshold}'` とすれば、同じマイルストーンは UNIQUE 索引 `(user_id, type, dedupe_key)` により二重発行されない。
- **週 1 上限** = 発行前に「その提案者の `stats_milestone` の直近 `created_at` が 7 日以内」なら**発行しない(破棄)**。上限はユーザー単位(ルール単位でない): 複数ルールを持つ提案者にも週 1 通まで。判定は `notifications` への SELECT 1 本で、状態テーブルは持たない。
- 破棄されたマイルストーンは**後追い送信しない**(デフォルト案。PS-T4)。数字自体はマイ提案画面でいつでも見えるため、通知は「呼び戻しのきっかけ」に徹し、キュー・再送機構という運用物を作らない。次の閾値に到達すれば(7 日空いていれば)また通知される。
- 複数閾値を一度に跨いだ場合は**最大の閾値 1 通だけ**発行する。通常運用では値は 1 ずつしか動かないため同時跨ぎは起きないが、閾値設定の変更や機能の遡及導入(既に閾値を大きく超えているルールへの初回判定)で起こりうるため、防御ルールとして置く。

### 2.6 計測(PS-D5)

- **通知経由の再訪**: E16 の `opened_at`(種別 `stats_milestone` で絞る)。E19 側の追加実装なし。
- **スタッツの再訪閲覧頻度**: マイ提案画面を開いたときに呼ばれる既存の `POST /api/proposals/seen` を計測点に使う。現状は `users.proposals_seen_at` の単一タイムスタンプ上書きで履歴が残らないため、**最小の閲覧ログ 1 テーブル**(`proposal_screen_views(user_id, viewed_at)` 相当。追記のみ・行は小さい)を追加し、seen 更新と同じ箇所で 1 行書く(PS-T6 で採否裁定。落選なら構造化ログ集計で代替)。30 日再訪率は `proposals.author_id` × このログ(または対局参加)の SQL で出す。当面ダッシュボード化せず E10 の流儀(CLI + SSH)で読む。

### 2.7 テスト戦略

- 集計: 遊ばれた卓数(未終了セット除外・was_active=0 除外)、高評価率の分母 0、priorityRank の非 active null。リリース前の提案に stats が付かないこと。
- 通知: 閾値到達で 1 件発行 / 同一マイルストーン再判定で冪等(dedupe_key)/ 7 日以内の 2 通目が破棄される / 7 日経過後は次の閾値で発行される / 複数閾値同時到達で最大 1 通 / 非 active ルールに発行されない。
- API: 認証(401)・他人の提案が混ざらない・released 以外に stats が付かない。
- クライアント: リリース済みカードのスタッツ表示分岐(評価待ち・「—」・排除注記)、375×812 の実画面で目視確認(既存 Epic と同じ検証水準)。
- E16 未実装環境(PS-01 単独先行時)でも表示系が壊れないこと(PS-02 は E16 NC-01 完了後に着手)。

## 3. ストーリー詳細・受け入れ条件

### PS-01: 自分のリリース済み提案に 3 指標が表示される

「提案者として、自分のルールが何卓で遊ばれ、どれだけ高評価され、いま何位なのかを、マイ提案からいつでも見たい」

受け入れ条件:

- [ ] `GET /api/proposals/mine` のリリース済み item に `stats`(setsPlayed / ratingUp / ratingDown / priorityRank / ruleStatus)が付き、released 以外には付かない
- [ ] 遊ばれた卓数が §2.2 の定義(was_active=1 かつ終了済みセット)で一致する(自動テストで境界を確認)
- [ ] 高評価率が `rules.rating_up/rating_down`(latest-wins 重複除去済みの値)と一致し、評価 0 件では「評価待ち」表示になる
- [ ] 現在の優先順位が図鑑(`priorityRank`)と同じ値で、排除・停止済みルールでは「—」+ 状態注記になる
- [ ] 匿名ユーザー(E15 未登録)でも自分の提案のスタッツが見える
- [ ] 375×812 の実画面でリリース済みカードの表示一式を目視確認

### PS-02: マイルストーン到達で通知が届く(週 1 上限)

「提案者として、自分のルールが節目(◯人に高評価・◯卓で遊ばれた)に達したら、アプリを開いていなくても知りたい。ただししつこくは要らない」

受け入れ条件:

- [ ] E16 種別レジストリに `stats_milestone` が登録され、評価保存後・セット確定後の判定(§2.4)で到達時に通知が作成される
- [ ] 同一マイルストーンが二重発行されない(dedupe_key)。複数閾値の同時到達は最大の 1 通のみ
- [ ] 同一提案者への `stats_milestone` は 7 日に 1 通まで。上限で破棄されたものは再送されない
- [ ] 排除・停止済み(非 active)ルールでは発行されない
- [ ] 通知タップでマイ提案画面へ遷移し、E16 の `opened_at` が記録される
- [ ] 通知側の失敗が評価保存・セット確定の成否に影響しない(E16 NC-01 と同じ担保)
