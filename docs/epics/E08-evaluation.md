## 1. Epic 概要

### 1.1 目的

セット(3 戦)ごとの評価を集め、**つまらないルールを自動で排除する**ことで、増え続けるルールが「面白いカオス」から「ただの遊びにくさ」へ劣化するのを防ぐ(企画書 §4.4・§8)。あわせて、集めた高評価・低評価は E9(人気度・優先順位)への入力になる。

この Epic は「評価データの受け皿を作る」ことと「その評価をもとに排除を判断・実行する」ことの 2 つを担う。**人気度の算出式そのものは E9(PR-02)の責務であり、この Epic では扱わない**(§1.3)。

### 1.2 担当ストーリー

| ID | 概要 | 依存 | 本書での節 |
|---|---|---|---|
| EV-01 | セット終了時に「面白かったか」を答える(セット単位評価) | GE-05 | §3.1 |
| EV-02 | セットで発動したルールに高評価/低評価を付ける(ルール単位評価) | EV-01, CX-06 | §3.2 |
| EV-03 | 低評価が集まったルールを自動で排除する | EV-02, CX-04 | §3.3 |

企画書 §9-2「ルール排除の基準(閾値・恒久/復活)」は **EV-03 が方針決定ごと引き受け、本書 §3.3 で具体案を起草する**(バックログ §5 対応表)。

### 1.3 他 Epic との接続

## 2. Epic 横断の技術仕様

### 2.1 前提となるセット/対局結果データ(E1・E3 が書き込む)

E8 の評価は **セットを単位**に紐づく(企画書 §4.4「1 セット(3 戦)ごと」)。評価を成立させるため、セット終了時に E1/E3 が書く対局結果に、以下が含まれている必要がある(E12 §4.4「対局結果」の具体化。§5 で E12 への追記を提案)。

```
game_sets                       -- 1 セット = 1 行(セット終了時に確定)
  id            TEXT PK          -- setId(uuid)
  room_id       TEXT            -- 招待コード等(参照用・任意)
  started_at    INTEGER         -- unix ms
  ended_at      INTEGER
  standings     TEXT (JSON)     -- 4 席分の総合順位(AI 含む・氏名/isAi つき。画面 5b 表示用)

set_participants                -- セットの「人間」参加者(= 評価できる主体)
  set_id        TEXT FK
  user_id       TEXT FK
  PRIMARY KEY (set_id, user_id)
  -- AI 席はここに入れない(AI プレイヤーは user を持たない前提)。これにより
  -- 「AI は評価しない」がデータ構造上そのまま成立する。この前提は E1/E3 への
  -- 要求として §5.2 提案#2 に明記する(E12 §4.9 は AI の非アカウント化を明文化していない)。

set_rules                       -- セットに紐づくルールのスナップショット
  set_id        TEXT FK
  rule_id       TEXT FK
  was_active    INTEGER(bool)   -- セット開始時に有効ルールセットへ固定されていたか(EV-01 用)
  did_fire      INTEGER(bool)   -- 3 戦のいずれかで実際に発動したか(EV-02 の投票対象。CX-06 由来)
  PRIMARY KEY (set_id, rule_id)
```

- `was_active` は EV-01(「そのとき有効だったルールに紐づけて保存」)の根拠。`did_fire` は EV-02(「発動したルールに限る」)の投票対象リスト。
- レジストリはセット開始時にルールセットを固定する(E12 §4.6(4))ので、`was_active` はセット開始時点で確定する。`did_fire` は 3 戦を通して発動ログ(CX-06)を集約し、セット終了時に確定する。

### 2.2 評価データモデル(この Epic が新設する)

```
set_evaluations                 -- EV-01: セット単位の「面白かったか」
  id            TEXT PK
  set_id        TEXT FK -> game_sets.id
  user_id       TEXT FK -> users.id
  rating        TEXT            -- 'fun' | 'neutral' | 'boring'
  created_at    INTEGER
  UNIQUE (set_id, user_id)      -- ★重複評価の防止:1 人 1 セット 1 回

rule_evaluations                -- EV-02: ルール単位の高評価/低評価
  id            TEXT PK
  set_id        TEXT FK -> game_sets.id
  user_id       TEXT FK -> users.id
  rule_id       TEXT FK -> rules.id
  vote          TEXT            -- 'up'(高評価) | 'down'(低評価)
  created_at    INTEGER
  UNIQUE (set_id, user_id, rule_id)  -- ★同一セット内で同一ルールへの二重投票を防ぐ
  INDEX (rule_id, vote)         -- 集計(EV-03)と人気度読み取り(E9)の索引

rule_eliminations               -- EV-03: 排除履歴(§3.3)
  id             TEXT PK
  rule_id        TEXT FK -> rules.id
  eliminated_at  INTEGER
  trigger_set_id TEXT FK        -- 閾値超えの引き金になった評価送信のセット
  stats_snapshot TEXT (JSON)    -- { up, down, n, wilsonLower, theta, nMin, z } 排除時点の値
  reason         TEXT           -- 既定 'evaluation_threshold'
  reverted_at    INTEGER NULL   -- 運営が手動復活させた場合のみ
  revert_reason  TEXT NULL
```

- ORM は E12 に合わせて **Drizzle**(スキーマが TS の型になる)。`rating` / `vote` / `status` は文字列 enum + アプリ層のユニオン型で表現する。
- **`rules` テーブル**(E12 §4.4 が定義)には既に `status`(`有効` | `無効` | `排除済み`)・`人気度`・`優先度` がある。EV-03 は `status` を `排除済み` に更新する。**`無効` は CX-04 の運用停止(バグでのロールバック中など)、`排除済み` は評価淘汰**、という provenance の違いで使い分ける(§3.3・§5 で E12 へ明記を提案)。どちらもレジストリが読み込まないのは同じ。

### 2.3 重複評価の防止(まとめ)

3 層で担保する。

1. **DB の UNIQUE 制約**: `set_evaluations(set_id, user_id)` と `rule_evaluations(set_id, user_id, rule_id)`。最終防衛線。
2. **API の事前チェック**: 送信時に `set_evaluations` に当該 (set_id, user_id) が既にあれば `409 Conflict`(§3.1 (d))。
3. **参加者チェック**: `set_participants` に user_id が無ければ受け付けない。AI は user を持たないので構造的に弾かれる。

再送・二重タップは (1)(2) で冪等に扱う(最初の 1 件のみ保存)。UI 上のトグル(高評価↔低評価の付け替え)は**送信前のクライアント状態**であり、サーバーは「送信」時点の最終ペイロードだけを 1 トランザクションで受ける(画面 5b は評価一式を 1 ボタンで送る設計)。

### 2.4 集計ジョブの設計(いつ・どこで)

| 論点 | 決定 |
|---|---|
| **起点(いつ)** | 評価送信 API のトランザクション commit **直後**。バッチ待ちにせず、送信を引き金にする(企画書 §4.4「評価送信を起点にバックエンドで淘汰が走る」/ wireframes 冒頭「バックエンド処理と起点」)。 |
| **対象** | その送信に含まれた `rule_evaluations` の対象ルールだけ(= up か down が付いたルール)。全ルール再スキャンはしない。 |
| **処理** | 各対象ルールについて**有効化ウィンドウ内**の `rule_evaluations` を集計し `(up, down)` を得る → `shouldEliminate()`(§3.3)で判定 → **現在 `status='有効'` かつ真なら排除実行**(status を `排除済み` にし、`rule_eliminations` に 1 行追記)。`status='無効'`(CX-04 の運用停止中)・`排除済み` のルールは status ガードで排除実行しない(no-op。意図どおり:運用停止中のルールを評価淘汰で二重に外さない)。 |
| **実行場所(どこで)** | **ゲームサーバープロセス内**。pipeline ワーカー(codex 実装用)ではない。単一 Node プロセス・単一 SQLite writer(E12 §3)なので、プロセス間競合はなく、排他制御は不要。 |
| **同期/非同期** | 対象ルールごとに索引付き `GROUP BY` 数本で済む(書き込み頻度は毎秒数件以下、E12 §4.4)ため、**commit 後に同期実行で十分**。応答性が気になれば「送信の応答を返した後に in-process の軽量キューで処理」に寄せられる(初期は同期でよい/過剰なジョブ基盤は入れない)。 |
| **冪等性** | 排除実行の前に必ず `status='有効'` を確認する。二重発火しても 2 度目は no-op(既に `排除済み`)。 |
| **集計の持ち方** | 都度 `SELECT vote, COUNT(*) ... WHERE rule_id=? AND created_at > :windowStart GROUP BY vote`(索引 `(rule_id, vote)`)で算出。ドリフトを避けるため**集計テーブルは持たない**(必要になってから `rule_vote_stats` ロールアップを足す。初期は不要)。 |
| **有効化ウィンドウ(復活対応)** | `:windowStart = 当該ルールの最新 rule_eliminations.reverted_at`(復活履歴が無ければ 0 = 全票)。**手動復活したルールは復活時刻より後の票だけで再評価される**ため、復活直後に旧累積(例 20up/80down・wilsonLower=0.711)を読み直して即再排除される事故を防ぐ(§3.3 b-4)。観測用の `getRuleVoteStats`(§3.2)はウィンドウを掛けない生集計で、用途が別(人気度算出は E9 が `rule_evaluations` を直接集計する。E09 §5.4)。 |
| **フルスキャン(保険・任意)** | 閾値パラメータ(θ・N_min)を変更したときに全ルールを再判定するための手動トリガ(または日次ジョブ)を 1 つ用意。OP-04 のチューニング反映に使う。通常運用では走らない。 |

**E9 との分離**: 人気度の更新は PR-02 の集計が担う。E8 の集計ジョブは**排除判定だけ**を行い、人気度・優先度には触れない。両者は同じ `rule_evaluations` を読むが、責務が分かれている。

## 3. ストーリー別詳細仕様

### 3.1 EV-01: セット終了時の評価(セット単位)

#### (a) 原文引用(product-backlog.md)

> **[EV-01]** プレイヤーとして、1 セット(3 戦)終わるごとに「面白かったか」を答えたい。それはカオスが楽しめているかどうかを、みんなの声で測る入力だからだ。
> - 受け入れ条件:
>   - セット終了時(総合結果の表示)に評価の入力が表示される(ゲーム間の簡易リザルトでは評価を求めない §3.4・§4.4)
>   - 評価が当該セットとそのとき有効だったルールに紐づいて保存される
>   - 保存された評価が集計の対象になる

#### (b) 挙動仕様

- セット(3 戦)の最終戦が終わると画面 5b(セットリザルト+評価)に遷移し、3 択(`おもしろかった` / `ふつう` / `つまらなかった`)を提示する。
- 選択は **1 人 1 セット 1 回**。EV-02 のルール単位評価と**同一の「評価を送信」操作でまとめて送る**(画面 5b は 1 ボタン送信)。
- 評価は当該 `set_id` に紐づく。「そのとき有効だったルール」との紐付けは、セットの `set_rules(was_active=true)` を経由して間接的に成立する(評価行ごとにルール ID を持たせない)。
- **エッジケース**:
  - **AI プレイヤー**: user を持たず `set_participants` に入らないため、評価は構造上できない(追加のガード不要)。
  - **未入力(送信せず離脱)**: 評価は**任意**。送信しなければ行は作られず、そのセットの評価が 1 件少なくなるだけ。ペナルティも督促もなく、集計はある分だけで進む。何もブロックしない。
  - **途中離脱者**: セット途中で切断し AI 代打ちに替わった人間(E3 の再接続猶予)も `set_participants` には残る。ただし画面 5b は「セット終了時に接続している人間」に表示されるため、離脱したまま戻らなければ評価は送られない。復帰していれば送信できる。
  - **送信ウィンドウ**: 対局状態はメモリのみ(E12 §3)だが `set_participants` は永続化されるので、専用トークンは不要。**`ended_at + TTL`(既定 60 分)まで**、参加者本人の認証トークンで送信を受け付け、以降は締め切る(遅延票は価値が低く、無制限に開けない)。TTL は設定値。

#### (c) 画面仕様(5a / 5b)

- **画面 5a(ゲーム間リザルト・第 1/2 戦後)**: 評価入力は**置かない**。順位のみの簡易リザルトでテンポよく次戦へ(企画書 §3.4、wireframes 画面 5a 注記 mk1・「評価はセットの最後にまとめて行う」)。E8 は 5a に対して「ここでは評価を集めない」ことだけを規定する。
- **画面 5b(セットリザルト+評価・第 3 戦後)**: 上部に総合結果、その下の「このセットはおもしろかった?」ボックスがこのストーリーの UI(wireframes 画面 5b mk2)。3 セグメントの単一選択。送信ボタンは EV-02 と共有。

#### (d) API・データ定義

EV-01 と EV-02 は **1 エンドポイントで同時送信**する(画面 5b の「評価を送信」1 ボタンに対応)。

```
POST /api/sets/:setId/evaluation
Authorization: <user token>(匿名 ID・E12 §4.9)

Request body:
{
  "setRating": "fun" | "neutral" | "boring",     -- EV-01(必須)
  "ruleVotes": [                                  -- EV-02(任意・空配列可)
    { "ruleId": "r0042-yagiri", "vote": "up" },
    { "ruleId": "r0031-miyakoochi", "vote": "down" }
  ]
}

Responses:
  200 OK        受理(set_evaluations + rule_evaluations を 1 tx で保存 → 集計起動)
  409 Conflict  (setId, userId) の set_evaluations が既に存在(重複送信)
  403 Forbidden user が set_participants に含まれない / 送信ウィンドウ超過
  422 Unprocessable  ruleVotes に「発動していないルール」が含まれる(§3.2)
```

保存先: `set_evaluations`(§2.2)。`rating` の enum は `'fun' | 'neutral' | 'boring'` で、画面表示語(おもしろかった/ふつう/つまらなかった)とアプリ層でマップする。

#### (e) 実装方針

- セット終了時、E1/E3 が `game_sets` / `set_participants` / `set_rules` を書く(§2.1)。E8 はこれらが揃っている前提で送信 API を実装する。
- 送信ハンドラ: (1) 認証 → (2) `set_participants` で参加者確認 → (3) 送信ウィンドウ確認 → (4) 既存 `set_evaluations` 確認(409)→ (5) `ruleVotes` の各 ruleId が `set_rules(did_fire=true)` に含まれるか検証(422)→ (6) `set_evaluations` + `rule_evaluations` を 1 トランザクションで挿入 → (7) commit 後に集計ジョブ(§2.4)を起動。
- `setRating` 自体は**排除判定には使わない**(§3.3 の設計判断参照)。E10 の「面白かった」率(OP-03)と、ルール構成との相関観測に使う。

#### (f) 受け入れ条件の精緻化

1. 第 3 戦終了時のみ画面 5b で `setRating` の入力が表示され、第 1/2 戦後の画面 5a では表示されない(自動テストで両分岐を確認)。
2. 送信すると `set_evaluations` に (set_id, user_id, rating) が 1 行保存され、`set_rules(was_active=true)` 経由で当該セットの有効ルールを辿れる。
3. 同一 (set_id, user_id) の 2 回目送信は 409 で拒否され、1 件目のみが残る。
4. `set_participants` に無い user(AI 相当・非参加者)からの送信は 403。
5. 未送信のセットが存在しても、他プレイヤーの集計・次セット開始をブロックしない。

#### (g) 未解決事項

- 送信ウィンドウ TTL(既定 60 分)の妥当値は E3 の「切断・離脱の確定条件」と合わせて最終決定(§5)。
- 「未入力理由」の記録は**しない**(価値に対し複雑さが見合わない)。この判断を確定とみなす。

### 3.2 EV-02: ルール単位の高評価/低評価

#### (a) 原文引用(product-backlog.md)

> **[EV-02]** プレイヤーとして、セットで発動したルールに名指しで高評価・低評価を付けたい。それは「面白いカオス」と「ただの遊びにくさ」をプレイヤー自身が選別し、残したいルールを残すためだ。
> - 受け入れ条件:
>   - そのセットで発動したルールの一覧(CX-06)から対象を選び、高評価・低評価のどちらも付けられる(対象は発動したルールに限る §4.4)
>   - 評価が高評価/低評価の別つきでルール単位に記録される
>   - 高評価・低評価の両方が人気度の算出(PR-02)の入力として参照できる

#### (b) 挙動仕様

- 画面 5b に、**当該セットで発動したルール**(`set_rules(did_fire=true)`。発動ログは CX-06 由来)だけを一覧する。有効だが未発動のルールは出さない(見ていないものは評価させない = ballot stuffing 防止)。
- 各ルールに `高評価` / `低評価` / (無指定)の 3 状態。無指定は「意見なし」で、行を作らない(neutral という別値は持たない)。
- 高評価・低評価は**どちらも付けられる**(低評価だけではない。企画書 §4.4)。
- **対象は発動ルールに限る実装**: サーバー側で `ruleVotes[].ruleId ∈ set_rules(did_fire=true)` を検証し、外れたものは 422 で拒否する(クライアント表示だけに頼らない)。
- **エッジケース**:
  - **投票対象ルールが評価時点で既に排除済み**: セット固定後に他セットの評価で当該ルールが排除されることはありうる。それでも「自分の体験に対する票」は有効な入力・履歴なので**記録する**(ルールの現 status は問わない)。排除済みルールへの高評価が記録されても自動復活はしない(§3.3)。
  - **同一ルールへの二重投票**: `UNIQUE(set_id, user_id, rule_id)` で防止。UI のトグルは送信前のクライアント状態で、送信は最終値のみ。
  - **発動ルールが 0 件**(素の大富豪だけで基本ルールしか動かなかった等): `ruleVotes` は空配列。EV-01 のセット評価だけが送られる。

#### (c) 画面仕様(5a / 5b)

- **画面 5a**: ルール単位評価も**置かない**(簡易リザルト)。
- **画面 5b**: 「このセットで発動したルールを評価」ボックス(wireframes 画面 5b mk3)。行ごとに `ルール名` + `高評価`/`低評価` ボタン。ワイヤーの例(8切り=高評価済み、革命返し=低評価済み、都落ち=未指定)がそのまま状態表現になる。「対象はこのセットで発動したルールのみ・低評価が集まると排除・評価は人気度にも反映」というキャプションを添える(既にワイヤーに記載)。

#### (d) API・データ定義

#### (e) 実装方針

#### (f) 受け入れ条件の精緻化

### 3.3 EV-03: 低評価が集まったルールの自動排除(§9-2 の解決案)

#### (a) 原文引用(product-backlog.md)

> **[EV-03]** 開発者(運営)として、低評価が集まったルールを自動で排除したい。それはつまらないルールの蓄積でカオスが遊びにくさに変わるのを防ぎ、淘汰を機能させるためだ。
> - 受け入れ条件:
>   - 排除の閾値と方式(恒久か、復活があるか)が決定・文書化され、そのとおり実装されている
>   - 閾値を超えたルールがゲームから外れる(CX-04 の無効化機構を使う)
>   - 排除されたルールの履歴が残り、参照できる

企画書 §9-2:「低評価がどの程度集まったら排除するか。排除は恒久か、復活があるか。」← **本節で解決案を確定する。**

#### (b) 挙動仕様(概要)

評価送信のたびに、投票が付いたルールの累計票を集計し、**閾値式**を満たしたルールを `排除済み` にする。排除は次に始まるセットから効く(進行中セットは影響を受けない)。以下、閾値式・恒久/復活・実行機構・履歴の順に定める。

#### (b-1) 排除の閾値式(統計的配慮つき)

**入力**: 対象ルールの全 `rule_evaluations` を集計した `up`(高評価数)・`down`(低評価数)。復活歴のあるルールは有効化ウィンドウ内の票のみ(§2.4)。
**分母**: `n = up + down`(明示投票のみ。無投票は「意見なし」で数えない)。低評価割合 `p̂ = down / n`。

**素朴案の問題**: 「`down ≥ N` で排除」や「`p̂ > X%` で排除」は、**票が少ないルールを誤排除する**。例:1 セットで発動して 1 低評価だけ付いたルールは `p̂ = 100%` で即排除されてしまう(企画書 §9-2 で懸念される事態そのもの)。少数サンプルへの統計的配慮が必要。

**採用案: 最小票数ゲート + Wilson スコア下側信頼限界**。低評価割合 `p̂` の **Wilson 下側信頼限界**が閾値 θ を超えたときだけ排除する。Wilson 下限は**票が少ないほど区間が広く、下限が下がる**ため、サンプルが薄いルールは自動的に排除されにくい(= 誤排除しない統計的配慮が式に内在する)。

排除条件(両方を満たす):

1. `n = up + down ≥ N_min`(最小票数ゲート。既定 **10**)— 票が薄いルールを構造的に除外する明示ガード。
2. `wilsonLower(down, n, z) ≥ θ`(既定 θ = **0.70**, z = **1.96**)— 「低評価割合が真に 70% 以上」と統計的に確からしい場合のみ。

```ts
// packages/server/src/evaluation/elimination.ts

/** 低評価割合 down/n の Wilson スコア下側信頼限界 */
export function wilsonLowerBound(down: number, n: number, z = 1.96): number {
  if (n === 0) return 0;
  const p = down / n;
  const z2 = z * z;
  const denom = 1 + z2 / n;
  const center = p + z2 / (2 * n);
  const margin = z * Math.sqrt((p * (1 - p) + z2 / (4 * n)) / n);
  return (center - margin) / denom;
}

export interface EliminationParams {
  nMin: number;   // 最小票数(既定 10)
  theta: number;  // 低評価割合の下限しきい値(既定 0.70)
  z: number;      // 信頼係数(既定 1.96 ≒ 片側 97.5%)。上げるほど排除は保守的
}

export const DEFAULT_ELIMINATION_PARAMS: EliminationParams = { nMin: 10, theta: 0.70, z: 1.96 };

export function shouldEliminate(
  up: number, down: number, params: EliminationParams = DEFAULT_ELIMINATION_PARAMS,
): boolean {
  const n = up + down;
  if (n < params.nMin) return false;                       // 票が薄いルールは誤排除しない
  return wilsonLowerBound(down, n, params.z) >= params.theta;
}
```

**挙動の確認(既定パラメータ)**:

| up | down | n | p̂ | wilsonLower | 判定 | 意味 |
|---|---|---|---|---|---|---|
| 0 | 1 | 1 | 1.00 | — | 非排除(n<10) | 1 票だけでは絶対に排除しない |
| 0 | 10 | 10 | 1.00 | ≈0.72 | **排除** | 10 連続低評価は排除 |
| 2 | 8 | 10 | 0.80 | ≈0.49 | 非排除 | 80% でも 10 票では確信が足りない |
| 20 | 80 | 100 | 0.80 | ≈0.71 | **排除** | 80% 低評価が 100 票で安定したら排除 |
| 40 | 10 | 50 | 0.20 | 低い | 非排除 | 高評価多数のルールは残る |

**θ の読み方(キャリブレーションの出発点)**: θ=0.70 は**観測低評価率そのものではなく、下側信頼限界に対する閾値**である。観測上の低評価率に換算すると、下限が 0.70 に達するには **n=10(N_min)付近では実質 100%、n=100 で約 79%** の低評価が必要になる(n がさらに増えれば 70% に漸近)。つまり初期設定は**過少排除寄り(残す方向に安全)**であり、OP-04 のキャリブレーションはここを起点に、「排除が起きなさすぎる」なら θ・N_min を下げる方向で調整する。

**パラメータの置き場所**: `EliminationParams` は環境変数 or 設定テーブルから読み、コードにハードコードしない。OP-04 が「面白かった率が下がった/排除されすぎ」を見て θ・N_min・z を調整できるようにする。デフォルトは実データが無い初期の暫定値であり、**運用開始後にキャリブレーションが必要**(§5)。

**設計判断: セット評価(setRating)は排除に使わない**。`つまらなかった` はセット全体への評価で、どのルールが原因かを特定できない(発動ルールが複数ある)。排除は**ルール単位の低評価(rule_evaluations.down)のみ**を根拠にし、帰属を明確に保つ。セット評価は E10 の健全性指標(面白かった率)に回す。

#### (b-2) 恒久排除か、復活ありか(推奨と理由)

**推奨: 恒久排除を基本とし、自動復活はしない。運営による手動復活の口だけ残す。**

理由:

1. **自動復活は入力データが存在しない**。排除されたルールは以後発動しない → 新たな評価が付かない。よって「票が改善したら自動で戻す」判断材料が原理的に得られない。自動復活を作るなら「一定期間ルールを強制的に対局へ再投入して再審査する」別機構が要り、スケジューリング・強制ルールセット混入・再検証の複雑さに見合わない(**新規提案が無尽蔵に供給される**本企画では、古いルールを掘り起こす必要が薄い)。
2. **予測可能性と図鑑の意味**。排除 →(自動)復活 → 再排除のちらつきはプレイヤーを混乱させる。恒久にすることで図鑑の「排除済み」が「みんなに一度否決された」という明確な履歴になる(§11 の淘汰観測にも合う)。
3. **誤排除リスクは閾値側で既に緩和**済み(Wilson + 最小票数で、持続的な低評価合意がないと排除されない)。稀な誤排除には**運営の手動復活**(status を `有効` に戻す。同じ CX-04 のフラグ操作)を逃げ道として残す。これは自動経路ではなく稀な運営操作であり、OP-04 の「対応手順」に位置づく。

したがって状態モデルは次の 3 値(E12 §4.4 の `status` をそのまま使う):

| status | 意味 | 設定者 | レジストリ読込 | 復帰 |
|---|---|---|---|---|
| `有効` | 対局で発動する | 既定・運営・手動復活 | する | — |
| `無効` | 運用停止(バグ/ロールバック中) | CX-04(運用) | しない | 運営が再有効化 |
| `排除済み` | 評価淘汰で外れた | **EV-03(自動)** | しない | 原則しない(稀に運営が手動復活) |

`無効` と `排除済み` は**どちらもレジストリが読み込まない**点は同じで、**なぜ外れたか(provenance)と図鑑表示・§11 の排除カウント**で区別する。

#### (b-3) 排除の実行機構(CX-04 の無効化フラグ利用)

- EV-03 は独自の停止機構を作らず、**CX-04 が公開する無効化サービスを呼ぶ**。イメージ:

```ts
// CX-04(E7)が提供する想定のサービス。EV-03 はこれを status='排除済み' で呼ぶ。
disableRule({ ruleId, nextStatus: '排除済み', reason: 'evaluation_threshold' });
```

- 実体は **DB の `rules.status` を 1 つ更新するだけ**(E12 §4.6(4)「有効化/無効化 = DB のフラグ 1 つ。次に始まるセットから反映。サーバー再起動なし」)。バンドルの差し替えやコード revert は伴わない(排除はコードを消すのではなく「読み込まない」だけ)。バンドルは図鑑表示と将来の手動復活のために残す。
- **反映タイミング**: レジストリはセット開始時に有効ルールを固定する(E12 §4.6(4))。よって排除は**次に始まるセットから有効**になり、進行中セットのルール構成は変わらない(E12 の「セット単位でルールセットが確定」と整合。EV-01 の評価紐付けにも都合がよい)。

#### (b-4) 排除履歴

- 排除実行時に `rule_eliminations`(§2.2)へ 1 行追記する: `rule_id` / `eliminated_at` / `trigger_set_id`(引き金の評価送信のセット)/ `stats_snapshot`(排除時点の up・down・n・wilsonLower・θ・N_min・z)/ `reason`。
- `stats_snapshot` を残すのは、後から「なぜこの票数で排除されたか」を監査でき、OP-04 のパラメータ調整の根拠になるため。
- 手動復活時は同じ行に `reverted_at` / `revert_reason` を書き、`rules.status` を `有効` に戻す。履歴は追記のみ(削除しない)。図鑑(画面 8)と OP-03「排除されたルール数の推移」はこの表を参照する。
- **復活後の再集計は `reverted_at` より後の票のみを対象にする**(§2.4 の有効化ウィンドウ)。これをしないと、旧累積の低評価(排除に至った票)を読み直して**次の 1 票で即座に再排除**されてしまい、手動復活が実質機能しない。復活時刻より後に、改めて N_min 以上の持続的低評価が集まった場合のみ通常どおり再排除され、新しい `rule_eliminations` 行が追記される。

#### (c) 画面仕様(5a / 5b)

- EV-03 は**専用の入力画面を持たない**(バックエンド処理)。起点は画面 5b の「評価を送信」(wireframes 冒頭「評価集計と淘汰」の起点)。
- 排除の**可視的な結果**は画面 8(ルール図鑑)の `排除済み` バッジ + 「低評価が集まったため排除」表示(wireframes 画面 8 mk2、担当は E11/RV-02)。E8 は状態と履歴を供給し、図鑑がそれを描く。
- 画面 5a / 5b 自体に排除の UI 要素は無い(5b のキャプションで「低評価が集まったルールは排除される」と予告するのみ。既にワイヤー記載)。

#### (d) API・データ定義

- **排除はサーバー内部処理で、公開 API を持たない**(自動)。
- **運営の手動復活**(逃げ道)だけ内部/管理 API を用意:

```
POST /api/admin/rules/:ruleId/reinstate     (運営認証。認証基盤は E10/§5)
  body: { reason: string }
  効果: rules.status = '有効' に戻す + rule_eliminations に reverted_at/revert_reason 追記
```

- データ: `rule_eliminations` 追記、`rules.status` 更新(§2.2)。

#### (e) 実装方針

- 集計ジョブ(§2.4)の中で、有効化ウィンドウ内(最新 `reverted_at` より後、無ければ全票)の `(up, down)` に対し `shouldEliminate(up, down, params)` を呼び、真かつ `status='有効'` のときだけ `disableRule(..., '排除済み', ...)` と履歴追記を**1 トランザクション**で行う。
- `EliminationParams` は設定から注入(テスト時はパラメータを差し替えて境界を検証できる)。
- 手動フルスキャン(§2.4)は同じ `shouldEliminate` を全 `有効` ルールに適用する薄いスクリプト。パラメータ変更時のみ運営が実行。

#### (f) 受け入れ条件の精緻化

1. `shouldEliminate` が §b-1 の表(1票=非排除、10連続低評価=排除、20/80=排除、高評価多数=非排除)どおりに判定する(ユニットテスト)。
2. 閾値を超えた瞬間、`rules.status` が `排除済み` になり、`rule_eliminations` に snapshot 付きで 1 行残る。
3. 排除は**次セットから**反映され、進行中セットには影響しない(レジストリのセット開始固定を確認)。
4. 排除はコード/バンドルを消さず、DB フラグのみで行われる(バンドル参照は残存)。
5. 図鑑(画面 8)で `排除済み` として参照でき、OP-03 が排除数を集計できる。
6. 運営の `reinstate` で `有効` に戻り、履歴に `reverted_at` が残る。

#### (g) 未解決事項

- **既定パラメータ(θ=0.70, N_min=10, z=1.96)の妥当値**は実データが無いため暫定。稼働後、排除率と面白かった率を見て OP-04 でキャリブレーションする(§5)。
- **手動復活 API の認証**は E10 の運営者認証基盤に依存(§5)。それが無い初期は「DB を直接操作 + 手順書」でも成立する(過剰な管理画面を先に作らない)。
- 無投票を人気度の分母に含めるか(E9 側の論点)は §3.2 (g) と同じ。排除判定は明示投票のみなので E8 内では未決を残さない。

## 4. テスト観点

### 4.1 データモデル・重複防止

### 4.2 EV-01
- 画面 5a では評価入力が出ず、画面 5b でのみ出る(分岐テスト)。
- 未送信のセットがあっても集計・次セット開始をブロックしない。
- `set_evaluations` から `set_rules(was_active=true)` を辿って有効ルールを取得できる。

### 4.3 EV-02
- 投票対象が `set_rules(did_fire=true)` に限定され、未発動ルール ID を含む送信が 422。
- up/down が正しく記録され、`getRuleVoteStats()` が正しい集計を返す。
- 発動ルール 0 件でも EV-01 単独送信が成立する。
- 排除済みルールへの票も記録される(が自動復活はしない)。

### 4.4 EV-03 閾値式
- `wilsonLowerBound` の数値が既知値(§b-1 の表)と一致する(n=1/10/50/100 の各ケース)。
- `n < N_min` では常に非排除(誤排除しない統計的配慮の検証)。
- 持続的低評価(20/80 等)で排除、高評価多数で非排除。
- パラメータ(θ・N_min・z)を差し替えると判定が期待どおり動く。

### 4.5 EV-03 実行・履歴・冪等性
- 閾値超えで `status='排除済み'` + `rule_eliminations` 追記が 1 tx で起きる。
- 既に `排除済み` のルールに再度集計が走っても二重排除しない(no-op)。
- 排除が**次セットから**反映され、進行中セットに影響しない。
- `reinstate` で `有効` に戻り、履歴に `reverted_at` が残る。
- **手動復活後、旧累積が閾値超えでも次の投票 1 件では再排除されない**(集計が `reverted_at` より後の票に限定される)。復活時刻より後に N_min 以上の持続的低評価が新規に集まれば再排除され、新しい履歴行が追記される。
- `status='無効'`(CX-04 停止中)のルールは、票が閾値を超えても排除実行されない(status ガードで no-op・意図どおり)。

### 4.6 集計ジョブ・結合
- 評価送信の commit 後に集計が起動し、送信に含まれたルールだけが判定対象になる。
- 集計が pipeline ワーカーでなくゲームサーバープロセス内で動く。
- 排除が CX-04 の無効化機構(DB フラグ)を使い、バンドルを差し替えない。
- 排除判定が E9(人気度)に依存せず単独で成立する(PR-02 未実装でも EV-03 が動く)。
