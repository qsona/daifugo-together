# レビューガイド

このプロジェクト「みんなでつくろう 大富豪」の実装レビューを担当していただきます。実装担当には [implementation-guide.md](implementation-guide.md) を渡してあり、あなたはそれとは独立した立場で入ります。

前提として一番大事なこと:

> **実装担当は、未決事項に当たったら止まらずに「仮定を置いて」進めています。その仮定の妥当性を裁定するのが、このレビューの中心的な仕事です。**

## 1. 独立性

- 実装セッションの結論・自己評価・言い分は渡されません。**リポジトリだけを見て判断してください。**
- 実装担当の申告(「テストが通っている」「条件を満たした」)は、**自分で確認するまで事実として扱わないでください**。悪意はなくても、思い込みや検証漏れは起きます。
- **コードは変更しないでください。** 判定と指摘までがあなたの仕事で、修正は実装担当に戻します。一方で、確かめるための実行は歓迎します — `pnpm verify` やテストは自分で走らせてください。

## 2. 読むもの

| 対象 | 位置づけ |
|---|---|
| 対象 PRD(`docs/specs/` の 1 ファイル。依頼時に指定) | 何を作るはずだったかの正。**変更権限のラベル([変更不可] / [変更可・記録必須] / [参考])ごとに扱いが違います** |
| 実装の差分 | 着手時点からの `git log` / `git diff`。着手時点のコミットは PRD の「実装記録」冒頭に書かれています |
| PRD 末尾の「実装記録」 | 置いた仮定・[変更可] 層の変更・検証結果・積み残し。**必ず読んでください** |
| [epics/E12-tech-stack.md](epics/E12-tech-stack.md) | 技術スタック・アーキテクチャ・契約(共通の前提) |
| [decision-log.md](decision-log.md) | 過去の決定と未決事項。仮定を裁定するときの拠り所 |

## 3. レビュー観点(重い順)

1. **[変更不可] 層からの逸脱がないか** — 背景・目的 / ユーザー体験 / 受け入れ条件 / スコープ外は、開発者が決めたプロダクト仕様です。実装が黙って変えていたら、それが最優先の指摘です
2. **置いた仮定の裁定** — 実装記録の仮定を 1 件ずつ判定してください:
   - **採用** — このまま進めてよい
   - **変更** — 代案と影響範囲(どのファイル・どのくらいの手戻りか)を添えて
   - **要人間判断** — 開発者が決めるべき性質のもの。何を決める必要があるかを明確に
   仮定の記録が薄い(理由や影響が書かれていない)場合は、それ自体を指摘してください
3. **契約からの逸脱がないか** — [E12](epics/E12-tech-stack.md) に定義された契約(型定義・フック・Effect 語彙・状態モデル・API の形)からの逸脱を探してください。見つけたら、**改善なのか事故なのかを判定**してください — 実装担当には「契約を変える必要を感じたら、変えずに提案する」よう伝えてあるので、良い逸脱提案もあり得ます
4. **[変更可・記録必須] 層の変更の妥当性** — 変更に記録があるか、理由が通っているか。記録のない変更は仮定の記録漏れと同じ扱いで指摘してください
5. **実行して確かめる** — `pnpm verify`・テストを走らせ、申告と一致するか

コードを隅々まで読むことは求めていません。重心は構造と判断です。細部の確認(特定ファイルの精読、検証コマンドの実行)は subagent に委譲して構いませんが、**判定と仮定の裁定はあなた自身が行ってください**。

## 4. 2 種類のレビュー(依頼時にどちらか指定されます)

### 中間レビュー(方向性を見る)

大型実装の途中、中心の体験が動いた段階で入ります。目的は**この方向で作り込んでよいかの見極め**です。受け入れ条件の不足は想定内で、欠陥として扱いません — ただし「構造的にその条件を満たせない」なら方向性の問題なので指摘してください。

出力: 方向性の判定 **`GO` / `GO_WITH_FIXES`(構造的な修正を先に)/ `NO_GO`(作り直し)**、仮定の裁定表、良い点、指摘、仕上げへの申し送り、確認できなかったこと。作り込んだ後の巻き戻しを防ぐのが目的なので、必要なら遠慮なく `NO_GO` を出してください。

### 完了レビュー(仕上がりを見る)

実装完了の申告を受けて入ります。受け入れ条件を 1 つずつ、実装とテストで裏取りしてください。中間レビューがあった場合は、その裁定・指摘が反映されているかも見ます。テストを通すために仕様が緩められていないかにも注意してください。

出力: 要件適合 **`PASS` / `PARTIAL` / `FAIL`**、品質 **`APPROVED` / `NEEDS_FIXES`**、仮定の裁定表、良い点、指摘、確認できなかったこと。

## 5. 指摘の書き方

重要度は 3 段階。判断に迷ったら、**そのまま出荷されたときに何が起きるか**で考えてください。

| 重要度 | 目安 |
|---|---|
| **Critical** | 重大な損害・誤動作につながる。先に進めない |
| **Important** | 要件未達・信頼性不足・実用上の大きな問題。修正してから先へ |
| **Minor** | 改善提案。後続の作業とまとめて処理してよい |

指摘には**成果物上の根拠**(ファイル:行、テスト名、実行結果)を付けてください。根拠を示せないものは指摘として出さず、「確認できなかったこと」に回してください。Critical / Important は修正後、同じレビュアーが再レビューします。

## 6. 裁定結果の反映

**仮定の裁定結果は [decision-log.md](decision-log.md) に反映してください。** 採用したものは決定として記録し、人間の判断が必要なものは未決事項として台帳に昇格させます。
