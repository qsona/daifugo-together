# レビューガイド

このプロジェクト「みんなでつくろう 大富豪」の実装レビューを担当していただきます。実装担当には [implementation-workorder.md](implementation-workorder.md) を渡してあり、**Epic ごとに 2 つのプロセスで進めています**。あなたはその境目に入ります。

前提として一番大事なこと:

> **実装担当は、未決事項に当たったら止まらずに「仮定を置いて」進めています。その仮定の妥当性を裁定するのが、このレビューの中心的な仕事です。**

## 1. 何をレビューするか

- **プロダクト**: ユーザーがルールを提案すると AI が実装し、ルールが増えるほどカオスになっていく大富豪。カオスそのものを楽しんでもらうゲームです。
- **対象**: 発注時に指定された Epic。実装担当がその Epic のストーリー群を一通り終えた状態です。

## 2. 読むもの

| ドキュメント | 位置づけ |
|---|---|
| 実装の差分 | Epic 着手時点からの `git log` / `git diff` |
| `docs/impl-progress.md` | 実装担当の記録。**「置いた仮定」と「プロセス2に回したもの」は必ず読んでください** |
| `docs/epics/E{対象}.md` | 対象 Epic の詳細設計。**冒頭の改訂反映ノートから読んでください** |
| `docs/epics/E12-tech-stack.md` | 技術スタック・アーキテクチャ・ルールプラグイン契約(全 Epic 共通の前提) |
| [product-backlog.md](product-backlog.md) | ストーリー本文と受け入れ条件 |
| [decision-log.md](decision-log.md) | 未決事項の一覧。仮定を裁定するときの拠り所 |

情報が食い違っていたら、**設計書 > 台帳**、設計書どうしなら **E12 > 個別 Epic** が正です。

**コードは変更しないでください。** 判定と指摘までがあなたの仕事で、修正は実装担当に戻します。一方で、**確かめるための実行は歓迎します** — 型検査・lint・テストは自分で走らせて、実装担当の申告と一致するか確認してください。「テストがあると書いてある」ことと「そのテストが実際に何かを検証している」ことは別です。

### レビューの高度

コードを隅々まで読むことは求めていません。重心は大局です — **設計の大方針が妥当か、置いた仮定に問題がないか、受け入れ条件の確認手法が適切か**。行単位の網羅的なコードリーディングに時間を使うより、構造と判断を見てください。細部の欠陥は、構造が正しければプロセス2 や次の Epic で安く直せます。

細部の確認が必要になったら(特定ファイルの精読、検証コマンドの実行、設計書との突き合わせなど)、**subagent に委譲して構いません**。あなたは裁定に集中し、確認作業は分担してください。ただし**方向性の判定と仮定の裁定は subagent に任せず、あなた自身が行ってください**。

## 3. 2 つのレビューの違い

| | プロセス1 のレビュー | プロセス2 のレビュー |
|---|---|---|
| 実装の状態 | ユーザーストーリーが動くところまで | 受け入れ条件を満たし切ったところまで |
| 目的 | **この方向で作り込んでよいかの見極め** | 仕上がりの確認 |
| 重心 | 設計の妥当性・置いた仮定の裁定 | 受け入れ条件の充足・テストの質 |
| 受け入れ条件の不足 | **想定内。欠陥として扱わない** | 指摘対象 |

プロセス1 のレビューが本命です。**作り込んだ後に方向性の巻き戻しが起きるのを防ぐ**ためにこの段階を設けています。ここで見逃した構造的な問題は、後で直すほど高くつきます。

**プロセスを分けないストーリー**(発注時に「単回レビュー」と指定されたもの。例: TS-02)は、1 回のレビューで両方の観点をまとめて見ます。出力はプロセス1 の形式(方向性判定 + 仮定の裁定表)に、プロセス2 の要件適合判定(`PASS` / `PARTIAL` / `FAIL`)を加えてください。

## 4. プロセス1 のレビュー(方向性を見る)

見てほしいことを、重い順に挙げます。

**1. ユーザーストーリーが実際に成立しているか**
「〜として、〜したい」が動くことを、テストを走らせるか自分で動かして確認してください。ここが成立していなければ、他を見る前に差し戻しです。

**2. 方向性と設計の妥当性**
契約(型定義・フック・Effect 語彙・状態モデル・API の形)からの逸脱を探してください。逸脱を見つけたら、**改善なのか事故なのかを判定**してください — 実装担当には「契約を変える必要を感じたら提案する」よう伝えてあるので、良い逸脱もあり得ます。作り込む前に直すべき構造的な問題を見つけるのが、この項目の主眼です。

**3. 置いた仮定の裁定(最重要)**
`impl-progress.md` の「置いた仮定」を 1 件ずつ判定してください。

- **採用** — このまま進めてよい
- **変更** — 代案を提示してください。影響範囲(どのファイル・どのくらいの手戻りか)も添えてください
- **要人間判断** — 開発者が決めるべき性質のもの。何を決める必要があるかを明確に

仮定の記録が薄い(なぜそう決めたかが分からない、影響範囲が書かれていない)場合は、それ自体を指摘してください。次のプロセスの精度に直結します。

**4. プロセス2 への申し送り**
「プロセス2に回したもの」が妥当か見てください。本来この段階で必要だったものが逃げていないか、逆に追加で回すべきものがないか。

**5. 実行して確かめる**
型検査・lint・テストを走らせ、申告と一致するか。

**やらないこと**: 受け入れ条件の網羅チェック、エッジケースの不足指摘。これらはプロセス2 の担当です。ただし「**構造的にその条件を満たせない**」なら、それは方向性の問題なので指摘してください。

### 出力

- **方向性の判定**: `GO`(この方向で作り込んでよい)/ `GO_WITH_FIXES`(構造的な修正を先に)/ `NO_GO`(作り直し)
- 良い点(具体的な根拠とともに)
- 指摘(重要度・場所・問題・影響・修正方向)
- **仮定の裁定表**(仮定 → 採用 / 変更 / 要人間判断 → 理由)
- プロセス2 への申し送り
- 確認できなかったこと

## 5. プロセス2 のレビュー(仕上がりを見る)

方向性は前回承認済みなので、こちらは絞って見ます。

1. **受け入れ条件の充足** — バックログの各条件を 1 つずつ、実装とテストで裏取りしてください
2. **前回の指摘と仮定の裁定結果が反映されているか**
3. **「プロセス2に回したもの」が消化されているか**
4. **テストの質** — 設計書のテスト観点(不変条件)が実際に守られているか。テストを通すために仕様が緩められていないか
5. 型検査・lint・テストを自分で実行して確認

### 出力

- 要件適合: `PASS` / `PARTIAL` / `FAIL`
- 品質: `APPROVED` / `NEEDS_FIXES`
- 良い点 / 指摘(重要度・場所・問題・影響・修正方向)/ 確認できなかったこと

## 6. 指摘の書き方

重要度は次の 3 段階で。判断に迷ったら、**そのまま出荷されたときに何が起きるか**で考えてください。

| 重要度 | 目安 |
|---|---|
| **Critical** | このまま進むと重大な損害・誤動作につながる。先に進めない |
| **Important** | 要件未達・信頼性不足・実用上の大きな問題。次のプロセスに入る前に直す |
| **Minor** | 改善提案。次の Epic とまとめて処理してよい |

指摘には**成果物上の根拠**(ファイル:行、テスト名、実行結果)を付けてください。「〜すべき」だけでは実装担当が動けません。逆に、根拠を示せないものは指摘として出さず、「確認できなかったこと」に回してください。

実装担当の申告(「テストが通っている」「条件を満たした」)は、**確認するまで事実として扱わないでください**。悪意はなくても、思い込みや検証漏れは起きます。

## 7. レビューのあとの流れ

- **GO** → プロセス2 へ進みます
- **GO_WITH_FIXES** → 構造的な修正をプロセス2 の先頭に入れます
- **NO_GO** → そこで止めて設計に戻ります。この早期発見がプロセスを分けている目的なので、必要なときは遠慮なく出してください
- Critical / Important は修正後、**同じレビュアーが再レビュー**します(あなたに戻ってきます)
- **仮定の裁定結果は [decision-log.md](decision-log.md) に反映してください**。採用したものは決定として記録し、人間の判断が必要なものは未決事項として台帳に昇格させます
