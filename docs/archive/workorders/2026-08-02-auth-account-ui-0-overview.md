### 1.1 なぜこの順序か

1. **1/5 が最初**なのは、Critical (1)(2) が「アカウントという概念の置き場が無い」という 1 つの欠落の裏表だから(レビュー §4.1)。置き場を 1 つ作ると J1-1・J1-2・J6-1・J6-2・J8-1 が同時に閉じる。他のどのフェーズも、DLG-1(認証実行の唯一の入口)とアカウント画面が無いと着地先を持てない。
2. **2/5 を 3/5 より先に置く**のは、3/5 が認証の入口を 2 か所増やす(退室後の誘い・提案画面の枠うまりパネル)からである。入口を増やす前に、失敗がアプリの外(生 JSON のページ)へ落ちる経路(J4-1)を塞いでおかないと、**露出だけが増える**。廃止D-6 は RES-3 の表示前提でもある(ワイヤー RES-3 の注記「前提(重要)」)。
3. **3/5 が Critical (3) の本体**。提案画面と退室後の誘いから DLG-1 へ届くようにし、認証語彙を 1 語に揃える。**N-8 は `817409b` によって縮小した** — A2HS 案内が登録済み限定になったため、未登録者の再ログイン経路は「ホーム画面アプリ側の通知設定画面に出る認証導線(実装済み)+ 1/5 のアカウント行」が受け持つ(3/5 §3.1)。
4. **4/5 を後ろに置く**のは、なまえが Critical 3 点に直接は入っていないため。ただし J8-2(改名手段が Web に無い)は Critical なので、1/5 で作るアカウント画面の**レイアウト上の位置だけ**を空けておき、ボタン自体は遷移先ができる 4/5 で足す(押しても何も起きないボタンを置かないため。1/5 §3.3)。
5. **5/5 は着手しない**。通知設定画面の本格改修(J9-4・J9-5・J9-7)を認証の再設計と同じ流れに混ぜるとレビュー対象が二重になる(ワイヤー冒頭「本書で描かないもの」)。

各フェーズは**単独で main に取り込める**。1/5 だけを入れた状態、1/5 + 2/5 だけを入れた状態のいずれもユーザーから見て一貫している(途中状態の扱いは各発注書の「このフェーズだけを入れた状態」節に書いた)。

## 3. スコープ制約(全フェーズ共通)

- **サーバー変更は一切しない。**E15 のバックエンド仕様は固定で、使うのは既存の `POST /api/auth/begin` / `POST /api/auth/complete` / `user:rename` と読み取り系 API だけ。サーバー側に不足を見つけたら**実装せず報告する**。
- **通知設定画面(`PushSettingsScreen`)の本格改修はしない。**このフェーズ群で触ってよいのは**文言(語彙統一)だけ**(3/5)。表示条件・状態表示・エラー分類は動かさない。端末の通知状態表示(J9-4 / N-12)・購読とサーバーのずれ(J9-5)・許可拒否からの回復(J9-7)は 5/5 の引き継ぎメモに書いてある範囲にとどめ、詳細設計は別 work order に委ねる。
- **`subscribeProposalResults` を呼ぶ側は登録済みを保証する**(レビュー §0.9 の J9-2 追記)。この不変条件を破る入口を新設しない。
- **対局中(部屋の画面)に認証導線を出さない**(E15 §2.3)。アカウント行そのものを出さない(A-7)。
- ドキュメントの書き換えは、各発注書が明示した読み替えノートだけ。設計書本文は書き換えない。

## 5. 全フェーズ共通の約束

### 文言

- 文体は**やさしい敬体**。「〜だよ / 〜してね」は `GuideMessage` 専用(ガイド §2.2・§8.1)。
- 句点はガイド §3 の表に従う(ボタン・ラベル・バッジ=なし / 本文=全文に付ける / トーストは 1 文ならなし)。
- 分かち書きの空白は全角・半角とも使わない。
- **複数箇所に出る文言は `packages/web/src/messages.ts` に定数化する**(ガイド §11.3)。既存の `RETRY_GENERIC_ERROR` / `CONFIRM_BACK_LABEL` はそのまま使う。
- 確認ダイアログ: 見出しは「〜しますか?」、選択ボタンは動詞の言い切り、**破壊的な操作では primary を取り消し側**に置く(`ConfirmDialog.tsx:6-22`)。

### 部品

既存部品で組む。**新規部品は `AccountRow` の 1 つだけ**を想定する(ワイヤー §7)。

| 用途 | 部品 |
|---|---|
| アカウント行 | 新規 `AccountRow`(1/5) |
| 状態バッジ | `Tag`(`components/Tag.tsx`)。**現状の `variant` は local / original / active / removed / human / ai の 6 種で、アカウント用が無い**。1/5 で追加する |
| 確認 | `ConfirmDialog`(`components/ConfirmDialog.tsx`) |
| 説明を伴うモーダル | `Dialog` + `DialogBody`(`components/Dialog.tsx`) |
| 注記 | `Callout`(1 画面 1 枚まで) |
| 成功通知 | `Toast`(自動退場は 2/5 で新規実装) |
| 入力 | `InputField`(`components/Field.tsx`)+ `countCodePoints` / `clampCodePoints` |

### テスト

- 既存の流儀に合わせ、画面・部品と同じディレクトリに `*.test.tsx`(Testing Library)を置く。参照例: `screens/PushSettingsScreen.test.tsx`・`screens/PlaySheet.test.tsx`・`components/Dialog.test.tsx`。
- 認証の状態は `MultiplayerState` の `registered` / `displayName` / `connection` で決まるので、**この 3 つを軸にケースを作る**。
- 実行は `pnpm exec vitest run packages/web/src`。テスト初回実行の前に `pnpm --filter @daifugo/ai... build` が要る。

### コミット

- `git add` は**ファイル単位**で行い、無関係の未コミット変更を巻き込まない(§4 のとおり作業ツリーに他セッションの変更が残りうる)。
- PR は作らない。フェーズが完了・検証できた時点で `main` へ直接コミットして push する(AGENTS.md)。
