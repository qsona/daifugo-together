## 3. 残っている指摘(詳細設計が要る)

根拠と改善方向は `docs/design/auth-ux-review.md` §0.9 にある。**サーバー仕様(登録済みゲート)は固定制約として扱い、変更を前提にしない。**

| # | 内容 | 重要度 | サーバー変更 |
|---|---|---|---|
| **J9-4** | 端末の通知状態(オン / オフ / 許可拒否 / 非対応)を読んでおらず、**登録済みの人に**「受け取る」と「止める」が常に両方出る。**状態を先に出し、その状態でできる操作だけを出す**(N-12)。粒度が端末単位の 1 つになったので、見出しは「この端末」だけで足りる | Important | 不要 |

## 4. 着手前に必要なもの

1. **通知設定画面の画面仕様**(状態表示・許可拒否からの回復手順)。`push/install.ts` の `detectInstallEnvironment` が既に環境を判定しているので、回復手順は A2HS 案内と同じく環境で分岐させられる。粒度は端末単位の 1 つだけなので、J9-6 の「見出しで射程を言う」は不要になった
2. **テストの網羅軸**(レビュー §0.8 の P2 引き継ぎ): 匿名 / 登録済み / VAPID 未設定 / OS 許可拒否 / iOS タブ / ホーム画面アプリ

## 5. 注意

- **不変条件(最重要)**: `subscribeProposalResults` は `Notification.requestPermission()` を最初に呼ぶ構造のままである(user activation を保つための意図的な順序)。安全なのは**呼び出し口 3 つがすべて登録済みを保証しているから**にすぎない。**登録済みガードのない入口を足すと J9-2 が即座に再発する**(レビュー §0.9 の J9-2 追記)
- **J9-3 は J4-4(認証の失敗が 3 原因で 1 文言)と同じ形の欠落だが、対象コードも画面も別**(`push/client.ts` の `#request`)。2/5 の作業に混ぜない
- **認証後に元の文脈へ戻すパターンの前例**: `beginPushLogin` が `markOfferAfterLogin()` で意図を記録し、完了ハンドラが `consumeOfferAfterLogin()` で回収する(`App.tsx`)。OAuth のフルページ遷移で失われる「何をしようとしていたか」をサーバー変更なしに引き継げるので、この画面から認証へ送り出す設計を足すときは**新しい仕組みを作らずこれをなぞる**
- Push は「登録ゼロで遊べる」(E15 §1.1)と衝突する最初の機能である。サーバーは購読に登録済みを要求し、匿名は 403 `registration_required`(`packages/server/src/push/service.ts`)。これは E17 の設計判断であり、**本フェーズ群では動かさない**
