# 実装ガイド

このプロジェクト「みんなでつくろう 大富豪」の実装を担当していただきます。プロダクトは、ユーザーがルールを提案すると AI が実装し、ルールが増えるほどカオスになっていく大富豪です(2026-08-02 リリース済み)。

実装の依頼は、**本書 + 対象 PRD(`docs/specs/` の 1 ファイル)** で完結します。ほかに前提として:

- 技術スタック・アーキテクチャ・ルールプラグイン契約: [epics/E12-tech-stack.md](epics/E12-tech-stack.md)
- git 運用(ブランチ・main への取り込み・push guard・ASCII 命名): [../AGENTS.md](../AGENTS.md)。本書では繰り返しません

## 1. PRD の読み方 — 変更権限の 3 段階

PRD の各セクションには変更権限のラベルが付いています。**本書で一番大事な取り決めです。**

### [変更不可]

背景・目的 / ユーザー体験 / 受け入れ条件 / スコープ外。開発者が議論して決めたプロダクト仕様です。変える必要を感じたら、**変えずに提案として報告**してください(その提案自体は歓迎です)。

### [変更可・記録必須]

詳細仕様・エッジケース。実装担当のレビュー対象です。**批判的に読み、より良い案があれば自分の判断で変えて構いません。** ただし、変更した内容と理由を必ず PRD の実装記録(本書 §5)に残してください。

### [参考]

技術設計メモ。設計者のスケッチであり、実装は実装担当の領域です。より良い設計があれば自由に再設計してください。file:line のアンカーは書いた時点のもので、ずれていたら関数名などで取り直してください。

ただし、[E12](epics/E12-tech-stack.md) に定義された契約(型定義・フック・Effect 語彙・状態モデル・API の形)は、この自由の対象外です。変える必要を感じたら、変えずに提案として報告してください。PRD の技術設計メモと E12 が食い違ったら E12 が正です。また、オーバーエンジニアリングは避けてください。入れた方がよいと考える機構があれば、実装する前に提案してください。

### ラベルのない旧形式の PRD

`docs/specs/` にはラベルの付いていない既存 PRD があります。渡された場合は、全体を [変更可・記録必須] 相当として扱い、変更は同じ様式で記録してください。ただし、目的・スコープ外に相当する記述は [変更不可] として扱ってください。実装記録セクションがなければ末尾に追加してください。

## 2. 未決事項と仮定

未決事項に当たっても止まらず、[変更不可] 層と整合する範囲で**妥当な仮定を置いて進めてください**。

置いた仮定は必ず PRD の実装記録に記録します(内容 / 理由 / 覆ったときの影響)。記録してあれば、後で覆っても事故になりません。**記録がないまま埋め込まれた判断が一番危険です。**

料金体系や対外的な約束など、人間にしか決められない性質のものは、仮定を置かずに「要判断」として報告してください。

## 3. 進め方の目安

既定は **1 パス**です: 実装 → 検証 → 報告。完了レビュー(review-guide.md)を入れるかどうかは、依頼時に指定します。

大型の場合(目安: 複数画面にまたがる、契約の変更を含む、または数日規模)は 2 パスに分けてください:

1. **縦に通す** — 中心となる体験が実際に動くところまで
2. **中間レビュー** — 独立レビュー([review-guide.md](review-guide.md))で方向性と仮定の裁定を受ける
3. **仕上げる** — 裁定を反映し、受け入れ条件を満たし切る

仕上げ後に完了レビューを入れるかも依頼時に指定します(大型では入れることを推奨します)。

レビューは、**実装と同じセッション・同じコンテキストで自己レビューしてはいけません**。会話履歴を共有しない独立したセッションに依頼し、渡すのは review-guide.md・対象 PRD・レビュー種別の指定だけにしてください(実装側の結論や言い分は渡さない)。レビュアーがリポジトリだけで判断できるよう、依頼前に実装記録を書き切っておいてください。

## 4. 検証

- `pnpm verify` を通してください(format / lint / design lint / typecheck / test / build)
- UI の変更は、375×812 の画面サイズで実画面を確認してください
- 実行結果は、**実際に走らせた出力**で報告してください

## 5. 記録

PRD 末尾の「実装記録」セクション(§8 テンプレート参照)に書きます:

- 着手時点のコミット(レビュアーが差分の基準にします。**着手したら最初に書いてください**)
- 置いた仮定(内容 / 理由 / 覆ったときの影響)
- [変更可・記録必須] 層の変更と理由
- 検証結果
- 積み残し・提案([変更不可] 層への提案もここに)

あわせて、PRD 冒頭の「状態」行と、[status.md](status.md) の該当行を更新してください。

仮定の裁定の [decision-log.md](decision-log.md) への反映は、レビューを入れる依頼ではレビュアーが行います。レビューを入れない依頼では、開発者が報告を読んで裁定します。

## 6. 止まってほしいとき

次の場合だけ、記録を残して報告し、指示を待ってください:

- PRD の [変更不可] 層と矛盾していて、仮定を置くことすらできない
- 同じ問題で 3 回以上やり直している(手を変えても抜けられない)
- [変更不可] 層や既存の契約を変更しないと実装できない
- 環境や権限の問題で作業自体が進まない

## 7. 報告

作業を終えたら、次を教えてください:

- 変更内容とコミット
- 検証結果(`pnpm verify` の実際の出力、UI 確認の方法)
- 置いた仮定(裁定してほしい順に)
- [変更可] 層で変えたものとその理由
- [変更不可] 層への提案・気づいたこと
- 積み残し・詰まっている点

## 8. 付録: PRD テンプレート

```markdown
# <機能名>

- 日付: YYYY-MM-DD / 状態: 起草中 | 実装中 | 完了
- 関連: <epics・decision-log・過去 PRD へのリンク>

## 1. 背景と目的 [変更不可]
## 2. ユーザー体験 [変更不可]
<画面・文言・可視挙動。ワイヤーや画面遷移があればここから参照>
## 3. 受け入れ条件 [変更不可]
## 4. スコープ外 [変更不可]
## 5. 詳細仕様 [変更可・記録必須]
<エッジケース・データ仕様・エラー時挙動など。実装担当のレビュー対象>
## 6. 技術設計メモ [参考]
## 7. 未決事項(実装時に仮定を置いたら実装記録へ)
## 8. 実装記録(実装担当が記入)
- 着手時点のコミット: <SHA>
### 置いた仮定
| 仮定 | 理由 | 覆ったときの影響 |
### 詳細仕様の変更
| 変更 | 理由 |
### 検証
### 積み残し・提案
```

## 9. ファイルの置き場

- **PRD**: `docs/specs/YYYY-MM-DD-<slug>.md`(ASCII 命名)。1 ファイルが既定です。大型機能では `-design.md` / `-implementation.md` の分冊も可(例: [specs/2026-08-07-midgame-join-design.md](specs/2026-08-07-midgame-join-design.md))
- **現在地**: [status.md](status.md) — 進行中・外部ゲート・人間判断待ち・小粒の残件だけを持つ薄いファイル
- **裁定の記録**: [decision-log.md](decision-log.md)
- **過去の記録**(旧 workorders・impl-progress など): [archive/](archive/) — 歴史的資料であり、現行フローの正ではありません
