## 実装の共通基盤(最初に作る)

jinro-ai-app の `links.ts` と同じ一元管理ファイルを作る:

```ts
// packages/web/src/links.ts(案)
export const SERVICE_NAME = "みんなでつくろう 大富豪";
export const SERVICE_URL = "https://daifugo-together.fly.dev";
export const SUPPORT_URL: string = "https://ofuse.me/qsona"; // 空文字なら支援リンク非表示
export const X_ACCOUNT_URL = "https://x.com/qsona";

const SHARE_HASHTAGS = "みんなでつくろう大富豪"; // #なし・カンマ区切り

export function buildXShareUrl(text: string, path = "/"): string {
  const params = new URLSearchParams({
    text,
    url: `${SERVICE_URL}${path}?from=share`,
    hashtags: SHARE_HASHTAGS,
  });
  return `https://x.com/intent/post?${params.toString()}`;
}
```

- X連携はintent URL方式(API・審査・ログイン不要)。X側のcomposerが開き、**ユーザーは文面を自由に書き換えられる**(「何を書くかはユーザーに任せる」方針と整合)
- **ハッシュタグ: `#みんなでつくろう大富豪` を全Xシェアに自動付与**(intentの `hashtags` パラメータ、`#`なしのカンマ区切りで渡す)。目的は開発者のエゴサーチではなく、**ユーザーが「他の人はどんな投稿してるんだろう」とタグを踏んで見に行ける公開の場**を作ること。正式名フルのタグにする理由: 一意で他の話題と混ざらない(#大富豪 はゲーム外の投稿と混ざり、略称タグは定着前に分裂する)。長いがintentで自動挿入されるのでユーザーは打たない
- ハッシュタグを**付けない**もの: 優先1の招待共有(LINE等への私信。タグは宣伝臭になるだけ)
- タグの初期投稿がゼロだと踏んだ人が寂しいので、**リリース告知のリプツリー1本目と、初週カレンダーの開発者ポストにこのタグを付けて種をまく**(本ポスト案Eは278字でタグを足すと超過するため付けない)
- シェアURLに `?from=share`、招待経由に既存の招待パラメータを維持。効果測定はアクセスログ/流入で後から見る

## 優先1: 招待リンクのOS共有シート(実プレイに一番効く)

**どこ**: 既存の招待リンク/QR画面(`InviteCode` 相当)に「共有する」ボタンを1つ追加。

**実装**: 常設のURL表示+コピーボタンの行は**廃止**し、ボタン1本に統合する(共有シート内にコピーがあるため二重になる)。ボタンは環境で出し分ける:

- `navigator.share` が使える環境(スマホほぼ全部+一部PC): 「📤 リンクを共有する」→ OSの共有シート(LINE/Discord/AirDrop/コピー)
- 使えない環境(PCのFirefox等): **同じ位置のボタンが「リンクをコピー」になる**(clipboard APIで招待URLをコピー+「コピーしました」トースト)

**アドレスバーには頼らない**: ホストが見ているページのURLと招待用URLが同一とは限らないうえ、同一だとしてもワンクリックコピーの方が確実。PCでの実態は「ホストがPC・友達はスマホ」なので、**QRこそがPCの主役導線**(画面のQRを友達がその場で読む)。QRと部屋コードの表示は残す(コードは「友だちの部屋にはいる」の手入力用)。

**共有文面**(編集可能な初期値):

```
大富豪しよう。この部屋に入って: <招待URL>
```

**意図**: 日本で「今から遊ぼう」の実態はLINE。OSの共有シートならLINE/Discord/AirDropすべてに1実装で流せる。X宣伝より実プレイへの転換が速い、今日入れる価値が最も高い導線。

## 優先2: セット総合結果のXシェア

**どこ**: セット終了時の総合結果画面に「Xでシェア」ボタン(secondary。primaryは「もう一度あそぶ」系のまま)。

**プリセット文面**(順位で1行だけ変える。ユーザーがcomposer上で自由に消せる・書き換えられる):

| 総合順位 | 初期文面 |
|---|---|
| 1位 | 大富豪になりました |
| 2位 | 富豪でした |
| 3位 | 貧民でした |
| 4位 | 大貧民でした… |

+ URL(buildXShareUrl)。凝った文面にしない(「都落ちしたわー」のような味付けはユーザー自身がやる。こちらは素直な事実だけ)。

**意図**: 到達ユーザー数が最多の画面。1ゲームものの定型シェアは弱いが、コストが数十行で済むので入れる価値がある。

## 優先3: ルール図鑑のシェア(図鑑エントリの自慢として設計)

図鑑はポケモン図鑑的な収集体験なので、シェアは「サービスの宣伝」ではなく**そのルールのエントリの自慢**として成立させる。各ルールカードの右下に小さめのゴーストボタン「𝕏 このルールをシェア」を置く。

**文面テンプレ**(ルール名+説明の先頭を動的に入れる。個別ページは作らず path=`/rules` 固定):

```
ルール図鑑「{ルール名}」
{説明の先頭 40字程度}
```
+ URL。都道府県の報告があるルールは1行目に `(埼玉県で遊ばれていた報告)` を続ける。

**後日版(今日はやらない)**: ルール個別URL(`/rules/:id`)+ルールごとのOGP画像。図鑑No.(リリース順の安定番号)の表示もこのタイミングで検討(現在カードに出ている数字は「優先」で人気度により変動するため、シェア文面には使わない)。

## 優先5: 提案採用時のシェア(E16実装済みのため今日やる)

E16(通知センター)はmainに実装済み。おしらせ画面の **`proposal_released`** 項目にだけシェアボタンを付ける(`proposal_rejected` には付けない)。採用の瞬間はこのゲーム最強のシェアモーメント。

- ボタン文言の第一候補: **「𝕏 じまんする」**(このゲームのトーンに合う。硬めなら「Xでシェア」)
- **文面テンプレ**:

```
提案したルール「{ルール名}」が、みんなでつくろう大富豪に実装されました
```
+ URL(path=`/rules`)。**一人称は入れない**(ユーザーの一人称を固定しない方針。全シェア文面共通)。

- 通知payloadにルール名が無ければフィールドを追加する(表示title文字列のパースはしない)
- 効果が出るのは最初のユーザー提案が採用される数日後から。今日入れておけば、その瞬間を取りこぼさない

## 優先6: イエローカードのシェア(2026-08-02追加)

E6の設計原則「対策自体を笑える演出にする」の延長。イエローカードのスクショはどのみち勝手に拡散されるので、**シェアボタンを公式に置いて「笑っていい出来事」として framing を握る**。カードを受けた人が宣伝者に変わる、この製品らしい導線。

- **どこ**: イエローカード表示(`YellowCardModal`)にゴーストボタン。**異議申立て導線より下・控えめに**(誤検知された人のための救済が主、シェアは従)
- **ボタン文言**: 採用時と同じ「𝕏 じまんする」を推奨(イエローカードを"自慢"するのがオチとして成立する)
- **文面テンプレ**(一人称なし):

```
みんなでつくろう大富豪で、イエローカードをもらいました🟨
```
+ URL

- **入れないもの**: カードの理由文(検出されたプロンプト内容)はプリセットに含めない。本人が書きたければcomposer上で足せる
- **懸念と判断**: カード欲しさの軽い試行は増えるが、2枚で24時間停止という実デターレントは既にあり、審査は自動。「ハッキングから〜」の告知文とも整合する。逆に隠すほうが、誤検知時の不満だけが拡散する

## 全体の注意(重要)

- **1回のデプロイにまとめる**。デプロイ→スモーク確認(招待共有・結果画面・支援リンク・OGPカードのcurl)→フリーズ→告知、の順。チェックリスト必須-7の「中途半端な状態で告知時刻を迎えない」を守る
- 告知は12-13時にこだわらない。**作業が押したら14時でも日曜午後として問題ない**。慌てたデプロイ直後に告知する方がリスク
- 結果画面のボタン序列: あそぶ系 > シェア > 支援。シェア・支援が主張しすぎると実直トーンと矛盾する
- `x.com/intent/post` はスマホでXアプリのcomposerに繋がる。特別な対応不要
