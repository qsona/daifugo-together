# 実装発注テンプレート(長時間稼働・Epic 単位レビュー)

実装は codex(実装エージェント)、レビューは Fable(強いモデル)で Epic 単位に入れる運用の発注テンプレート。**このファイルは発注する人間が使う道具**であり、実装エージェントに読ませるのは §2 の本文である。

- 運用の骨格: **1 ストーリー = 1 コミット(または 1 PR)** → ストーリー完了ごとに進捗台帳を更新 → **Epic の全ストーリー完了時に Fable レビュー** → 指摘を修正して次の Epic へ。
- 参照する台帳: [product-backlog.md](product-backlog.md)(何を作るか・優先順・状態)/ [decision-log.md](decision-log.md)(着手前に決めるべきこと)/ `docs/impl-progress.md`(実装の進捗。初回に作る)

---

## 1. 発注前に人間がやること(3 分)

1. **対象 Epic を決める**(バックログの並び順に従う。フェーズ 1 は TS-02 → E1 → E2 → E3 → E4 の順)
2. **decision-log を見て、その Epic のストーリーをブロックする未決事項があるか確認**する。あれば先に決める(決めずに投げると、エージェントが推測で埋めるか止まる)
3. 下の §2 テンプレートの `{{...}}` を埋めて渡す

## 2. 実装エージェントへの発注テンプレート(ここから下をコピーして使う)

```text
あなたはこのリポジトリの実装担当です。長時間の自律作業を前提に、以下のプロトコルに厳密に従ってください。

## 担当範囲
Epic: {{E1: 素の大富豪ゲームエンジン}}
ストーリー: {{GE-02, GE-03, GE-05, GE-04}}(バックログの並び順に、上から順に 1 つずつ)

## 必読(この順に読む。読まずに着手しない)
1. docs/epics/{{E01-game-engine}}.md — 担当 Epic の設計書。**冒頭の改訂反映ノートを必ず読む**(E12 改訂による読み替えが書いてある)
2. docs/epics/E12-tech-stack.md — 技術スタック・ルールプラグイン契約・アーキテクチャ(全 Epic 共通の前提)
3. docs/product-backlog.md — 担当ストーリーの原文と受け入れ条件、依存関係
4. docs/decision-log.md — **「宛先」欄で担当ストーリー ID を検索**し、該当する決定事項を確認する
5. docs/impl-progress.md — 実装の進捗台帳(存在しなければ §「進捗台帳」の形式で新規作成)

設計書と実装が食い違ったら**設計書を正**とする。設計書どうしが食い違ったら E12 を正とし、その旨を報告する。

## 作業プロトコル(1 ストーリーごとに繰り返す)

各ストーリーについて、次を順に行う:

1. **着手宣言**: impl-progress.md に「ストーリー ID / 状態: 進行中 / 開始時刻」を追記してコミットする。
2. **決定事項の確認**: decision-log にこのストーリーをブロックする未決事項があれば、**推測で埋めずに停止して報告**する(§停止条件)。仮値で進めてよいと台帳に明記されている項目は、採用した値を impl-progress に記録して進む。
3. **テストを先に書く**: バックログの受け入れ条件と設計書のテスト観点を、実行可能なテストに落とす。この時点でテストは失敗する。
4. **実装する**: テストが通る最小の実装を書く。設計書の型定義・命名・契約に従う(勝手に設計を変えない)。
5. **検証する**: 型検査・lint・テストをすべて実行し、**出力を確認**する。落ちていたら直す。「通ったはず」で進めない。
6. **セルフレビュー**: 受け入れ条件を 1 つずつ声に出して確認する。設計書の該当節と実装を突き合わせ、逸脱がないか見る。
7. **コミット**: `feat({{ストーリーID}}): 要約` の形式で 1 ストーリー 1 コミット。コミットメッセージに受け入れ条件の充足状況を書く。
8. **台帳更新**: impl-progress.md を「状態: 完了 / コミット SHA / 検証結果 / 残した TODO」に更新してコミットする。バックログの該当ストーリーにも `状態: 完了` を追記する。
9. 次のストーリーへ。

## 進捗台帳(docs/impl-progress.md)の形式

コンテキストが切れても再開できるよう、**作業の事実だけ**を簡潔に記録する。

```md
# 実装進捗

## 現在の作業
- Epic: E1 / ストーリー: GE-02 / 状態: 進行中 / 開始: <時刻>
- 次にやること: <1 行>

## 完了ログ
| ストーリー | 状態 | コミット | 検証 | 備考 |
|---|---|---|---|---|
| TS-02 | 完了 | abc1234 | 型/lint/test 通過 | — |

## 採用した仮値・判断
- <項目>: <採用値>(出典: decision-log B-2。TS-03 の計測後に見直し)

## 詰まっている点(人間の判断待ち)
- <なければ「なし」>
```

## 守ること(ガードレール)

- **担当 Epic の範囲外のファイルを変更しない**。他 Epic のコードに手を入れる必要が出たら、変更せずに報告する。
- **設計書(docs/epics/*.md)を書き換えない**。設計の誤り・不足を見つけたら、impl-progress の「詰まっている点」に書いて報告する(重要なら停止する)。
- **decision-log を勝手に決定済みにしない**。決定は人間が行う。
- **既存の通っているテストを壊さない**。壊れたら直すか、直せないなら停止して報告する。
- テストを「通す」ためにテストを緩めない。実装を直す。
- 秘密情報(API キー・トークン)をコミットしない。

## 停止条件(以下に当たったら作業を止めて報告する)

1. decision-log の未決事項が担当ストーリーをブロックしており、仮値で進める指示がない
2. 設計書に重大な矛盾・不足があり、推測で埋めると手戻りが大きい
3. 同じテスト失敗を 3 回直せない、または同じ箇所で 3 回以上やり直している
4. 設計書の契約(型・フック・Effect・状態モデル)を変更しないと実装できない
5. 担当範囲外のファイルへの変更が必要になった

停止するときは impl-progress.md に状況を記録してコミットしてから、「何を試したか / 何が確定したか / 何が阻害要因か / どんな判断が必要か」を報告する。

## 完了報告(担当ストーリーをすべて終えたら)

Status / 完了ストーリー一覧(コミット SHA 付き)/ 検証結果(型・lint・テストの実行結果)/ 採用した仮値 / 設計書への提案 / 残した TODO / 詰まっている点
```

## 3. Epic 単位の Fable レビュー発注テンプレート

実装エージェントが Epic を終えたら、**別のエージェント(Fable)**に読み取り専用でレビューさせる。

```text
あなたは Epic {{E1}} の実装レビュアーです。コードを変更せず、証拠に基づいて判定してください(読み取り専用)。

## 読むもの
- 実装: {{packages/core}} 配下の変更(git log / git diff で Epic 開始時点からの差分を見る)
- 仕様: docs/epics/{{E01-game-engine}}.md(冒頭の改訂反映ノート込み)、docs/product-backlog.md(担当ストーリーの受け入れ条件)、docs/epics/E12-tech-stack.md(契約・アーキテクチャ)
- 実装の申告: docs/impl-progress.md

## 検証すること
1. **受け入れ条件の充足**: 各ストーリーの受け入れ条件を 1 つずつ、実装とテストで裏取りする。「テストがある」ではなく「そのテストが条件を実際に検証しているか」を見る
2. **設計書との一致**: 型定義・命名・契約(フック・Effect・状態モデル)が設計書どおりか。逸脱があれば、それが改善なのか事故なのか判定する
3. **仕様の穴**: 設計書が規定していないケースを実装が勝手に決めていないか(決めているなら妥当か、decision-log に上げるべきか)
4. **テストの質**: 不変条件(設計書のテスト観点)が実際に守られているか。ハッピーパスだけでないか。テストを通すために仕様を緩めていないか
5. **自分でテストを実行する**: 型検査・lint・テストを実行し、実装の申告と一致するか確認する
6. **範囲**: 担当外のファイルに手が入っていないか

## 判定
要件適合: PASS | FAIL | PARTIAL
品質: APPROVED | NEEDS_FIXES
良い点 / 指摘(重要度 Critical|Important|Minor・ファイル:行・問題・影響・修正方向)/ 確認不能
```

レビュー結果の扱い: Critical / Important は実装エージェントに修正させ、**修正後に同じレビュアーで再レビュー**する。Minor は次の Epic とまとめて処理してよい。
