# 実装ガイド

このプロジェクト「みんなでつくろう 大富豪」の実装を担当していただきます。設計は一通り終わっていて、Epic ごとの設計書とバックログが揃っています。**設計の意図を汲みつつ、良い実装に着地させることを期待しています。**

---

## 1. 何を作るか

- **プロダクト**: ユーザーがルールを提案すると AI が実装し、ルールが増えるほどカオスになっていく大富豪。カオスそのものを楽しんでもらうゲームです。
- **今回の担当**: Epic ごとの**発注書**(`docs/workorders/`)で指定します。本書は全発注に共通する進め方だけを書いています。
- **全体像**: [product-backlog.md](product-backlog.md) に Epic とユーザーストーリーが優先順に並んでいます。

## 2. 読んでおくもの

| ドキュメント | 位置づけ |
|---|---|
| `docs/epics/E12-tech-stack.md` | 技術スタック・アーキテクチャ・ルールプラグイン契約。**全 Epic 共通の前提** |
| `docs/epics/E{担当}.md` | 担当 Epic の詳細設計。**冒頭の改訂反映ノートから読んでください**(後の決定による読み替えが書いてあります) |
| [product-backlog.md](product-backlog.md) | 担当ストーリーの本文と受け入れ条件、依存関係 |
| [decision-log.md](decision-log.md) | まだ決まっていないことの一覧。「宛先」欄に自分のストーリー ID があるものは目を通してください |
| `docs/impl-progress.md` | 実装の進捗記録。前任の作業がここに残っています(なければ §6 の形式で作ってください) |
| `docs/workorders/E{担当}-*.md` | **担当分の発注書**。担当範囲・着手前の前提・レビューの重点はここが正 |

情報が食い違っていたら、**設計書 > 台帳**、設計書どうしなら **E12 > 個別 Epic** を正としてください。食い違い自体は報告してもらえると助かります。

## 3. 進め方

一度で完璧に仕上げるのではなく、途中でレビューのプロセスを挟みます(レビュー側の観点は [review-guide.md](review-guide.md) にあります)。

**プロセス1: 縦に通す**
担当ストーリーが「ユーザーストーリーとして成立する」状態まで持っていきます。「〜として、〜したい」が実際に動いて確認できればこの周は達成です。**受け入れ条件を全部満たす必要はありません。** エッジケース・エラー処理・網羅的なテストはプロセス2に回して構いません(回したものは記録してください)。

ここで一度レビューが入ります。見るのは主に「**この方向で作り込んでよいか**」と「**置いた仮定が妥当か**」です。

**プロセス2: 仕上げる**
レビュー指摘と仮定の裁定結果を反映し、受け入れ条件を満たし切ります。エッジケースとエラー処理もここで仕上げます。

Epic ごとに、プロセス2が完了したら main ブランチにチェックインしてください。

### レビューの体制(独立性の担保)

実装は基本的に **GPT-5.6 Sol** に担当してもらう想定です。プロセス1と2の間の方向性レビュー(および完了レビュー)も GPT-5.6 Sol が行いますが、**実装と同じセッション・同じコンテキストで自己レビューしてはいけません**。

- **あなたが GPT-5.6 Sol で実装担当の場合**: レビューは、会話履歴を共有しない**新しい独立したコンテキストの GPT-5.6 Sol セッション**に依頼してください(自分でレビューを兼ねない)。レビューアに渡すのは [review-guide.md](review-guide.md) と担当範囲の指定だけで、実装セッションの結論・自己評価・言い分は渡さないでください。レビューアはリポジトリ(コード・設計書・`docs/impl-progress.md`)だけを見て判断します。
- 実装側は、レビューアがリポジトリだけで判断できるよう、仮定と積み残しを `docs/impl-progress.md` に書き切ってからレビューを依頼してください(§6)。
- レビュー結果の反映は実装側のセッションで行い、裁定が必要な仮定は開発者に確認します(§5)。

## 4. 判断の基準

設計書は「ミドル以上のエンジニアが追加質問なしで着手できる」ことを目指して書いていますが、当然すべては書ききれていません。**書かれていないことは、あなたの判断で決めて進めてください。** 実装の詳細、ファイル分割、テストの書き方、命名の細部、リファクタの判断などは、あなたの領域です。

一方で、**勝手に変えないでほしいもの**が 3 つあります。ここを動かすと他の Epic が連鎖的に壊れるためです:

1. **設計書に定義された契約** — 型定義、フック、Effect 語彙、状態モデル、API の形。変える必要を感じたら、変えずに提案として報告してください(その判断自体は歓迎です)
2. **設計書そのもの**(`docs/epics/*.md`) — 誤りや不足を見つけたら、書き換えずに報告してください
3. **decision-log の決定状態** — 決定は人間が行います

オーバーエンジニアリングをしないように注意してください。入れた方がよいと考える機構があれば、実装する前に提案してください。

## 5. 未決事項に当たったら

設計書の意図と企画書に整合する範囲で、妥当な仮定を置いて進めてください。

**置いた仮定は必ず記録してください**(§6)。記録してあれば、後で覆っても事故になりません。記録がないまま埋め込まれた判断が一番危険です。

なお、`decision-log.md` に「仮値で着手可」と書いてある項目は、そのまま進めて構いません。

## 6. 記録の残し方(`docs/impl-progress.md`)

長時間の作業になるので、**セッションが切れても再開できる**ことが重要です。リポジトリを見れば状況が分かる状態を保ってください。以下は最低限あってほしい項目で、形式は自由です。

```md
# 実装進捗

## 現在
- Epic: E1 / 周: 1 周目 / ストーリー: GE-02 / 次にやること: <1 行>

## 完了したストーリー
| ストーリー | 周 | コミット | 検証結果 |
|---|---|---|---|

## 置いた仮定(レビューで裁定してもらう)
| 仮定した内容 | なぜそう決めたか | 出典 | 覆ったときの影響範囲 |
|---|---|---|---|

## 2 周目に回したもの
| ストーリー | 内容 | 理由 |
|---|---|---|

## 詰まっている点(人間の判断待ち)
```

「置いた仮定」と「2 周目に回したもの」は、レビュアーが直接使います。ここが薄いとレビューの精度が落ちるので、丁寧にお願いします。

## 7. 止まってほしいとき

次の場合だけ、記録を残して報告してください:

- 設計書どうしが矛盾していて、**何を作るべきかが定まらない**(仮定を置くことすらできない)
- 同じ問題で 3 回以上やり直している(手を変えても抜けられない)
- **契約を変更しないと実装できない**
- 担当範囲外への変更が必要になった
- 環境や権限の問題で作業自体が進まない

## 8. 報告

プロセスを終えたら、次を教えてください。他にも必要な情報があれば追加してください。

- 完了したストーリーとコミット
- 型検査・lint・テストの実行結果(**実際に走らせた出力**でお願いします)
- **置いた仮定**(裁定してほしい順に)
- (プロセス1では)意図的にプロセス2に回したもの
- 設計への提案・気づいたこと
- 詰まっている点

1 周目の報告では、**「ユーザーストーリーが動くことをどう確認したか」**(テスト名、手元での動作手順など)を書いてください。レビュアーが最初に見る情報です。

## 9. 発注書(`docs/workorders/`)

Epic ごとの発注は本書から分離し、**発注のたびに `docs/workorders/` に 1 ファイル生成**します。実装担当は本書(共通ルール)と担当分の発注書の 2 つを読めば着手できる状態にします。

- ファイル名: `E{番号}-{スラッグ}.md`(例: `E15-auth-account.md`)。フェーズ単位の過去の発注は `phase1.md`・`phase2.md` に記録として残しています。
- 発注書に書くこと(テンプレート): **着手前の前提**(読み替え・決定済み事項・開発者タスク)/ **担当範囲**(Epic・ストーリー・関係する未決・レビューの重点の表)/ **並行可否**。共通ルールの繰り返しは書かない。
- 発注書と本書が食い違ったら、進め方は本書、担当範囲・前提は発注書を正としてください。
